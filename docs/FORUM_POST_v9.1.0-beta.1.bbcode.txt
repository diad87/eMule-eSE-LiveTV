[b][size=4]What is eMule eSE?[/size][/b]

[b]eMule eSE - Streaming Engine[/b] is an experimental GPL fork of eMule 0.70b Community. It preserves ordinary eD2K/Kad file sharing and adds two separate streaming surfaces:

[b]1. Local eSE streaming and media dashboard[/b]

The [b]eSE[/b] toolbar button opens a local dashboard, normally on [code]127.0.0.1:8080[/code]. This is a presentation and control layer over the native eMule client, not a replacement eD2K/Kad engine and not a remote streaming service.

[list]
[*]Browse, search and control normal eMule downloads from a local web interface.
[*]Play completed media directly from the configured Incoming directory.
[*]Play suitable sufficiently downloaded [code].part[/code]/[code].part.met[/code] media before the complete file has finished, where its format and available ranges permit it.
[*]Use byte-range streaming, seeking, audio-track selection and subtitles when supported by the media.
[*]Maintain a local cinema-style library, favourites, posters and metadata.
[*]Play locally reconstructed LiveTV HLS through the packaged HLS.js player, VLC or another compatible local player.
[*]Keep the native [code]emule.exe[/code] authoritative for transfers, peers, Kad, files and Live streams; [code]ese-server.exe[/code] exposes the bounded local API and user interface.
[*]Remain loopback-only by default. Remote dashboard or HLS access requires deliberate configuration and authentication.
[/list]

[b]2. Decentralized P2P LiveTV[/b]

LiveTV allows an eSE user to broadcast a screen, media file, RTMP/OBS input or deterministic test source to other compatible eSE peers. FFmpeg produces independent two-second HLS segments; the native client signs, distributes, requests, relays and reconstructs those segments.

There is no central video server and Kad is not used to carry the video payload. Kad2, PEX, LAN discovery, cache or a direct link can locate a broadcaster; the actual Live control and media records travel as additive eD2K extended-protocol packets between compatible eSE peers. Viewers can obtain segments from several parents and replenish their sources when one disappears.

[b][size=4]What this beta does and does not claim[/size][/b]

[list]
[*]It supports native dual-stack listening and native IPv6 connections between capable eSE peers.
[*]It preserves the original IPv4 eD2K and Kad2 paths for vanilla interoperability.
[*]It can carry LiveTV directly over an IPv6 socket when the viewer has an explicit IPv6 endpoint or learns one through the capability-gated peer-list-v2 path.
[*]It contains an independent experimental Kad6 client and keeps Kad6 routing/persistence separate from Kad2.
[*]It does not claim universal HighID, universal CGNAT traversal, support for every ISP/router/proxy combination or strong anonymity.
[*]It does not operate a stable public Kad6 exit or public KRP relay infrastructure.
[*]It does not claim that automatic IPv6-only LiveTV discovery is complete. The present Kad2 directory still advertises an IPv4 broadcaster endpoint; the explicit IPv6 direct-link and peer-list-v2 paths validate the IPv6 media plane independently.
[*]A local two-instance IPv6-only test proves transport correctness in that controlled topology. It is not presented as proof of public Internet reachability between two physical machines.
[/list]


[b][size=5]Detailed changelog: changes in 9.1.0-beta.1[/size][/b]

The following is the current changelog requested by the Mod guidelines. It first lists the 9.1 delta, then the 9.0 foundations included since stable eSE 8.1, and finally the complete cumulative feature inventory relative to the original eMule 0.70b base.

[b]1. Native dual-stack peer transport[/b]

[list]
[*]Auto and Preferred modes create a dual-stack TCP listener and fall back to IPv4 if the IPv6 bind is unavailable.
[*]An explicitly configured IPv4 [code]BindAddr[/code] remains IPv4-only; enabling the beta does not silently broaden the bind to other interfaces.
[*]Outgoing capable-peer connections preserve the authoritative [code]CAddress[/code] and create an [code]AF_INET6[/code] socket for a native IPv6 target.
[*]Accepted dual-stack sockets retain the real remote family and address instead of collapsing the peer into a synthetic IPv4 identity.
[*]Client lookup, de-duplication, dead-source state and bans are address-aware.
[*]Server-discovered, callback-discovered and LiveTV-discovered IPv6 endpoints retain separate provenance.
[*]Bracketed [code][IPv6]:port[/code] literals are accepted where an additive eSE endpoint can be supplied.
[*]Hostname resolution retains both A and AAAA answers. Complete migration of every [code]getaddrinfo(AF_UNSPEC)[/code] operation to a non-blocking worker remains pending before RC.
[/list]

[b]2. Negotiated IPv6 sources, callbacks and proxies[/b]

[list]
[*][code]CAP_FORK_IPV6_WIRE[/code] is advertised through an additive capability tag and gates the new address-family-neutral records.
[*][code]OP_FOUNDSOURCES_V6 = 0xE2[/code] carries an independent list of full IPv6 source endpoints. The original IPv4 server-source response remains unchanged.
[*][code]OP_CALLBACK_V6 = 0xE1[/code] is accepted only after negotiation, with exact length, a usable address and a previously known endpoint. A buddy cannot use it to force a connection to an arbitrary target.
[*]The optional 32-bit TCP obfuscation port in an extended [code]OP_IDCHANGE[/code] is parsed and retained.
[*]Unknown non-integer [code]SERVER_IDENT[/code] tags are skipped and diagnosed instead of triggering a debug assertion.
[*]SOCKS5 supports [code]ATYP=4[/code] destinations and consumes variable-length replies with unsigned lengths.
[*]HTTP CONNECT emits a bracketed [code][IPv6]:port[/code] authority.
[*]SOCKS4/4A reject IPv6 explicitly instead of truncating or misrepresenting the address.
[*]Unsupported SOCKS BIND replies fail closed instead of being reinterpreted as an IPv4 structure.
[/list]

[b]3. LiveTV over native IPv6[/b]

[list]
[*]Live links and [code]/api/live/direct_join[/code] accept [code]ed2k : //|live|STREAM_KEY|[IPv6]:PORT|TITLE|/[/code] (spaces added here only because this new forum account cannot yet post link-like text).
[*]The web-to-native join request carries a full [code]CAddress[/code]; no IPv6 address is passed through the old 32-bit source field.
[*][code]OP_LIVE_PEER_LIST_V2 = 0xCD[/code] carries [code]<CAddress><TCP port><Score>[/code] for each candidate and is sent only after [code]CAP_FORK_IPV6_WIRE[/code] negotiation.
[*]The receiver accepts the normative scored V2 format and the exact no-score draft emitted by the local beta.2 candidate, then routes a native IPv6 entry through the address-aware connection path.
[*]A V2 list remains capped at 16 candidates; malformed counts, addresses, lengths and ports are rejected.
[*]The strict authenticated tunnel body is still IPv4-only. In strict mode an IPv6 peer-list entry is skipped instead of silently escaping the selected tunnel policy.
[*]Each Live peer has a bounded send backlog. A slow viewer loses recoverable chunks above the limit instead of allowing an unbounded socket queue to consume memory.
[*]The initial push, pull response and relay push paths all apply that backlog guard.
[*]The Live ratio throttle now releases a rejected packet instead of leaking one allocation for every discarded request.
[*]Basic LiveTV still works over Kad2 and direct eD2K extended packets. The new IPv6 direct-join proves that the media data plane does not require Kad6 discovery when an explicit endpoint is already known.
[/list]

[b]4. Kad6: name, purpose and separation from Kad2[/b]

The name is literal: [b]Kad6 means Kad for IPv6[/b]. The "6" refers to IPv6, not to a sixth official Kademlia revision and not to an official successor endorsed by the eMule Project.

The public name deliberately skips [b]Kad3[/b]. Kad3 would naturally suggest a direct third revision of the existing public Kad network. Leaving that name unused keeps it available if this project or another developer eventually proposes a genuine direct successor to Kad2. Conceptually, Kad6 is this project's first Kad generation for the IPv6 era; it is a separate experimental branch designed to coexist with Kad2.

Its wire is family-neutral and can also carry IPv4 endpoints. That permits dual-stack migration, verified fallback and bootstrap, but native IPv6 is the reason the separate overlay and the Kad6 name exist.

[b]Why Kad2 cannot simply be switched to an IPv6 socket:[/b]

[list]
[*]Kad2 contacts, packets, routing maps, firewall checks, buddy/callback paths and several security decisions assume a 32-bit IPv4 endpoint.
[*]The original Kad2 routing table and anti-Sybil/diversity maps are keyed by [code]uint32[/code] IPv4 addresses.
[*]Enlarging an existing packet field would make its layout incompatible with vanilla peers on the public Kad network.
[*]Replacing IPv6 with a synthetic 32-bit value would introduce collisions and could misroute or misidentify a peer.
[*]IPv6 nodes may have several temporary or changing endpoints and may move between native IPv6, dual stack, NAT64/DNS64, 464XLAT and IPv4 fallback.
[/list]

[b]Kad2 remains the compatibility plane:[/b]

[list]
[*]The public Kad2 network, original packets, 128-bit IDs, XOR routing, searches, publications and [code]nodes.dat[/code] remain available.
[*]Kad2 contacts and packets are not enlarged or reinterpreted.
[*]A Kad6 contact cannot be inserted into [code]nodes.dat[/code] or the Kad2 routing table.
[*]Vanilla nodes never receive a Kad6 packet.
[/list]

[b]Kad6 adds a separate native plane:[/b]

[list]
[*]Uses the experimental [code]OP_KAD6HEADER = 0xE6[/code] discriminator and [code]CAP_FORK_IPV6_KAD[/code]; unsupported peers never receive its packets.
[*]Uses an independent routing table and [code]nodes_v6.dat[/code] persistence.
[*]Carries explicit IPv4 or full 128-bit IPv6 addresses with no synthetic address on the wire.
[*]Binds Kad ID, persistent Ed25519 node identity, capabilities and up to four endpoints in signed, expiring records with monotonic epochs.
[*]Keeps indirectly learned contacts in probation until a transaction-bound reply verifies the exact endpoint.
[*]Adds IPv6-first dual-stack endpoint racing with bounded IPv4 fallback.
[*]Adds dedicated bootstrap, hello, route, signed source-store and source-find RPCs.
[*]Applies bounded packet/contact counts, replay and expiry checks, subnet diversity, deterministic vectors and fuzz-tested parsers.
[*]Keeps gateway, tunnel, Strict-path, shaped-carrier and anonymous-quota research behind additional gates; these are optional research layers, not requirements for basic Kad-over-IPv6 and not an anonymity promise.
[/list]

New profiles, and legacy Kad-enabled profiles migrated from [code]NetworkKademlia=1[/code], select both networks with [code]KadNetworkMask=3[/code]. This selects the experimental native Kad6 client alongside Kad2; it does [b]not[/b] enable a public exit, KRP, relay duty, a gateway or bandwidth contribution. Kad2 and Kad6 can be deselected independently, and their routing state remains separate.

Some internal RPC constants retain the historical [code]KADEMLIA3_*[/code] source prefix. Those implementation names do not announce a public network called Kad3.

[b]5. Public-network traffic and why it is included in this review[/b]

This project does not assume that capability negotiation alone makes additional network traffic acceptable. The relevant question is whether every additional request, publication and maintenance operation has a demonstrated purpose and a proportionate cost.

[b]What has not been changed:[/b]

[list]
[*]The original Kad2 [code]SEARCHKEYWORD_TOTAL[/code] remains [code]300[/code].
[*]The original Kad2 packet layouts are not enlarged to carry IPv6 or LiveTV headers.
[*]Kad6 packets use their own discriminator and are sent only to Kad6 endpoints; they are not sent as unknown Kad2 requests to vanilla nodes.
[*]Kad6 public-exit, relay, KRP, contribution, automatic keepalive, Punch3 and bounded port-prediction traffic remain disabled without their respective consent and runtime gates.
[/list]

[b]Additional Kad2 work performed for LiveTV:[/b]

[list]
[*]A broadcaster can publish up to five logical discovery keys: the global [code]eselive[/code] key, one title key, one category key, one language key and one exact stream-hash key.
[*]During the compatibility transition those keys can be published in both the prefixed clean namespace and the legacy eSE namespace. This duplication exists only so earlier eSE releases can still find a channel; it can be disabled independently.
[*]Publication uses an initial discovery burst and then a 60-second steady republish interval while the broadcast remains active.
[*]Viewer searches are protected by a global token bucket capped at ten searches per minute. The same-key cooldown is five seconds while no channel has been found and thirty seconds after results exist.
[*]Stopped channels use bounded tombstone publication and all discovered records have bounded local retention.
[/list]

This traffic is intended to provide measurable channel-discovery latency, compatibility with already released eSE clients and recovery from broadcaster/source churn. It is not video traffic: HLS segments never travel through Kad2.

[b]Additional Kad6 work:[/b]

[list]
[*]The native Kad6 client performs its own bounded bootstrap, hello, routing maintenance, signed source publication and source lookup.
[*]Its packets are useful only between compatible Kad6 nodes. With a small population, some bootstrap or maintenance attempts may produce no usable result.
[*]This beta deliberately selects Kad6 together with Kad2 on a new or migrated Kad-enabled profile. The user can deselect Kad6 independently and immediately.
[*]The present test evidence demonstrates codec, routing, isolation, security-gate and controlled-topology behaviour. It is not presented as proof that the current public-network cadence or default selection has already been accepted by the eMule Project.
[/list]

I am therefore explicitly asking the reviewers to judge both the mechanisms and their cost. In particular, I am prepared to make Kad6 opt-in instead of selected by default, reduce its maintenance cadence, disable legacy LiveTV namespace duplication, lengthen LiveTV publication/search intervals or move LiveTV discovery away from public Kad2 if the current behaviour is considered disproportionate.

[b]Measured Kad2/NetLab traffic evidence - 24 July 2026:[/b]

[list]
[*]A 30-second isolated profile with NetLab declined and disabled produced no Punch2 attempts, Punch3 operations or keepalive ping/pong counter movement.
[*]A real two-process local run maintained one active keepalive peer for 55 seconds while receiving 30 LiveTV chunks. It produced two pings and two correlated pongs, with no visible keepalive loss. When the origin later had zero keepalive peers, leaving the service running produced no pings.
[*]The origin's cumulative counters contained 2,838 pings and 2,823 correlated pongs: a 99.47% observed response rate. The 15 unmatched pings represent at most 750-990 IPv4 bytes sent without a visible response; they may include transient loss and are not automatically classified as redundant traffic.
[*]One keepalive peer at the present fixed 25-second cadence costs 331,776-442,368 IPv4 bytes per day, depending on Kad encryption overhead. Ten peers cost approximately 3.32-4.42 MB per day.
[*]A return-routability cookie adds 118-150 IPv4 bytes to a Punch2 attempt. This is an intentional security cost, not periodic traffic.
[*]A [code]spread=4[/code] port-prediction attempt adds 448-576 bytes for its eight initial extra requests. It remains disabled by default and should be used only after a base failure or restrictive-NAT classification.
[*]A complete Punch3 signalling exchange costs 390-518 IPv4 bytes before uTP data. It is an escalation path, not continuous background traffic.
[*]FastKad has no periodic traffic generator. It can add a query only when its bounded adaptive timer triggers an earlier retry.
[*]A physical home-to-tethering run was repeated with overlay paths removed. The native public connection did not form during the 35-second window, so the destination never became an authenticated NetLab peer and Punch2/Punch3 emitted zero extra datagrams. This is positive fail-closed behaviour, but it does [b]not[/b] measure Punch2 effectiveness.
[/list]

The present keepalive volume is small in absolute terms, but its fixed 25-second cadence has not been demonstrated as necessary for every NAT. A model using 120-300 second UDP timeouts indicates that an adaptive refresh could avoid approximately 74-90% of that traffic; this is a model, not a measured NAT result. The project therefore does not claim a demonstrated CGNAT success improvement yet. A physical A/B matrix and measured UDP timeout are still required.


[b]6. IPv6 identity, credits and anti-abuse[/b]

[list]
[*]IPv6-only endpoints never enter the inherited IPv4 SecureIdent, credit, friend, buddy, Kad firewall, hole-punch or uTP-expectation formats through a fabricated IPv4 address.
[*]This beta uses a neutral IPv6-only credit policy. The peer can transfer, but receives no inherited IPv4 credit multiplier and its wait state remains local.
[*]A new IPv6 peer no longer receives artificial queue age from a synthetic compatibility key.
[*]Bans, bad-request accounting, hash history and address comparisons use the native address.
[*]The queue anti-Sybil limit groups IPv6 endpoints by [code]/64[/code] instead of using an IPv4 [code]/24[/code] rule or a 32-bit truncation.
[*]A future key-bound eSE credit identity remains possible, but it is not claimed by this beta.
[*]The original 0.70b download-queue source policy is restored: only a complete single-part file can answer as a source before it moves to the shared-file list.
[/list]

[b]8. Relay and connection lifecycle hardening[/b]

[*]A locally accepted KRP configuration or kill switch can take effect without restarting eMule.
[*]Incomplete KRP settings disable the client instead of opening a partially authenticated path.

[b]9. Core reliability carried forward into 9.1[/b]

[list]
[*]Stored-search restoration is time-sliced so a large [code]StoredSearches.met[/code] file does not monopolize the UI thread.
[*][code]known.met[/code] serialization is time-sliced and handed to a below-normal-priority writer.

[*]After a transferred block, a stopped file cancels, a paused/error file requeues and a healthy file remains connected.
[*]Kad fast-refresh classification is hardened against backward wall-clock movement and interval underflow.
[/list]

[b][size=4]How large is the fork?[/size][/b]

This is not a small UI patch or an external wrapper. A conservative direct Git tree comparison made at the 9.0 baseline against [code]eMule_v0.70b-community[/code] gave the lower bounds below; the additional 9.1 work is not used to inflate them:

[list]
[*]At least [b]669 first-party files changed[/b], with more than [b]131,000 inserted lines[/b]. This scope excludes vendored dependencies, node_modules, generated package copies and deprecated dashboard copies.

A 25-second keepalive interval costs little in absolute terms, but the whole cadence is not yet justified as necessary. Modelling a refresh at 80% of an assumed 120-300 second UDP timeout gives a potentially avoidable fraction of approximately 74-90%, or 245,376-396,288 bytes per peer per day. [b]A. Native P2P LiveTV engine[/b]

[b]LiveTV protocol architecture[/b]

LiveTV is divided into four independent planes:

[list=1]
[*][b]Production:[/b] FFmpeg converts screen, file, RTMP/OBS or test input into independent two-second HLS segments.
[*][b]Discovery:[/b] the broadcaster publishes a bounded directory record through Kad2; viewers may also learn it through PEX, TTL-1 LAN discovery, cache or a direct stream-key link.
[*][b]Control:[/b] compatible eSE peers subscribe, exchange the live-edge bitmap, announce new sequences, measure RTT, exchange alternative sources and signal denial or shutdown.
[*][b]Media:[/b] viewers request missing sequences and receive complete HLS segment records directly or through optional tunnel/Bulk paths. Broadcaster-originated Chunk V2 records are signed; the legacy Chunk V1 compatibility format is not.
[/list]

Kad is therefore used for [b]discovery and optional control routing[/b], not as the video payload transport. Ordinary Live chunks travel as additive eD2K extended-protocol packets between compatible peers.

[b]Broadcast identity and segment model:[/b]

[list]
[*]Every broadcast generates a fresh ephemeral Ed25519 key pair; the private key is never persisted.
[*][code]streamKey[/code] is the first 16 bytes of SHA-1 over the broadcaster public key.
[*]A receiver accepts the advertised public key only when it reproduces the expected [code]streamKey[/code].
[*]The private key signs Chunk V2 and the final END record and is destroyed when broadcasting stops.
[*]The live ring contains 16 two-second segments, providing approximately 32 seconds of bounded history.
[/list]

[b]Direct LiveTV wire protocol under [code]OP_EMULEPROT[/code]:[/b]

[code]
0xC3 SUBSCRIBE   <streamKey 16><viewerHash 16><uploadCapacity u32>
0xC4 UNSUBSCRIBE <streamKey 16><viewerHash 16>
0xC0 ANNOUNCE    <streamKey 16><newestSeq u32><bitrate u16>[<pubkey 32>]
0xC6 HEARTBEAT   <streamKey 16><bitmap u16><oldestSeq u32>[bounded PEX]
0xC1 REQUEST     <streamKey 16><sequence u32>
0xC2 CHUNK       <streamKey 16><sequence u32><timestamp u32><size u32><data>
0xCC CHUNK_V2    <streamKey 16><sequence u32><timestamp u32><size u32>
                 <bitrate u16><SHA-256 32><Ed25519 signature 64><data>
0xE0 CHUNK_FRAG  <streamKey 16><sequence u32><fragment index/count>
                 <inner opcode><total length><fragment>
0xCA PEER_LIST   <streamKey 16><count u16>(<IPv4 u32><TCP port u16>)[count]
0xCD PEER_LIST_V2 <streamKey 16><count u16>
                  (<CAddress><TCP port u16><Score u8>)[count]
0xC9/0xCB PING/PONG <streamKey 16><pingId u32><timestamp u64>
0xC7 DENY        <streamKey 16><reason u8>
0xC8 END         <streamKey 16><reason u8>[<Ed25519 signature 64>]
[/code]

The base messages are accepted only from a peer identifying as an eSE client. Fragmentation, the scored address-family-neutral peer list, authenticated tunnels, Bulk/FEC and the Kad6 gateway have additional capability gates. The V2 reader also accepts the exact no-score draft produced by the local 9.0 beta.2 candidate; new writers emit the scored form.

[code]CHUNK[/code] is the original unsigned compatibility record. A broadcaster normally emits signed [code]CHUNK_V2[/code]; however, the present non-owning mesh-relay path can still serialize a relayed segment as V1. The authenticity statements below therefore apply to V2 records, not to every possible compatibility-path segment.

[b]Why Kad6 is still needed when LiveTV already works over Kad2[/b]

Kad2 makes compatibility possible, but it has no native Live record or Live search header. A stream must look like a synthetic one-byte file entry, and extra semantics are encoded as unrelated keyword tags. Kad2 has no native fields for:

[list]
[*]Live versus file/source/notes search kind.
[*]Kad2 versus Kad6 result origin.
[*]Request and response correlation.
[*]Per-request result limit and deadline.
[*]Cancellation and final completion status.
[*]Canonical typed Live metadata.
[*]Authenticated target authorization.
[*]A signed, expiring IPv4/IPv6 endpoint set.
[*]A privacy rule requiring an endpoint to remain at the exit.
[/list]

Changing existing Kad2 packets to add those headers would break their layout for public-network peers.

Two related Kad6 surfaces must be distinguished:

[list]
[*][b]Native Kad6 UDP overlay:[/b] [code]OP_KAD6HEADER[/code] followed by the capability-gated bootstrap, hello, route, source-store and source-find RPC families. These use family-neutral routing and signed endpoint/source records.
[*][b]K6 gateway protocol:[/b] a [code]K6FrameV1[/code] carried inside [code]TUN_OP_KAD6_GATEWAY[/code]. This is where the current typed Live search and authorization headers are implemented.
[/list]

The following are therefore native K6 control/search headers, not video headers and not a claim that a public native Kad6 Live-store RPC is already deployed:

[code]
K6FrameV1:
  version | message_type | flags | request_id |
  session_id | body_length | body

K6 SEARCH_START:
  search_kind | network_mask | max_results | deadline |
  target_hash | query | options

K6 SEARCH_RESULT:
  result_id | result_kind | network_origin |
  canonical tags | optional target tickets

K6 SEARCH_END:
  status | result_count | queried_nodes | elapsed | load_hint
[/code]

For privacy-preserving Live discovery, the K6 result contains the title, category, language, bitrate, viewer count and start time but [b]forbids the broadcaster IP and ports[/b]. Unlike a file-source result, a Live result must not contain a reusable target ticket, because that ticket would expose its endpoint. The exit instead retains a short-lived authorization mapping under:

[code]
authenticated circuit + source request_id + result_id
[/code]

The mapping and its matching origin-side route currently expire after 120 seconds. The viewer subscribes later using only [code]<result_id 16><source_request_id u32><version 2>[/code] over that same pinned circuit. The exit resolves and contacts the broadcaster. This gives LiveTV native correlation and endpoint-hiding semantics which cannot be obtained by simply adding another Kad2 metadata tag.

[b]Current boundary:[/b] the implemented K6 Live gateway presently wraps a real Kad2 search at the exit; its Live request explicitly selects the Kad2 network, and its opaque Live-subscribe resolver currently materializes an IPv4 broadcaster endpoint. Thus Kad2 remains the working public directory while the K6 side already provides the typed, correlated and privacy-preserving control headers. Independently, 9.1 can dial a bracketed IPv6 direct link and can learn a native IPv6 peer through [code]OP_LIVE_PEER_LIST_V2[/code]. Codecs for Kad6-origin results, signed source/endpoint records and a Live-public record class exist, but a complete public LiveTV publication/search path and opaque IPv6 Live endpoint resolution running natively on the Kad6 UDP overlay are not claimed as finished.

Kad6 is therefore [b]not required for basic LiveTV or for media transfer to an explicitly known IPv6 endpoint[/b]. It is required by the design for the [b]complete IPv6-native, typed and privacy-preserving evolution of the LiveTV discovery/control architecture[/b]: native search kind, correlation, deadlines, cancellation, origin, typed metadata, signed expiring endpoints and endpoint-hiding authorization cannot be added safely by changing the public Kad2 packet layouts.
