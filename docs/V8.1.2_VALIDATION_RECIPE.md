# v8.1.2 Data plane bulk — Receta de validación (smoke 2/3-PC + bench G1)

> El data plane bulk (chunks por el túnel con FEC) está **code-complete y compila** (build8,
> 2026-06-13) pero con **CERO validación runtime**. Esta receta lo arranca por primera vez.
> El binario es **WIP + cambios bulk mezclados** (no es un release): `emule_v8.1.2-test2.exe`.
> `ese-server.exe` es **idéntico al de v8.1.0** (los cambios bulk son todos C++), así que los
> nodos del banco pueden conservar el suyo.

---

## 0. Qué se está probando (y qué NO)

El bucle nuevo: **el exit recibe los chunks del broadcaster, los FEC-codifica y los empuja por
el túnel como celdas `0xD9`; el viewer las descifra, reensambla el segmento y lo inyecta en su
HLS**. Antes de v8.1.2 los chunks iban directos (la IP del viewer se exponía).

- **Smoke (3-PC, 1 salto):** ¿arranca el path bulk sin crash/deadlock? ¿el viewer reconstruye
  segmentos vía FEC? Ejercita ingest + encode + carrier + decode + inject. **NO** prueba el
  reenvío de 2 saltos (F-1) ni G1 (a 1 salto el exit ve al viewer).
- **Bench G1 (4-PC, 2 saltos):** hop1 ≠ exit ≠ broadcaster → el exit NO ve la IP del viewer.

## 1.5 Con solo 2 PCs (B + X) — smoke de REGRESIÓN (no del data plane)

⚠️ **El data plane bulk necesita 3 nodos DISTINTOS** (broadcaster, exit, viewer): el exit y el
viewer **no pueden ser el mismo nodo** (en loopback el chunk se divierte al path bulk y se
re-inyecta… volviendo a divertirse; ahora hay un guard que lo evita, pero entonces el nodo
reproduce por el camino directo, NO por el bulk). Así que con 2 PCs **no se ejercita la entrega
bulk** — pero sí se valida que **el binario nuevo no rompe lo que ya funcionaba** (¡importante
tras semejante volcado de código!):

1. Arranca `emule.exe` (el test build) en **B** y **X**.
2. **B** emite; **X** lo ve por el túnel como en Sprint Z (X-Adaptive/Tunelizado viendo B,
   1-hop o loopback; sembrar circuito con `test_circuit`).
3. **Criterios de PASA (regresión):**
   - [ ] Ningún **crash** al arrancar ni durante 10 min de broadcast+view.
   - [ ] Ningún **deadlock/freeze** (UI responde, logs fluyen) — valida que los hooks E3.1 y el
         lock-hoja no atascan el camino normal de recepción de chunks.
   - [ ] **El control plane sigue OK:** búsqueda Kad tunelizada, subscribe, heartbeat relay (como v8.1).
   - [ ] **X reproduce el stream** (por el camino directo — el guard evita el bucle de re-divert).
   - [ ] En el log de arranque: `Privacy: TAG_ESE_CAPS runtime = 0x...` con el **bit 0x4000**
         encendido (la cap bulk se anuncia) → confirma que la negociación está lista para 3 PC.
4. Si todo eso pasa → la base no regresiona y está lista para que, **cuando tengas el 3er PC**,
   hagas el smoke real del §2. Si algo peta aquí, es un bug en el camino común (mejor encontrarlo
   con 2 PCs que con 3).

## 2. Smoke test — 3 PC, 1 salto (el data plane DE VERDAD)

**Roles e IPs** (ajústalas a tu Tailscale):

| Nodo | Rol | Modo | Notas |
|------|-----|------|-------|
| **B** | broadcaster | **Directo** (arranca en Directo → cap 0x2600, no es exit) | emite un stream a **bitrate BAJO primero** (p.ej. 2000-4000 kbps) para descartar el límite de paquete/encode antes de subir |
| **X** | **exit PURO** | **Tunelizado** (o Adaptive) | ⚠️ **X NO debe estar viendo el stream en su propio VLC** — si lo ve, su hook divierte sus chunks al path proxy y le rompe la reproducción (limitación conocida, ver §5). X solo actúa de exit. |
| **V** | viewer | **Tunelizado + Balanced** | abre la URL del stream; construye el circuito a X |

**Pasos:**
1. **B** empieza a emitir. Confirma que reproduce localmente.
2. **V** abre `http://localhost:8080/live/watch/<STREAMKEY>`. En modo Tunelizado el pool no
   auto-construye → **siembra el circuito** con `test_circuit` (REST `/api/live/privacy/test_circuit?hops=1`
   o el botón del panel). El exit del circuito debe ser **X** (si hay más peers tunnel-capable,
   fija hop1 con `&hop1ip=<IP_de_X>` cuando esté implementado; con solo X disponible sale por X).
3. V tunnel-suscribe → **X se proxy-suscribe a B** → B **empuja** los chunks a X.

**Qué buscar en los logs (señal de éxito):**

| Log en | Línea (las añadí yo) | Significa |
|--------|----------------------|-----------|
| **X** (exit) | `[TUN] C2 exit-proxy SUBSCRIBE -> B...` | X se suscribió a B en nombre de V |
| **X** | `LiveTunnel: exit pushed bulk seq=N — M symbols across K viewer-session(s), J blocks` | **X FEC-codificó y empujó un segmento** ✅ |
| **V** | `LiveTunnel: [E3.2] viewer bulk-subscribed on N circuit(s)` | el trigger disparó (subscribe explícito) |
| **X** | `LiveTunnel: [E3.2] bulk SUBSCRIBE circ=... session=...` | X registró la sub bulk de V |
| **V** | `LiveTunnel: bulk segment rebuilt seq=N (... bytes, J blocks) via FEC — injecting` | **V reconstruyó un segmento vía FEC y lo inyectó** ✅✅ |
| **V** | VLC reproduce el stream | **el bucle entero funciona** 🎯 |

**Criterios de PASA (smoke):**
- [ ] Ningún **crash** en X ni V durante 5 min.
- [ ] Ningún **deadlock / freeze** del main thread (UI responde, el log sigue fluyendo).
- [ ] Aparecen `exit pushed bulk` (X) **y** `bulk segment rebuilt` (V).
- [ ] VLC en V reproduce (aunque sea con cortes — eso es ajuste, no fallo de arranque).
- [ ] Sube el bitrate a 8000 → 12000 kbps y repite (el path de fragmentos 0xE0 es el real a ≥1.8 MB/segmento).

> A 1 salto el path bulk corre pero V **también** puede seguir pulando directo de B (camino
> v8.1). Eso es OK para el smoke (solo verificamos que el bulk ENTREGA). El G1 (V no pula
> directo) es el bench de 4 PC.

## 3. Bench G1 — 4 PC, 2 saltos reales

Para que el exit NO vea la IP de V hace falta **hop1 ≠ exit**, es decir 3 relés tunnel-capable
distintos además del broadcaster:

| Nodo | Rol | Modo |
|------|-----|------|
| **B** | broadcaster | Directo |
| **H** | hop1 (relé intermedio) | Tunelizado/Adaptive |
| **X** | exit puro | Tunelizado |
| **V** | viewer | Tunelizado + STRICT |

1. V siembra un circuito **2-hop** (`test_circuit?hops=2`) con hop1=H, exit=X (fija con
   `&hop1ip=H` cuando esté implementado; si no, asegúrate de que H y X son los dos únicos peers
   tunnel-capable además de B, para que F-2 elija hop1≠exit).
2. **Aceptación G1:** captura **por-proceso** (Wireshark/netstat) en **X** durante 5 min →
   **CERO flujo a la IP de V**. Y grep en B y V: **0** `OP_LIVE_CHUNK`/`CHUNK_V2`/`CHUNK_FRAG`
   directos hacia/desde V en modo STRICT.
3. Stream reproduce en VLC de V por el camino bulk de 2 saltos.

## 4. Si algo peta — dónde mirar primero (las zonas sin validar)

1. **Cripto / AEAD desync:** si V loguea fallos de descifrado o el circuito muere al primer
   símbolo perdido → el nonce explícito (B2) no está bien cableado. Mirar `OnionDecryptAllExplicit`
   / `EncryptOneLayerExplicit` (LiveCircuit.cpp) y que `nonce_seq` viaja en el wire.
2. **Deadlock:** si la UI se congela cuando arranca el push → orden de locks. El diseño es
   lock-hoja (los hooks solo tocan `m_proxyIngestLock`), pero verifícalo. Saca un dump
   (`emule.exe` colgado → mini-dump) y mira qué hilos están en qué lock.
3. **Wire mismatch:** si X empuja pero V no reconstruye (`bulk segment rebuilt` nunca aparece) →
   desajuste en el header BULK_DATA o en el layout multi-bloque. Comparar `BulkDataPack`/`Parse`
   y `BulkComputeLayout` entre exit y viewer (mismo `msg_len` → mismo layout).
4. **Encode stall a 12000:** si a alto bitrate el main thread da hitches → el encode RS + AEAD
   inline (ProcessProxyIngest) es demasiado pesado → toca E8.5 (offload a worker). Empieza a
   bitrate bajo para aislar.
5. **Nada se empuja** (`exit pushed bulk` nunca) → X no está recibiendo los chunks de B
   (¿se proxy-suscribió? ¿B le empuja?) o `IsExitProxying` es false (¿RefreshProxyKeys corrió?).

## 5. Limitaciones conocidas de esta build (no son bugs del smoke)

- **Exit que TAMBIÉN ve el stream — ARREGLADO (build9, guard):** ahora el hook NO divierte un
  stream que el propio nodo está viendo (`m_bViewing && streamKey==m_streamInfo.streamKey`), así
  que un nodo exit+viewer **reproduce normal** (por el camino directo) y no entra en el bucle de
  re-divert. El coste: ese nodo no sirve bulk a otros (prioriza su propia reproducción). Para el
  smoke del §2, X debe seguir siendo exit PURO (no viendo) para que SÍ diverta y se ejercite el bulk.
- **Cap DoS por bytes de 0xD9:** aún es el cap de celdas (débil); no abusar en el banco.
- **Sin r adaptativo / créditos (E4′/E7):** el push va a `r=BULK_DEFAULT_R=3` fijo, sin
  backpressure. Si V es lento, X no frena (puede acumular).
- **Striping:** con 1 circuito (1 salto) no hay striping real (todo va por el único circuito).
  El striping interleaved se ejercita con un viewer de ≥2 circuitos bulk.
- **Todo esto es WIP sin validar.** Este es literalmente el primer arranque.
