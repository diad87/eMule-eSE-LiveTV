# v8.1 Sprint B — Desglose ejecutable (Búsqueda Kad real por túnel)

> Spec de implementación del **Sprint B** de [`V8.1_SPRINT_PLAN.md`](V8.1_SPRINT_PLAN.md).
> Convierte el `tunnel_search` demo (lee la caché local del exit) en una **búsqueda
> Kad nativa real**: el exit ejecuta una `CSearch` contra la DHT en nombre de V,
> acumula resultados asíncronos y los devuelve enriquecidos por el túnel.
>
> Refs `archivo:línea` verificadas por exploración directa del código a 2026-06-11.
> Depende de **Sprint A completo** (commit `2c9bfeb`): framing multi-cell, dispatcher,
> API async, pinning, y **el marco A6 de operaciones diferidas** — la pieza sobre la
> que se monta todo Sprint B.

## 0. Pre-flight — lo que YA existe (NO reconstruir)

La auditoría reveló que el subsistema de búsqueda Kad del fork es **maduro y completo**.
Sprint B es más pequeño de lo estimado en el plan original porque **reutiliza** estas
piezas en vez de construirlas:

| Pieza | Dónde | Estado |
|---|---|---|
| Búsqueda Kad keyword real | `kademlia/.../SearchManager.cpp:115` `PrepareFindKeywords()` | Funciona. **Main thread only.** |
| Búsqueda Live dual-namespace + rate-limit + cooldown | `LiveKadBridge.cpp:495` `SearchStreams(keyword)` | **Ya hace búsquedas Kad reales.** Token bucket 10/min, cooldown adaptativo. |
| Hash de keyword eSE (namespace limpio) | `Kademlia.cpp:602` `EseLiveGetKeywordHash()` (prefijo `\x00eSE\x00`) | **B4 ya existe.** + legacy `KadGetKeywordHash()` (`:579`). |
| Parsing completo del resultado Kad | `Search.cpp:1113` `ProcessResultKeyword()` | Extrae **todos** los tags Live: `sLiveKey`, title, category, language, bitrate, viewers, IP/port/uport, startedAt, AICH. **Corre en el hilo UDP listener.** |
| Puente resultado→directorio | `Search.cpp:1298-1312` → `LiveKadBridge.cpp:689` `OnKadSearchResult()` | Puebla `m_streamDirectory` (la caché que el exit ya sirve). |
| Caché de streams (= el "B6" parcial) | `LiveKadBridge.h:137` `m_streamDirectory` + `GetKnownStreams()` (`:641`) | Ya filtra tombstones, ya rate-limita. |
| Marco A6 diferido | `LiveTunnel.cpp:1335` `BeginExitOperation`/`CompleteExitOperation`/`AbortExitOperation` | **El andamiaje de Sprint B.** Sweep TTL 60 s ya integrado en `Tick()`. |
| Transporte multi-cell de respuesta | `SendReply()` (`:1376`) con `reply_op >= 0x40` → `SplitIntoCells` | Hasta `TUN_MSG_MAX_BYTES` (64 KB), 256 frags. Cientos de resultados caben. |
| Camino async V-side | `TunneledKadSearch()` (`:1496`) + A3 `RegisterPending`/`WaitPending` | Ya bloquea por evento, sin poll. |

**Implicación de alcance:** el corazón de Sprint B **no** es "implementar búsqueda Kad"
(ya existe). Es **conectar el exit a esa búsqueda y resolver el marshaling del
resultado asíncrono**: la búsqueda se lanza en el main thread, los resultados gotean
en el **hilo UDP listener** durante hasta 45 s, y la respuesta debe enviarse por el
túnel (sockets = main thread). Ese cruce de hilos + la **ventana de acumulación** son
el trabajo real.

## 1. El reto central — modelo de hilos

```
  HILO MAIN (ListenSocket / Kad Process ~1 Hz)        HILO UDP LISTENER (CAsyncSocket)
  ──────────────────────────────────────────         ────────────────────────────────
  OnCellReceived(TUN_OP_KAD_SEARCH_V2)
    └─ ExitHandle_KadSearchV2 (B1)
        ├─ BeginExitOperation(ctx, KAD_RESULT_V2)   (A6)
        ├─ crea TunnelSearchJob{circ_id,req_id,
        │     keyword, deadline, results, lock}
        ├─ siembra results con GetKnownStreams()      (caché → respuesta rápida)
        └─ SearchStreams(keyword) → searchIDs[]       (búsqueda fresca; MAIN THREAD ✓)
              │
              │   ... (hasta 45 s) ...                  Process_KADEMLIA2_SEARCH_RES
              │                                          └─ ProcessResultKeyword (Search.cpp:1113)
              │                                              └─ OnKadSearchResult (parsing completo)
              │                                                  └─ HOOK B2: ¿searchID es de un
              │                                                      TunnelSearchJob? → job.AddResult()
              │                                                          (bajo job.lock)   ▲
              │                                                                            │ cruce de hilo
  ProcessMainThreadWork() / Tick()  ◄───────────────────────────────────────────────────┘
    └─ por cada TunnelSearchJob (B2):
        si (now >= deadline) || (results >= CAP) || (búsqueda terminada):
          ├─ serializar results → KAD_RESULT_V2 (B3)
          ├─ CompleteExitOperation(circ_id, req_id, payload)   (A6 → SendReply multi-cell)
          ├─ StopSearch(searchIDs)                              (B1 cleanup, MAIN THREAD ✓)
          └─ borrar el job
```

**Reglas de hilo (de la auditoría, `Search.cpp` + `Kademlia.cpp:330`):**
- `PrepareFindKeywords` / `SearchStreams` / `StopSearch` → **solo main thread**.
- `ProcessResultKeyword` / `OnKadSearchResult` → **hilo UDP listener**. El hook B2 que
  mete resultados en el job cruza al estado del job → **el job necesita su propio lock**
  (igual que `m_pendingLock` protege A3/A6).
- `CompleteExitOperation` toca sockets → **solo main thread** (lo dispara `Tick`, no el
  callback UDP). Por eso la ventana de acumulación se evalúa en `Tick`, no en el callback.

**Por qué ventana de acumulación y no streaming inmediato:** los resultados llegan de
uno en uno durante decenas de segundos. Responder por celda según llegan (B5 "real")
exigiría múltiples `KAD_RESULT_V2` y un reassembly del originador que admita "más por
venir" — el reassembly actual asume `frag_count` fijo. **MVP de Sprint B: una respuesta
tras una ventana corta** (`TUN_SEARCH_WINDOW_MS`, p.ej. 6-8 s) o al juntar `CAP`
resultados, lo que ocurra antes. La entrega incremental verdadera (B5) se documenta como
extensión, no MVP.

## 2. Wire format nuevo

### 2.1 Opcodes (`enum TunnelOpCmd`, `LiveTunnel.h:103`)

Reservados libres confirmados (`0x42-0x7F`):

| Valor | Op | Dirección | Celda |
|---|---|---|---|
| `0x42` | `TUN_OP_KAD_SEARCH_V2` | V → exit | multi-cell (keyword; permite filtros futuros) |
| `0x43` | `TUN_OP_KAD_RESULT_V2` | exit → V | multi-cell (registros ricos) |
| `0x44` | `TUN_OP_KAD_CANCEL` | V → exit | single-cell framed (solo req_id) |

`0x10`/`0x11` (`KAD_SEARCH`/`KAD_RESULT` legacy single-cell) **se conservan** para compat:
un peer que no negocie V2 sigue recibiendo la caché local en formato `title|bitrate|viewers`.

### 2.2 `TUN_OP_KAD_SEARCH_V2` (request) — body

```
[0]       flags        uint8   (bit0 = incluir caché local en la respuesta; bit1 = solo fresco)
[1..2]    kw_len       uint16 LE
[3..]     keyword      UTF-8 (normalizado: lowercase, sin diacríticos — igual que SearchStreams)
```
Cabe en 1 fragmento. Va framed (>=0x40) por uniformidad con el dispatcher multi-cell.

### 2.3 `TUN_OP_KAD_RESULT_V2` (reply) — body

```
Cabecera (4 B):
  [0..1]   result_count  uint16 LE
  [2]      result_flags  uint8   (bit0 = parcial/“more coming” [reservado B5]; bit1 = final)
  [3]      reserved      uint8

Luego result_count registros, cada uno longitud-prefijada:
  [0..1]   rec_len      uint16 LE   (bytes del registro, sin contar estos 2)
  [2..17]  stream_key   16 B
  [18..21] source_ip    uint32 LE   (0 = desconocida)
  [22..23] source_port  uint16 LE
  [24..25] source_uport uint16 LE
  [26..29] bitrate      uint32 LE   (kbps)
  [30..33] viewers      uint32 LE
  [34..37] started_at   uint32 LE   (unix)
  [38]     category     uint8
  [39]     ns           uint8       (0=clean, 1=legacy, 2=unknown — discoveryNamespace)
  [40]     title_len    uint8
  [41..]   title        UTF-8
  [..]     lang_len     uint8
  [..]     language     UTF-8
```

- Registro típico ~50-90 B. Con `TUN_MSG_MAX_BYTES`=64 KB → cap práctico holgado;
  **fijar `TUN_SEARCH_MAX_RESULTS` = 100** (anti-DoS + UX razonable).
- El stream_key (16 B) **sí** se envía ahora (el demo lo omitía) — V lo necesita para
  suscribirse (Sprint C) sin re-buscar.
- **Compat:** formato append-only. `rec_len` permite a V saltar registros con campos
  futuros que no entienda.

### 2.4 Constantes nuevas (`LiveCellQueue.h` o `LiveTunnel.h`)

```
TUN_SEARCH_WINDOW_MS     = 7000     // ventana de acumulación antes de responder
TUN_SEARCH_MAX_RESULTS   = 100      // cap de registros por respuesta
TUN_SEARCH_JOB_TTL_MS    = 50000    // hard-stop de un job (> SEARCHKEYWORD_LIFETIME 45 s)
```

### 2.5 Capability

Reusar `ESE_CAP_TUNNEL_DATAPLANE` (0x1000, Sprint A): un exit con el bit entiende V2.
Sin el bit → V cae a `TUN_OP_KAD_SEARCH` (0x10) legacy. No hace falta bit nuevo.

## 4. Privacidad — qué cambia y qué se mantiene

- **Hoy** (`ExitHandle_KadSearch`): el exit lee su caché local; el keyword de V no toca Kad
  desde V, pero tampoco se busca de verdad — solo se sirve lo que el exit ya tenía.
- **Sprint B:** el exit **emite el keyword a Kad en su propio nombre** (`SearchStreams`).
  Esto es **exactamente el modelo deseado** (tesis §6.2.1 A1.V1): la red Kad ve que *el
  exit* busca ese keyword, asociado a la **IP del exit, no la de V**. V queda protegido.
- **El keyword llega en claro al exit** — aceptado por diseño (tesis **Decisión 12.3**: el
  cifrado del keyword hacia el exit es roadmap v9.0). Documentar en el código.
- **Sin cambio en G1/G6:** Kad nativo intacto; nodos 0.70b no se enteran; opcodes nuevos
  en rango reservado; tags Kad sin tocar.
- **Anti-amplificación:** el rate-limiter existente de `SearchStreams` (10/min) **protege al
  exit de ser usado como amplificador** de búsquedas Kad por un V malicioso. B6 (cache por
  keyword) lo refuerza. **Mantener el rate-limit per-circuito además del global** (un V no
  debe poder agotar el presupuesto de búsqueda del exit para otros).

## 6. Gotchas

- **Hilo de los resultados:** `OnKadSearchResult` corre en el **hilo UDP**, no el main.
  El hook B2 solo puede tocar el job bajo lock; **jamás** enviar celdas ni tocar circuitos
  ahí. El envío lo hace `Tick` (main).
- **El job y la `ExitOperation` son dos cosas:** la `ExitOperation` (A6) guarda *a dónde
  responder*; el `TunnelSearchJob` guarda *el trabajo en curso*. Mantener ambos
  keyed por el mismo `ExitOpKey(circ_id, req_id)` para correlacionar.
- **`StopSearch` siempre en main thread.** Nunca desde el callback ni el destructor del job
  si éste pudiera correr en otro hilo.
- **Cap de tamaño:** un keyword popular puede traer 300 resultados (`SEARCHKEYWORD_TOTAL`).
  Cap a `TUN_SEARCH_MAX_RESULTS`=100 **antes** de serializar, o reventarás `TUN_MSG_MAX_BYTES`.
- **No re-emitir el keyword de V dos veces:** B6 (cache) evita que pulsar refresh dispare
  una emisión Kad por clic.
- **req_id de un solo uso:** el modelo A3 consume el `PendingRequest` al primer
  `SignalReply`. El MVP (una respuesta) encaja; B5.2 (múltiples) NO — por eso se difiere.
- **Reusar la validación de `OnKadSearchResult`** (IP/bitrate/viewers/self/IPFilter). No
  re-implementar ni saltársela.

## 7. Definition of Done — Sprint B

- [ ] `tunnel_search?keyword=X` ejecuta una **`CSearch` Kad real** desde el exit (no solo
      caché) — verificado con un stream publicado en un 3er nodo que el exit no tenía cacheado.
- [ ] La respuesta es **rica y multi-cell**: JSON con `stream_key`, IP/port/uport, bitrate,
      viewers, category, language, started_at, ns — 30+ resultados íntegros.
- [ ] Dual-namespace: streams en clean y en legacy ambos aparecen con `ns` correcto.
- [ ] Cancelación: timeout de V o muerte de circuito → el exit hace `StopSearch`, sin
      `CSearch` huérfanas ni fugas de job.
- [ ] Cache: keyword repetido en < TTL responde rápido sin segunda emisión Kad.
- [ ] Anti-amplificación: rate-limit per-circuito + global activo.
- [ ] Privacidad: el keyword se emite a Kad desde la IP del exit, nunca la de V (verificado
      conceptualmente; documentado que el keyword llega en claro al exit, Decisión 12.3).
- [ ] Interop: peer sin `ESE_CAP_TUNNEL_DATAPLANE` → V cae a `TUN_OP_KAD_SEARCH` 0x10 legacy.
- [ ] Compila x64 Release sin warnings nuevos; verificado end-to-end en 2 PCs (ideal 3).

## 9. Limitación honesta (etiquetado)

Sprint B tuneliza la **búsqueda** (el plano de control): protege *qué busca V*. **No**
tuneliza la descarga del stream (los chunks siguen directos hasta v8.1.1 / Sprint E). Tras
una búsqueda anónima, si V se conecta a ver, su IP se expone al broadcaster. La UI no debe
sugerir "búsqueda privada = visionado privado". Coherente con §12.1 del plan y G1 (no se
cumple hasta v8.1.1).
