# eMule eSE 9.1.0-beta.2 — Plan de estabilización, desarrollo y validación

Estado: plan normativo de trabajo  
Versión del documento: 1.0  
Fecha de referencia: 25 de julio de 2026  
Ámbito: estabilización de eSE 9.1 sobre `v9.1.0-beta.1`  
Especificación superior: `docs/V9_RELEASE_SPECIFICATION.md`  
Evidencia de entrada: `docs/V9.1_GATE_GAP_EVIDENCE_2026-07-24.md`

---

## 1. Propósito

Este documento convierte las carencias observadas después de
`v9.1.0-beta.1` en un programa ejecutable para publicar
`v9.1.0-beta.2`.

Beta.2 no añade una nueva familia funcional. Su objetivo es reforzar y hacer
honesto lo que ya existe:

- eliminar riesgos conocidos de concurrencia;
- alinear capacidades anunciadas con handlers realmente operativos;
- hacer efectivo el aislamiento local del dashboard;
- impedir que las rutas HTTP bloqueen el proceso Node;
- probar código de producción en lugar de réplicas o expresiones de texto;
- convertir CI, build y self-test en gates reales;
- unificar versión, dependencias, documentación y artefactos;
- producir evidencia reproducible para una beta posterior.

Este plan es subordinado a `V9_RELEASE_SPECIFICATION.md`. No reduce la matriz
`V91-*` ni convierte una beta en RC o Stable.

## 2. Resultado que debe entregar beta.2

El candidato beta.2 debe cumplir simultáneamente:

1. No existe un orden de locks contradictorio en `CLiveTunnel`.
2. Ningún bit de capacidad se anuncia si su recepción y comportamiento
   correspondiente no están disponibles.
3. El dashboard escucha únicamente en loopback por defecto.
4. La exposición remota es explícita, autenticada y observable.
5. Ninguna ruta HTTP ejecuta procesos externos o recorridos de archivos de
   forma síncrona y no acotada.
6. Los vectores wire críticos se ejecutan contra C++ de producción.
7. Build, pruebas y self-test fallan de forma vinculante en CI.
8. La configuración Release no oculta símbolos duplicados conocidos.
9. La versión y el canal beta coinciden en binario, dashboard, paquete,
   instalador y documentación.
10. El paquete resultante supera regresión IPv4, IPv6/Kad6, dashboard,
    compatibilidad y soak de beta.

Beta.2 debe poder describirse públicamente como una release de
**concurrencia, seguridad de exposición, honestidad de protocolo y fiabilidad
de entrega**.

## 3. Autoridad y relación con 9.1

Los requisitos `V91-F01`–`V91-F18`, las pruebas `V91-*` y los gates comunes
siguen siendo normativos.

Los identificadores `V91B2-*` añadidos aquí:

- especifican trabajo adicional de estabilización;
- no reemplazan ninguna prueba `V91-*`;
- pueden cerrar defectos que impiden ejecutar la matriz 9.1;
- no permiten declarar RC mientras queden casos obligatorios de 9.1 sin
  evidencia.

En caso de contradicción:

1. prevalece `V9_RELEASE_SPECIFICATION.md`;
2. después prevalece este plan para el alcance beta.2;
3. una decisión de implementación debe registrarse antes de cambiar un
   contrato de wire, seguridad o persistencia.

## 4. Fuera de alcance

No forman parte de beta.2:

- funciones previstas para 9.2, 9.3 o 9.4;
- UPnP/PCP/NAT-PMP como promoción 9.2;
- Punch3, predicción de puertos o KRP;
- salida pública Kad6 estable;
- implementar un protocolo Gossip nuevo para justificar un bit existente;
- rediseñar por completo `LiveTunnel.cpp`, `WebServer.cpp` o
  `LiveStreamManager.cpp`;
- cambiar el formato de identidad o créditos IPv6-only;
- rediseñar la interfaz visual;
- migrar todas las bibliotecas de terceros;
- convertir warnings internos de dependencias vendorizadas en bloqueantes;
- afirmar compatibilidad universal con ISP, proxies o routers.

Se permiten extracciones internas pequeñas cuando sean necesarias para:

- establecer propiedad de locks;
- crear pruebas nativas;
- separar I/O bloqueante;
- retirar duplicación;
- conservar el comportamiento observable.

## 5. Estado de partida

### 5.1 Base disponible

- `v9.1.0-beta.1` tiene un build reproducible conocido.
- Las pruebas Node actuales pasan.
- Existen suites Core e Integration y librerías puras con pruebas focalizadas.
- El dashboard ya dispone de controles de token, origen, DNS rebinding, rate
  limiting y límites de cuerpo.
- El pipeline de release genera hashes y verifica determinados inputs
  descargados.
- Existe una especificación 9.x con requisitos y matriz de laboratorio.

### 5.2 Brechas verificadas

- `CLiveTunnel` contiene caminos `m_pendingLock → m_lock` y
  `m_lock → m_pendingLock`.
- Se anuncian capacidades Gossip aunque sus opcodes terminan en un handler
  stub o no-op.
- `server.listen(PORT)` no fuerza loopback.
- Rutas del dashboard usan `execSync`, `readdirSync`, `statSync` u operaciones
  equivalentes durante peticiones.
- Parte de las pruebas JavaScript verifica texto fuente y no comportamiento.
- Las pruebas Python de framing replican formatos, pero no ejecutan el C++ que
  deben validar.
- El workflow principal es manual y el smoke test admite fallos.
- CodeQL no cubre actualmente el código C++.
- Release usa `/FORCE:MULTIPLE`.
- Hay versiones diferentes en código, dashboard, guía e instalador.
- `npm audit` detecta una vulnerabilidad moderada corregible en `tar`.
- Permanecen copias históricas y scripts obsoletos junto al código activo.
- La matriz de promoción 9.1 mantiene casos físicos y de soak pendientes.

## 6. Modelo de estimación

Una jornada-persona (`JP`) equivale a siete horas de trabajo concentrado.

- Programa probable: **30 JP / 210 horas**.
- Rango optimista: **24 JP / 168 horas**.
- Rango adverso: **40 JP / 280 horas**.
- Reserva incluida: **3 JP / 21 horas**.
- Tiempo desatendido de CI, fuzz y soak no cuenta como horas activas.

Calendario orientativo:

| Dedicación | Calendario probable |
|---|---:|
| Una persona a tiempo completo | 7–9 semanas |
| 15 h/semana | 4–6 meses |
| 10 h/semana | 6–9 meses |
| 5 h/semana | 12–18 meses |

La estimación supone cambios focalizados. Si corregir los locks exige
rearquitecturar todo `LiveTunnel`, o eliminar `/FORCE:MULTIPLE` descubre una
incompatibilidad estructural, debe reestimarse antes de ampliar el diff.

## 8. Ruta crítica

```text
Base beta.1 + baseline
          ↓
Contrato de locks ───────────┐
          ↓                  │
Corrección LiveTunnel        │
          ↓                  │
Stress concurrente           │
                             ├──→ CI vinculante
Capacidad → handler ─────────┤         ↓
                             │   Build/package limpio
Loopback + I/O async ────────┘         ↓
                                  Matriz beta.2
                                       ↓
                              Físico + soak + publicación
```

Las tareas de versión, dependencias y limpieza pueden avanzar en paralelo,
pero no se integran en el candidato hasta que el baseline esté registrado.

## 9. Invariantes no negociables

1. Un hilo nunca adquiere dos locks de `LiveTunnel` en un orden diferente del
   contrato publicado.
2. Ningún I/O de socket, FEC, cifrado costoso o proceso externo ocurre bajo un
   lock global si puede prepararse mediante snapshot.
3. Un bit de capacidad implica un parser, validación, handler y resultado
   observable disponibles.
4. Una capacidad no disponible se omite; no se simula éxito y no se descarta
   silenciosamente como operación soportada.
5. El dashboard es local por defecto aunque no exista token.
6. La exposición remota requiere una decisión explícita y falla cerrada con
   configuración incompleta.
7. Las rutas HTTP no bloquean el event loop con procesos síncronos.
8. Una prueba wire normativa consume el mismo código o librería que el
   ejecutable.
9. Un PASS sin commit, comando, salida y artefacto es `NOT RUN`.
10. Un timeout de smoke test es fallo, no éxito tolerado.
11. El código de terceros no puede ocultar warnings nuevos del código propio.
12. El build no modifica silenciosamente archivos fuente o el índice Git.
13. La misma versión aparece en todos los artefactos públicos.
14. Todas las funciones 9.2+ permanecen en su estado anterior y fuera de la
    narrativa de beta.2.

## 13. Procedimientos obligatorios

Cada procedimiento produce:

- commit y estado del árbol;
- comando exacto;
- stdout/stderr;
- código de salida;
- duración;
- entorno y versiones;
- artefactos específicos;
- veredicto firmado `PASS`, `FAIL`, `BLOCKED` o `NOT RUN`.

### `V91B2-C01` — Ciclo de locks

Ejecutar el interleaving que anteriormente permitía:

```text
Thread A: m_pendingLock → espera m_lock
Thread B: m_lock        → espera m_pendingLock
```

PASS: el ciclo ya no puede construirse y el contrato impide reintroducirlo.

### `V91B2-C02` — Stress de fair queue y Tick

Ejecutar productores, expiraciones, cancelaciones y `Tick` concurrentes.

PASS: cero deadlock, doble completion, corrupción o timeout interno durante
10.000 ciclos y al menos 30 minutos.

### `V91B2-C03` — Presupuesto de lock

Instrumentar duración y operaciones ejecutadas bajo el lock global.

PASS: no existe socket I/O, proceso externo o FEC desacoplable bajo el lock;
percentil 99 y máximo quedan registrados y no empeoran respecto al baseline.

### `V91B2-P01` — Consistencia de capacidades

1. activar su configuración válida;
2. comprobar anuncio;
3. emitir un mensaje válido;
4. comprobar parser y handler;
5. desactivar o invalidar la configuración;
6. comprobar retirada del bit.

PASS: todos los bits cumplen el recorrido completo.

Gossip no negociado.

Arrancar sin variables de exposición y consultar la dirección efectiva.

## 15. Gates de promoción

### Dev

- tarea ligada a requisito y test;
- test rojo o reproducción antes de corregir;
- build focalizado verde;
- diff sin cambio de alcance;
- cero secreto o artefacto personal.

### Alpha

- WP91B2-0…6 completos;
- locks, capacidades, dashboard y wire pasan;
- CI automática activa;
- Release enlaza sin `/FORCE:MULTIPLE`;
- ningún `S0` o `S1` abierto.

### Beta.2

- todos los `V91B2-*` pasan sobre el commit candidato;
- `V91-A01`, IPv4-only, dual-stack y compatibilidad pasan;
- al menos una topología física remota;
- soak de 12 horas;
- paquete extraído y self-test vinculante;
- audit, versión, documentación y hashes coherentes;
- ningún `S0`, `S1` o `S2` abierto;
- las notas distinguen claramente lo probado de lo pendiente para RC.

### RC de 9.1

Beta.2 no alcanza automáticamente este gate. Para RC siguen siendo
obligatorios:

- toda la matriz `V91-*`;
- todos los gates comunes;
- T5 físico y casos IPv6/Kad6 pendientes;
- upgrade, compatibilidad, rollback y soak normativos;
- feature y wire freeze;
- cero deuda beta aceptada sin repetir.

### Stable

- dos ejecuciones completas del mismo commit RC en días distintos;
- una ejecución reproducida por un rol independiente;
- mismos hashes y paquete;
- cero cambio posterior no revalidado;
- evidencia pública sanitizada y notas honestas.

## 16. Política de defectos

| Severidad | Ejemplos | Promoción |
|---|---|---|
| `S0` | RCE, secreto expuesto, corrupción destructiva | detiene todo |
| `S1` | deadlock, capacidad falsa explotable, exposición remota involuntaria | bloquea Alpha+ |
| `S2` | event loop bloqueado, self-test falso, incompatibilidad, build no hermético | bloquea Beta.2+ |
| `S3` | warning heredado, diagnóstico o metadata incorrecta sin riesgo inmediato | bloquea RC según impacto |
| `S4` | cosmética o documentación menor | puede aplazarse con registro |

Todo `S0/S1` exige:

1. reproducción;
2. análisis de causa;
3. prueba de regresión;
4. revisión independiente;
5. repetición del carril afectado;
6. registro en notas si estuvo presente en una beta pública.

## 18. Riesgos y disparadores de reestimación

| Riesgo | Señal | Respuesta |
|---|---|---|
| Locks más entrelazados de lo inventariado | aparece un tercer ciclo | congelar diff y rediseñar ownership |
| `Tick` depende de efectos bajo lock | tests cambian orden observable | extraer snapshot por fases |
| Capacidades se usan como feature flags internos | retirar bit rompe código local | separar capacidad wire/configuración |
| Async cambia orden de respuestas | carreras o cancelación tardía | estado por request y generation ID |
| `/FORCE:MULTIPLE` oculta incompatibilidad amplia | muchos duplicados no triviales | ADR y reestimación |
| CI nativa supera presupuesto | PR >45 min | shard; no omitir pruebas críticas |
| Dependencia no puede actualizarse aisladamente | cambia empaquetado | fijar versión segura compatible o registrar bloqueo |
| Laboratorio físico no disponible | caso remoto no ejecutable | beta.2 queda `BLOCKED`, no simular PASS |
| Trabajo 9.2 se mezcla con beta.2 | diff fuera de paths acordados | separar por cherry-pick/worktree |

Reestimar si:

- tres tareas consecutivas superan 150 % de su probable;
- se consumen 2 JP de reserva antes de completar WP91B2-4;
- cambia el wire;
- se requiere migración de persistencia;
- el programa probable supera 36 JP.

## 19. Mejoras posteriores, no bloqueantes para beta.2

Después de beta.2 pueden planificarse sin mezclarlas en el candidato:

- división completa de `LiveTunnel` en circuitos, pending, Kad6, proxy,
  métricas y release gates;
- división de `WebServer` y `channel_api.js` por dominio;
- ampliar sanitizers a más código portable;
- actualización sistemática de todas las dependencias vendorizadas;
- cobertura y mutation testing de áreas no críticas;
- eliminación gradual de deuda histórica restante.

Estas mejoras pueden bloquear RC si revelan un defecto `S0`–`S2`, pero no se
incluyen preventivamente en beta.2 sin evidencia.
