# eMule eSE 9.2 — Stack de aseguramiento y gauntlet de calidad

Estado: obligatorio para aceptar código 9.2  
Especificación funcional: `V9_RELEASE_SPECIFICATION.md`  
Plan funcional: `V9.2_DEVELOPMENT_AND_TEST_PLAN.md`  
Política de modelos: `V9.2_MODEL_ORCHESTRATION.md`  
Runbook: `V9.2_EXECUTION_RUNBOOK.md`  
Estado maestro: `V9.2_EXECUTION_STATE.md`

---

## 1. Objetivo

Este stack permite aceptar código sin confiar en que su autor —humano o
agente— haya entendido o revisado correctamente cada línea.

La confianza procede de obligar a cada cambio a atravesar capas independientes:

```text
Requisito ejecutable
  → test rojo revisado
  → implementación acotada
  → compilador estricto
  → unit/property/model tests
  → cobertura
  → mutation testing
  → fuzz + ASan
  → análisis estático
  → Gherkin
  → integración T8
  → revisión adversarial
  → QA desde checkout limpio
  → laboratorio físico
  → soak
  → release reproducible
```

Ninguna capa sustituye a otra:

- cobertura alta no demuestra asserts correctos;
- mutation score alto no demuestra integración real;
- T8 no demuestra Internet real;
- router real no cubre fallos reproducibles;
- revisión humana no sustituye a tests;
- muchos tests no compensan requisitos ambiguos.

## 3. Principio de independencia

El mismo actor no debe:

1. definir el requisito;
2. escribir la prueba;
3. implementar;
4. revisar;
5. aprobar la evidencia final;

sin que exista al menos una pasada independiente entre funciones.

Con una sola persona se consigue independencia temporal:

- sesión/prompt 1: especificación y tests;
- sesión/prompt 2: implementación con tests congelados;
- sesión/prompt 3: revisión adversarial sin editar;
- sesión/prompt 4: reproducción QA desde estado limpio.

Los contextos y entregables se conservan por separado.

La independencia se demuestra con identificadores de contexto, no solo con el
nombre del modelo:

- un implementador Sol no puede reutilizar su conversación para firmar review;
- el revisor recibe primero contrato, diff y evidencia, no la defensa del autor;
- Luna y Terra no pueden sustituir un checkpoint Sol;
- un fallback de modelo se registra en el manifest;
- ningún PASS se basa en que el modelo sea supuestamente más capaz.

## 4. Roles

### `ROLE-SPEC` — Guardián de contrato

Modelo por defecto: **Sol/high**.

Puede modificar:

- especificación;
- `.feature`;
- tablas de invariantes;
- criterios PASS.

No puede:

- implementar producción;
- bajar umbrales;
- aprobar su propia ambigüedad.

Entrega:

- requisito;
- ejemplos positivos;
- ejemplos negativos;
- edge cases;
- definición de evidencia.

### `ROLE-TEST` — Autor de pruebas

Modelo por defecto: **Luna/medium** para casos mecánicos y **Terra/high** para
property, model-based o stateful. Escala a Sol si define un oráculo crítico.

Puede modificar:

- tests;
- fixtures;
- corpus;
- adapters de test.

No puede:

- cambiar código productivo;
- actualizar golden sin revisión;
- excluir mutantes.

Entrega:

- prueba roja;
- explicación de por qué falla;
- comandos;
- cobertura esperada.

### `ROLE-IMPL` — Implementador

Modelo por defecto: el asignado a la tarea por
`V9.2_MODEL_ORCHESTRATION.md`.

Puede modificar:

- archivos productivos permitidos por la tarjeta.

No puede:

- cambiar `.feature`;
- debilitar asserts;
- marcar tests skip;
- editar umbrales;
- modificar más archivos de los autorizados sin STOP.

Entrega:

- diff;
- tests verdes;
- riesgos.

### `ROLE-REVIEW` — Revisor adversarial

Modelo por defecto: **Terra/high**; **Sol/high en contexto nuevo** para tareas y
checkpoints críticos.

No modifica código.

Busca:

- stale generation;
- cleanup cruzado;
- falso HighID;
- race/UAF;
- timeout infinito;
- dirección privada;
- WebServer mapping;
- test que no prueba lo que afirma;
- mutante equivalente mal clasificado.

Entrega:

- hallazgos `S0`–`S4`;
- archivos/líneas;
- caso de reproducción.

### `ROLE-QA` — Reproductor

Modelo por defecto: **Luna/medium** para reproducción cerrada y **Terra/high**
para triage no trivial.

Trabaja desde checkout/worktree limpio.

No acepta:

- “funciona en mi carpeta”;
- artefactos no reproducibles;
- dependencia de archivos generados no inventariados;
- PASS manual sin evidencia.

Entrega:

- quality manifest;
- resultados;
- hashes;
- PASS/FAIL/BLOCKED.

### `ROLE-RELEASE` — Promoción

Modelo por defecto: **Sol/high en contexto independiente**.

Solo actúa cuando todos los gates anteriores están verdes.

No cambia código. Si encuentra un fallo:

- detiene release;
- abre defecto;
- exige nuevo candidato.

## 5. Capas del stack

## L0 — Scope y procedencia

Objetivo: demostrar qué se está probando.

Gates:

- commit conocido;
- worktree limpio;
- submódulos conocidos;
- versión y release notes coherentes;
- archivos cambiados dentro de tarjeta;
- cero binarios staged;
- diff dentro del presupuesto.

Bloquea:

- cualquier gate posterior si la procedencia es ambigua.

## L1 — Compilador estricto

Para `libnatmap`, T8 y todos los módulos puros extraídos por `MOD-*`:

- C++17;
- `/W4`;
- `/WX`;
- Release x64;
- Debug/ASan cuando corresponda;
- sin warnings nuevos.

Reglas:

- warning tratado como error;
- no añadir casts para silenciar sin explicar;
- no suprimir warning globalmente;
- una supresión local necesita comentario y test.

Métrica:

- warnings en changed scope: **0**.

## L2 — Análisis estático

Capas:

1. CodeQL existente para lenguajes soportados.
2. Análisis nativo de MSVC sobre archivos 9.2.
3. Linters propios:
   - puertos locales/anunciados;
   - WebServer mapping;
   - llamadas delete;
   - uso de clock no monotónico;
   - uso de `rand()` en nonce;
   - catch-all nuevos;
   - raw thread termination;
   - estados HighID;
   - ciclos/SCC de includes;
   - límites LOC y dependencias;
   - dominio que incluye su coordinador;
   - funciones >150 líneas y coordinadores >20 campos mutables.

Gates:

- cero alertas Critical/High nuevas;
- Medium revisadas y justificadas;
- baseline no puede crecer silenciosamente.

## L3 — Unit tests

Ámbito:

- codecs;
- clasificación IP;
- leases;
- epochs;
- generations;
- ownership;
- state transitions;
- backoff;
- pair TCP/UDP.

Reglas:

- deterministas;
- sin red;
- sin reloj real;
- sin sleep;
- test name describe contrato;
- un assert principal por comportamiento.

Gates:

- pass rate: **100 %**;
- flaky rate: **0 %**;
- veinte repeticiones verdes para tests nuevos sensibles a estado/tiempo.

## L4 — Property y model-based tests

Propiedades obligatorias:

1. Generation nunca decrece.
2. Respuesta antigua no cambia snapshot.
3. `verified` implica server evidence + inbound de la misma generación.
4. Endpoint no enrutable nunca se anuncia.
5. Par TCP/UDP no mezcla generaciones.
6. Cleanup nunca cruza owner.
7. Disable vuelve a baseline.
8. Epoch reset invalida evidencia.
9. Retry permanece acotado.
10. Shutdown conduce a cero operaciones aplicables.

Modelo:

- una máquina de referencia pura genera el estado esperado;
- secuencias aleatorias deterministas se aplican al modelo y al sistema;
- snapshots deben coincidir.

Gates:

- mínimo 100.000 transiciones deterministas por ejecución nightly;
- semilla registrada;
- cualquier divergencia es FAIL.

## L5 — Cobertura

La cobertura se usa como detector de huecos, no como prueba de corrección.

Umbrales:

| Ámbito | Lines | Branches |
|---|---:|---:|
| Código nuevo puro 9.2 | ≥95 % | ≥90 % |
| Líneas modificadas | 100 % | ≥95 % |
| Ownership/delete | 100 % | 100 % |
| HighID transitions | 100 % | 100 % |
| Parser/codec error paths | ≥95 % | ≥95 % |
| Lógica pura extraída `MOD-*` | ≥90 % | ≥85 % |
| UI glue | ≥80 % | ≥70 % |

Reglas:

- no excluir una línea por dificultad;
- exclusiones solo para código imposible con justificación;
- cobertura de test code no cuenta;
- changed-line coverage bloquea commit/PR;
- informe guarda commit y toolchain.

## L6 — Mutation testing

Objetivo: comprobar que los tests detectan código incorrecto.

Operadores mínimos:

- `==` ↔ `!=`;
- `<` ↔ `<=`;
- `>` ↔ `>=`;
- `&&` ↔ `||`;
- eliminar `!`;
- return true/false;
- cambiar `+1` por `+0`;
- omitir generation increment;
- aceptar stale response;
- omitir ownership comparison;
- omitir inbound requirement;
- omitir server evidence requirement;
- omitir TCP/UDP rollback;
- clasificar CGNAT como pública;
- promocionar MAP sin inbound proof;
- promocionar IPv6 global sin firewall/pinhole proof;
- cambiar `SAME_LAN` por `GLOBAL`;
- tratar PCP local como PCP upstream;
- eliminar expiry;
- convertir backoff en retry inmediato.

Umbrales:

| Área | Mutation score |
|---|---:|
| General changed pure code | ≥85 % |
| State machine | ≥90 % |
| Ownership/delete | 100 % de mutantes críticos |
| HighID | 100 % de mutantes críticos |
| Address classification | ≥95 % |

Mutante sobreviviente:

1. Añadir test que lo mate.
2. O demostrar que es equivalente.
3. La equivalencia requiere `ROLE-REVIEW`.
4. Registrar exclusión exacta.

Prohibido:

- excluir un archivo completo;
- contar timeout/crash del runner como “killed” sin clasificar;
- bajar score para poner verde.

## L7 — Fuzzing y sanitizers

Targets:

- NAT-PMP decoder;
- PCP decoder/options;
- UPnP XML/SOAP boundary;
- scenario JSON;
- ownership ledger;
- API JSON serialization inputs;
- state event sequences.

Lanes:

| Lane | Iteraciones | Sanitizer |
|---|---:|---|
| Commit rápido | 10.000/target | Release |
| Nightly | 100.000/target | Release + ASan |
| RC | 1.000.000/target o presupuesto equivalente | ASan |

Invariantes:

- no crash;
- no OOB/UAF;
- no allocation sin límite;
- consumed nunca excede input;
- malformed no produce success indebido;
- snapshot no cambia tras input rechazado.

Corpus:

- semillas válidas;
- truncación en cada byte;
- bit flips;
- field boundary values;
- replay;
- duplicados;
- tamaños máximos;
- regresiones de defectos.

## L8 — Requisitos ejecutables Gherkin

Ubicación propuesta:

```text
tests/features/v9.2/
  mapping_upnp.feature
  mapping_pcp.feature
  mapping_natpmp.feature
  ownership.feature
  highid_evidence.feature
  topology_change.feature
  cgnat_double_nat.feature
  direct_candidate_snapshot.feature
  pcp_upstream.feature
  ipv6_pinhole.feature
  lan_candidate_scope.feature
  mappings_disabled.feature
```

Ejemplo:

```gherkin
Feature: PCP external port selection

  Scenario: The gateway grants a different external TCP port
    Given mappings are enabled
    And T8 PCP grants TCP port 52001 for local port 4662
    And T8 PCP grants UDP port 52002 for local port 4672
    When eSE completes the mapping transaction
    Then the advertised TCP port is 52001
    And the advertised UDP port is 52002
    And the topology generation increases exactly once
    And direct reachability is not verified yet
```

Reglas:

- Given configura, no valida;
- When provoca una única acción;
- Then usa API estructurada y gateway state;
- no parsear texto de log;
- cada `V92-*` tiene al menos un Scenario;
- cada regla de seguridad tiene escenario negativo.

Gate:

- todos los escenarios verdes contra T8;
- tags permiten seleccionar `@fast`, `@t8`, `@physical`, `@release`.

## 8. Política de merge/aceptación

Un cambio solo se acepta cuando:

- tarjeta WBS `ACTIVE`;
- requisito asociado;
- Gherkin asociado cuando sea observable;
- test rojo revisado;
- implementación dentro de scope;
- CARD verde;
- CORE verde;
- INTEGRATION verde si aplica;
- cobertura verde;
- mutación verde;
- static verde;
- review sin `S0-S2`;
- QA reproducida;
- quality manifest archivado;
- commit autocontenido.

No se aceptan excepciones verbales. Una excepción:

1. se documenta;
2. tiene propietario;
3. tiene fecha/versión de resolución;
4. no puede afectar seguridad, ownership, HighID o compatibilidad;
5. nunca aplica a RC/Stable para casos obligatorios.

## 9. Flaky-test policy

Un test es flaky si el mismo commit/configuración produce resultados distintos.

Ante un flaky:

1. marcar lane FAIL;
2. conservar semillas y orden;
3. ejecutar 20 repeticiones;
4. aislar estado compartido, tiempo o carrera;
5. corregir;
6. ejecutar otras 20;
7. no reintentar automáticamente hasta verde.

Prohibido:

- “retry 3” para ocultarlo;
- aumentar sleep;
- excluirlo de CI;
- marcarlo allowed failure.

---

## 10. Mutation workflow

Por tarjeta de lógica:

1. Ejecutar tests verdes.
2. Generar mutantes solo en líneas cambiadas.
3. Compilar cada mutante.
4. Ejecutar focalizados.
5. Clasificar:
   - killed;
   - survived;
   - compile-error;
   - timeout;
   - equivalent-reviewed.
6. Añadir test para survivors reales.
7. Repetir.
8. Guardar informe.

Mutantes críticos predefinidos manualmente:

- aceptar stale generation;
- borrar sin owner match;
- omitir inbound;
- omitir server evidence;
- tratar CGNAT como pública;
- publicar tras TCP sin UDP;
- no retirar tras expiry.
- publicar candidato mapped sin proof vigente;
- publicar `HOST_V6` con firewall cerrado;
- publicar candidato privado con scope global;
- aceptar proof de otra generación;
- confundir PCP CPE con PCP upstream.

Estos doce deben morir siempre, aunque el mutation runner general cambie.

## 15. Gate de confianza de primera puesta en marcha

Este gate no promete infalibilidad. Demuestra que el candidato no depende del
orden, la carpeta, la caché, una máquina concreta ni una única ejecución
afortunada.

### `FP-01` Checkout limpio

1. Crear worktree nuevo desde el commit candidato.
2. No copiar ningún build anterior.
3. Ejecutar bootstrap documentado.
4. Ejecutar CARD/CORE/INTEGRATION.

PASS:

- cero archivo manual no documentado;
- cero dependencia del worktree de desarrollo.

### `FP-02` Dos builds independientes

1. Build A en directorio limpio.
2. Build B en otro directorio limpio.
3. Comparar versiones, manifests, inputs y artefactos esperados.

PASS:

- misma procedencia;
- misma lista de archivos;
- hashes reproducibles donde el pipeline los exige;
- ningún binario mezclado.

### `FP-03` T8 repetido y reordenado

Ejecutar la matriz T8:

- diez veces en orden canónico;
- diez veces con orden aleatorio y semilla registrada;
- una vez después de restart del host;
- una vez después de restart de T8.

PASS:

- cero resultado inconsistente;
- cero estado heredado entre casos;
- cero flaky;
- misma clasificación PASS/FAIL.

### `FP-04` Instalación/perfil nuevos

Ejecutar sobre:

- carpeta nunca usada;
- perfil nuevo;
- copia de 9.1;
- copia de beta anterior;
- rollback.

PASS:

- primer arranque no necesita edición manual;
- defaults seguros;
- mappings OFF y ON se comportan como se documenta.

### `FP-05` Dos máquinas o entornos

Reproducir al menos:

- H1;
- H2/H3 o una segunda instalación Windows controlada.

PASS:

- ninguna ruta absoluta;
- ninguna dependencia accidental de adaptador, hostname o usuario.

### `FP-06` Router y red móvil

Ejecutar:

- T7 completo dos veces;
- T3 LAN/hotspot/LAN;
- días diferentes;
- reinicio entre rondas.

PASS:

- mismo commit;
- cero `S0-S2`;
- cualquier limitación se detecta y expresa honestamente.

### `FP-07` Dry-run de release

Antes del RC:

1. Ejecutar pipeline completo con tag candidato no publicado.
2. Extraer paquete.
3. Seguir documentación como si fuera un usuario nuevo.
4. No usar rutas del árbol de fuentes.
5. Ejecutar self-test y smoke.

PASS:

- documentación suficiente;
- cero paso implícito;
- rollback practicado.

### `FP-08` Beta limitada

La Beta es parte del aseguramiento, no una declaración Stable.

Condiciones:

- features 9.2 etiquetadas;
- diagnóstico exportable;
- rollback;
- scope de afirmaciones limitado;
- defectos recibidos trazables al commit.

Stable solo se considera “lista para funcionar a la primera” después de que el
candidato supere FP-01…FP-08. Aun así, un router o ISP no observado puede
comportarse de forma distinta; en ese caso debe fallar de forma segura, visible
y reversible, nunca producir falso HighID o borrar reglas ajenas.

## 16. Assurance del handoff técnico 9.2 → 9.3

`G92-93-DEV` es un gate de dependencia, no de release. Usa las capas existentes
sin añadir una lane ni presupuesto:

| Grupos | Capas obligatorias |
|---|---|
| `H93-01`–`H93-05` | L0, L1, L3, L8 y QA desde checkout limpio |
| `H93-06`–`H93-12` | L3, L4, L7, L9 y revisión adversarial |
| `H93-13`–`H93-14` | L2, L5, L6, L10 y seguridad/privacidad |
| `H93-15`–`H93-16` | L11 y prueba independiente de ruta |

Reglas:

1. Las dos pasadas automáticas pertenecen al mismo commit; la segunda parte de
   un checkout limpio.
2. El revisor del schema y de `candidate→verified` no puede ser el implementador.
3. Un flaky, `SKIP` o `BLOCKED` nunca se convierte en PASS.
4. El manifest enlaza cada grupo con comando, salida, hash y veredicto.
5. Cualquier cambio de schema, ownership, endpoint, verificación o generación
   invalida el gate y detiene a los consumidores 9.3 hasta repetirlo.
6. El PASS permite desarrollo 9.3; RC/Stable 9.3 continúan bloqueados hasta
   `9.2 Stable` y sus gates completos.
