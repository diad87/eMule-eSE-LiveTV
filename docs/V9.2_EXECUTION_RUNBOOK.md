## 1. Qué es este documento

Este manual explica cómo ejecutar el plan 9.2 en pasos pequeños y verificables.
Está diseñado para reducir al mínimo la memoria, improvisación y atención
continua exigidas al ejecutor.

No convierte el proyecto en algo trivial. eSE 9.2 modifica:

- sockets;
- protocolos de router;
- concurrencia;
- estado persistente;
- publicidad de endpoints;
- decisiones HighID;
- cleanup de recursos externos.

Un error puede provocar un crash, un falso HighID o borrar un mapping ajeno.
Por eso este runbook reduce el margen de error mediante cuatro controles:

1. cambios muy pequeños;
2. test antes y después;
3. commits recuperables;
4. revisiones obligatorias en puntos peligrosos.

Una persona cuidadosa pero poco experta, patosa o propensa a despistarse puede
ejecutar el plan si respeta todas las paradas. No debe improvisar cuando una
tarjeta indique **STOP**. El objetivo no es formar al ejecutor, sino hacer que
el proceso detecte los errores antes de que puedan propagarse.

## 2. Cómo utilizarlo

Trabajar siempre con estos documentos abiertos:

1. `V9_RELEASE_SPECIFICATION.md`: qué debe cumplir la versión.
2. `V9.2_DEVELOPMENT_AND_TEST_PLAN.md`: qué paquetes de trabajo existen.
3. `V9.2_ASSURANCE_STACK.md`: qué pruebas y revisiones son obligatorias.
4. `V9.2_MODEL_ORCHESTRATION.md`: qué modelo ejecuta y revisa cada tarea.
5. Este runbook: qué hacer en cada sesión.
6. `V9.2_MODULARIZATION_AND_ARCHITECTURE_PLAN.md`: qué slices
   arquitectónicos son obligatorios.
7. `EMULEAI_INTEGRATED_RELEASE_ROADMAP.md`: qué comparativas se hospedan sin
   ampliar alcance.
8. `V9.2_EXECUTION_STATE.md`: qué tarea está activa y qué ocurrió realmente.
9. `TESIS_CONSOLIDADA_LOWID_A_LOWID_DIRECTO_V9.1_2026.docx`: qué evidencia
   local debe entregar 9.2 a la arquitectura Direct-Only posterior.

Cada tarjeta tiene:

- **Objetivo**: una sola cosa.
- **Leer**: archivos que hay que comprender antes.
- **Modificar**: límite de archivos esperado.
- **Pasos**: acciones secuenciales.
- **Prueba roja**: comportamiento que debe fallar antes.
- **Prueba verde**: resultado que debe pasar después.
- **Evidencia**: qué conservar.
- **Commit**: mensaje recomendado.
- **STOP**: condiciones en las que no se continúa.

No se empieza una tarjeta si la anterior de su cadena está roja.

### 2.2 Límite de trabajo en curso

Solo puede existir:

- una tarea funcional, QA o `MOD-*` `ACTIVE`;
- un diff funcional sin commit;
- un defecto principal bajo investigación;
- un entorno físico alterado.

No se permite empezar “algo rápido” mientras otra tarea está activa. Un
checkpoint eMule AI se captura dentro de su tarjeta anfitriona y nunca cuenta
como permiso para abrir un segundo diff. Las ideas nuevas se registran y
esperan.

### 2.3 Inicio de sesión mecánico

Ejecutar siempre, incluso si la sesión anterior terminó bien:

```powershell
$V92Repo = 'C:\tmp\eSE-v9.2-dev'
Set-Location -LiteralPath $V92Repo
git status -sb
git log -1 --oneline
Get-Content .\docs\V9.2_EXECUTION_STATE.md -TotalCount 35
```

Comprobar:

- la ruta es el worktree 9.2;
- la rama es la prevista;
- la tarea `ACTIVE` coincide con la sesión;
- el diff está vacío o pertenece exactamente a esa tarea;
- el último commit coincide con el registrado.

Si algo no coincide, no editar. Aplicar la tabla de recuperación de sesión.

### 2.4 Activación de una tarea

Antes de cambiar `READY` a `ACTIVE`:

1. Todas las dependencias aparecen `PASS`.
2. No existe otra tarea `ACTIVE`.
3. Se conocen los archivos permitidos.
4. Se conoce el test focalizado.
5. Existe espacio de evidencia.
6. La estimación restante cabe en la sesión o hay punto de corte seguro.
7. No hay un `S0/S1` abierto que afecte al componente.
8. Se ha resuelto el modelo de ejecución y está disponible o tiene fallback.
9. Se ha resuelto el modelo de revisión.
10. Si la tarea exige Sol, existe capacidad para ejecución/revisión Sol.

Registrar:

```text
Tarea:
Estado anterior: READY
Estado nuevo: ACTIVE
Commit inicial:
Hora:
Archivos permitidos:
Test focalizado:
Evidencia prevista:
Punto de corte seguro:
Modelo de ejecución solicitado:
Modelo de ejecución real:
Esfuerzo:
Fallback y motivo:
Modelo de revisión solicitado:
Modelo de revisión real:
Contexto independiente previsto:
```

### 2.5 Cierre de una tarea

Una tarea solo pasa a `PASS` si existen:

- diff revisado;
- test rojo documentado cuando aplique;
- test focalizado verde;
- Core verde;
- Integration verde cuando corresponda;
- quality lane exigida por `V9.2_ASSURANCE_STACK.md`;
- cobertura changed-line y branch dentro del umbral;
- mutation gate dentro del umbral;
- static analysis sin Critical/High;
- revisión adversarial;
- modelo solicitado/real y fallback registrados;
- revisión realizada desde un contexto distinto al implementador;
- checkpoint Sol satisfecho cuando lo exige la política;
- evidencia guardada;
- documentación/trazabilidad actualizada;
- commit;
- worktree sin cambios de la tarea;
- siguiente dependencia marcada `READY`, si procede.

Si falta uno:

- `ACTIVE` si se continuará sin cambiar de objetivo;
- `FAIL` si el criterio produce resultado incorrecto;
- `BLOCKED` si falta una condición externa.

### 2.6 Interrupción segura

Si hay que dejar la sesión a medias:

1. No hacer un commit verde falso.
2. Registrar exactamente qué está rojo.
3. Guardar `git diff --stat`.
4. Guardar el comando y primera línea de error.
5. Indicar el siguiente paso único.
6. No activar otra tarea.

Formato:

```text
INTERRUPTED
Task:
Base commit:
Changed files:
Last command:
First error:
Known-good tests:
Known-red tests:
Next exact action:
```

### 2.7 Recuperación de sesión

| Situación observada | Acción única |
|---|---|
| Estado dice `ACTIVE`, diff coincide | continuar desde `Next exact action` |
| Estado dice `ACTIVE`, diff vacío | comprobar si hubo commit y actualizar ledger |
| Estado dice `ACTIVE`, diff desconocido | STOP; inventariar antes de tocar |
| No hay `ACTIVE`, diff vacío | seleccionar primera fila `READY` |
| No hay `ACTIVE`, diff no vacío | STOP; no asignar tarea |
| Commit actual no coincide | STOP; identificar quién cambió la rama |
| Tests baseline rojos antes de editar | `BLOCKED`; no atribuirlos a la tarea |
| Hay dos tareas `ACTIVE` | STOP; corregir tablero antes de código |

### 2.8 Presupuesto de cambio

Por tarjeta:

- máximo recomendado: tres archivos productivos;
- máximo recomendado: un archivo de test nuevo;
- máximo recomendado: 250 líneas netas;
- máximo absoluto sin revisión: 500 líneas netas;
- cero cambios de default salvo tarjeta explícita;
- cero cambios de wire salvo especificación explícita.

Si se supera cualquier máximo:

1. detener;
2. dividir la tarjeta;
3. actualizar WBS/runbook;
4. volver a estimar;
5. continuar solo con una subtarea.

### 2.9 Orquestación mecánica de modelos

No cambiar manualmente el modelo de una conversación que ya está ejecutando
otra función. El coordinador crea un contexto nuevo para cada función:

```text
Sol coordinador
  -> Luna/Terra/Sol implementador
  -> tests y quality lane
  -> Terra/Sol revisor independiente
  -> Sol coordinador cierra o reabre
```

Secuencia obligatoria:

1. Leer el ID activo.
2. Buscar `Exec` y `Review` en `V9.2_MODEL_ORCHESTRATION.md`.
3. Comprobar disponibilidad del runtime.
4. Aplicar únicamente fallback ascendente.
5. Registrar solicitado, real, esfuerzo y motivo.
6. Encargar una sola microtarjeta.
7. Detener al trabajador ante un trigger `ESC-*`.
8. Ejecutar los gates antes de la revisión.
9. Crear un contexto revisor nuevo.
10. Registrar resultado y actualizar el estado.

Si Luna no está disponible:

```text
Requested: gpt-5.6-luna
Actual: gpt-5.6-terra
Fallback: LUNA_UNAVAILABLE
```

Esto no bloquea una tarjeta Luna. En cambio, si un checkpoint exige Sol y Sol
no está disponible:

```text
Status: BLOCKED
Reason: REQUIRED_SOL_UNAVAILABLE
```

No se permite que Terra o Luna firmen ese checkpoint.

## 3. Reglas absolutas de ejecución

### 3.1 Git

- No trabajar directamente sobre `main`.
- No usar `git reset --hard`.
- No usar `git clean -fd`.
- No borrar archivos para “arreglar” un build.
- No cambiar veinte archivos a la vez.
- Hacer un commit verde por tarjeta.
- Antes de cada tarjeta, ejecutar `git status -sb`.
- Si aparecen archivos no reconocidos, parar.

### 3.2 Código

- No desactivar asserts para obtener verde.
- No capturar `...` para ocultar el error.
- No aumentar timeouts sin demostrar que el algoritmo es correcto.
- No eliminar validaciones de nonce, epoch, source address o ownership.
- No marcar HighID directamente desde el resultado del mapper.
- No borrar un mapping si la propiedad es dudosa.
- No mapear el WebServer.
- No introducir Punch3, KRP o relay.
- No introducir DCO, ReachVector remoto, witnesses, birthday punching o DVL.
- No tratar `candidate` como sinónimo de `verified`.

### 3.3 Tests

- Escribir o seleccionar primero el test que representa el cambio.
- Comprobar que falla por el motivo esperado.
- Cambiar el mínimo código.
- Ejecutar el test focalizado.
- Ejecutar Core antes de commit.
- Ejecutar Integration cuando se toque código nativo, red o concurrencia.

### 3.4 Laboratorio

- Tailscale solo es canal de administración.
- No usar el router real hasta pasar el equivalente en T8.
- Guardar snapshot del router antes y después.
- No borrar manualmente reglas desconocidas.
- No reutilizar un perfil único entre versiones.
- No publicar direcciones, tokens o nombres privados.

## 4. Glosario mínimo

| Término | Explicación sencilla |
|---|---|
| Endpoint | Dirección IP y puerto |
| Puerto local | Puerto donde escucha eSE en el PC |
| Puerto externo | Puerto visible en el router/Internet |
| Mapping | Regla router: puerto externo → PC/puerto local |
| Lease | Tiempo durante el cual existe el mapping |
| Renovación | Petición para ampliar el lease |
| Epoch | Reloj/contador del gateway; si retrocede, probablemente reinició |
| Generación | Identificador local de una topología concreta |
| UPnP IGD | Protocolo HTTP/SOAP para gestionar mappings |
| PCP | Protocolo UDP con nonce y leases |
| NAT-PMP | Protocolo UDP simple anterior a PCP |
| Nonce | Valor aleatorio que identifica un mapping PCP |
| Ownership | Prueba de que la regla fue creada por esta instancia |
| Readback | Consultar al router lo que realmente almacenó |
| HighID | Estado eD2K de entrada pública; requiere evidencia real |
| Inbound | Conexión que entra desde fuera hacia eSE |
| CGNAT | NAT del operador; el usuario no controla la capa pública |
| RFC1918 | Direcciones privadas como `192.168.x.x` |
| Snapshot | Foto inmutable del estado en un instante |
| Main thread | Hilo principal que posee la UI y aplica el estado visible |
| Worker | Hilo secundario que realiza operaciones lentas |
| Callback tardío | Resultado que llega después de timeout/cierre/cambio de red |
| DoD | Definition of Done: condiciones para dar la tarea por terminada |
| T0/T3/T7/T8 | Topologías de prueba definidas por la especificación |

Si no se puede explicar cada término con palabras propias, no empezar la parte
de integración nativa.

8. ¿El fallo ocurre siempre?

Repetir tres veces un test sospechoso. Un test flaky es fallo, no PASS.

---

## 34. Si eMule se cuelga

No matar inmediatamente si se puede conservar evidencia.

Guardar:

- hora;
- proceso;
- threads;
- último log;
- operación mapper;
- si estaba cerrando;
- si hubo cambio de red.

Después:

- generar dump si las herramientas están preparadas;
- terminar proceso;
- no reutilizar el perfil sin copia;
- abrir defecto `S1` si el cuelgue es reproducible.

---

## 35. Si el router queda con una regla

No borrarla automáticamente.

1. Consultar journal.
2. Consultar mapping observado.
3. Comparar gateway, protocolo, puertos, cliente y descripción.
4. Si ownership es inequívoco, usar cleanup de la misma versión.
5. Si es ambiguo, documentar y permitir expiración o retirar manualmente desde
   la UI del router con conocimiento explícito.

Nunca ampliar el filtro de delete para “que funcione”.

---

## 36. Si aparece HighID inesperado

Tratar como `S1`.

Capturar:

- generation;
- mapper;
- endpoint;
- IDCHANGE;
- inbound observation;
- relay state;
- timestamps.

No corregir la UI solamente. Localizar qué transición promovió el estado.

## 41. Definición de éxito de la ejecución

La ejecución se considera exitosa si:

- cada tarjeta termina verde o se marca bloqueada;
- ningún STOP se ignora;
- cada cambio tiene test;
- cada commit es pequeño y recuperable;
- las revisiones obligatorias se realizan;
- no se consume reserva sin registrarlo;
- todos los requisitos y casos del plan normativo pasan;
- `MOD-0`–`MOD-6` y M0–M3 pasan;
- los límites de monolitos, ciclos, cobertura y ownership pasan;
- los ocho checkpoints `V92-ALIGNED` tienen evidencia y veredicto sin ampliar
  alcance;
- RC y Stable usan el mismo commit;
- no existen `S0`–`S2`;
- la persona puede explicar por qué la solución es segura, no solo afirmar que
  “los tests pasan”.

El objetivo final es que cada acción tenga comprobaciones suficientes para que
un despiste se convierta en un `STOP`, un test rojo o un diff visible, y no en
un defecto silencioso que llegue a la release.
