---

## 1. Objetivo

Esta política permite ejecutar el plan 9.2 sin que la persona tenga que escoger
manualmente un modelo para cada tarjeta. El modelo coordinador debe:

1. leer la tarea activa del estado maestro;
2. consultar la asignación prevista de esta política;
3. comprobar qué modelos están realmente disponibles;
4. crear un contexto de ejecución aislado con el modelo previsto;
5. escalar automáticamente cuando aparezca una condición de riesgo;
6. encargar una revisión independiente;
7. registrar el modelo solicitado y el realmente utilizado;
8. detenerse si no puede satisfacer un gate obligatorio.

Escribir el nombre de un modelo en una tarjeta no cambia por sí solo el modelo
de una conversación existente. La alternancia se implementa creando una tarea,
agente o ejecución nueva con el modelo indicado. El coordinador conserva la
responsabilidad sobre dependencias, alcance, evidencias y cierre.

Esta política no sustituye ningún test ni reduce los gates del stack de
aseguramiento. El modelo utilizado nunca constituye evidencia de corrección.

---

## 2. Principios obligatorios

1. **Sol coordina.** El coordinador de programa usa `gpt-5.6-sol`.
2. **Luna produce volumen acotado.** Se usa para trabajo mecánico, repetitivo,
   de bajo riesgo y con criterios de salida ejecutables.
3. **Terra integra.** Se usa para implementación media, integración y análisis
   que necesita más juicio que una microtarea mecánica.
4. **Sol decide lo difícil.** Se usa para arquitectura, contratos, seguridad,
   concurrencia, ownership, HighID, wire y promoción.
5. **Nadie se autoaprueba.** Implementación y revisión usan contextos
   independientes, aunque ambas necesiten el mismo modelo.
6. **No hay sustitución silenciosa.** Todo fallback queda registrado.
7. **Sol obligatorio no tiene fallback inferior.** Si Sol no está disponible en
   un checkpoint obligatorio, la tarjeta pasa a `BLOCKED`.
8. **El plan vence al router.** Una clasificación automática nunca puede bajar
   el modelo asignado explícitamente a una tarjeta.
9. **Los tests vencen al modelo.** Una respuesta convincente con gates rojos es
   `FAIL`, no una excepción.
10. **Una sola WBS activa.** Los agentes pueden ayudar dentro de la tarjeta,
    pero no abren una segunda tarea funcional.

## 3. Identificadores y perfiles

Los nombres completos son:

| Alias del plan | Modelo | Esfuerzo normal | Uso |
|---|---|---|---|
| `LUNA` | `gpt-5.6-luna` | `medium` | Volumen, búsqueda, boilerplate, tests y cambios locales |
| `TERRA` | `gpt-5.6-terra` | `high` | Integración y razonamiento de dificultad media |
| `SOL` | `gpt-5.6-sol` | `high` | Coordinación, arquitectura, riesgo alto y revisión crítica |

La clasificación parte de la
[guía oficial de modelos GPT-5.6](https://developers.openai.com/api/docs/guides/latest-model):
Sol es el nivel de máxima capacidad, Terra equilibra capacidad y coste, y Luna
está orientado a cargas eficientes de gran volumen. La disponibilidad concreta
se comprueba en el runtime y no se presume a partir de esta documentación.

El esfuerzo puede reducirse a `low` en inventarios o documentación puramente
mecánica. `xhigh` o `max` solo se permiten cuando:

- una tarjeta los asigna expresamente;
- existe un fallo medido con `high`;
- la mejora se verifica con los mismos criterios;
- el aumento queda registrado en el ledger.

No se usa `max` como valor global.

### 3.1 Roles de modelo

| Rol | Modelo por defecto | Puede editar | Puede aprobar |
|---|---|---|---|
| `ORCHESTRATOR` | Sol/high | Estado y documentación operativa | No aprueba su propia implementación |
| `SPEC` | Sol/high | Contratos, invariantes y criterios | Requiere revisión independiente |
| `TEST` | Luna/medium; Terra/high si es stateful | Tests, fixtures y corpus | No aprueba producción |
| `IMPL-LOW` | Luna/medium | Archivos exactos de la microtarjeta | No |
| `IMPL-MEDIUM` | Terra/high | Integración acotada | No |
| `IMPL-CRITICAL` | Sol/high | Código crítico autorizado | No |
| `REVIEW-NORMAL` | Terra/high | Nada | Puede cerrar hallazgos no críticos |
| `REVIEW-CRITICAL` | Sol/high en contexto nuevo | Nada | Puede aprobar el checkpoint |
| `QA` | Luna/medium o Terra/high | Evidencia, no producción | Solo reproduce |
| `RELEASE` | Sol/high | Nada de código | Sí, si todos los gates están verdes |

## 4. Disponibilidad y fallback

Antes de activar una tarjeta, el coordinador obtiene la lista de modelos que la
superficie actual permite usar. No debe deducir disponibilidad a partir de un
selector visto en otra sesión.

Cadena permitida:

```text
LUNA  -> TERRA -> SOL
TERRA -> SOL
SOL   -> BLOCKED
```

Reglas:

- el fallback solo puede subir de capacidad;
- nunca se baja de Sol a Terra o Luna;
- `LUNA -> TERRA` es el fallback operativo preferido;
- si una tarjeta Luna termina ejecutándose con Sol, se registra para medir
  sobreutilización del modelo caro;
- si el modelo solicitado no está disponible, se anota el motivo literal;
- si una revisión exige Sol y Sol no está disponible, no se acepta una revisión
  Terra como equivalente;
- cuando Luna vuelva a estar disponible, las tarjetas aún no iniciadas vuelven
  a su asignación original sin reescribir el plan.

Estado mínimo que debe quedar registrado:

```text
Requested execution model:
Actual execution model:
Execution effort:
Fallback reason:
Requested review model:
Actual review model:
Review effort:
Independent context:
```

## 5. Algoritmo de selección automática

El coordinador ejecuta estos pasos en orden.

### Paso 1 — Leer la única tarea activa

1. Abrir `docs/V9.2_EXECUTION_STATE.md`.
2. Confirmar que existe como máximo una fila `ACTIVE`.
3. Obtener ID, dependencias, archivos, test focalizado y checkpoint.
4. Si no existe tarea `ACTIVE`, seleccionar la primera `READY` solo después de
   aplicar las reglas normales de activación.

### Paso 2 — Resolver la asignación

1. Buscar el ID en las tablas de las secciones 8 y 9.
2. Aplicar cualquier override más específico de la microtarjeta del runbook.
3. No reducir el modelo asignado.
4. Si el ID no aparece, usar la clasificación de la sección 7 y registrar
   `ROUTING_GAP`.
5. Un `ROUTING_GAP` en código crítico obliga a Sol.

### Paso 3 — Comprobar disponibilidad

1. Consultar los modelos seleccionables por el runtime.
2. Elegir el solicitado si está disponible.
3. Si no, aplicar la cadena de fallback.
4. Registrar modelo solicitado, real y motivo.
5. Si falla un requisito Sol, marcar `BLOCKED`.

### Paso 4 — Crear un contexto limpio

El trabajador recibe únicamente:

- ID y objetivo;
- archivos permitidos;
- archivos de solo lectura necesarios;
- invariantes;
- test rojo;
- comandos de validación;
- presupuesto de diff;
- condiciones STOP;
- formato de entrega.

No recibe permiso implícito para abrir otras tareas, cambiar defaults, hacer
release, tocar el router real ni corregir fallos ajenos.

### Paso 5 — Ejecutar y observar

El coordinador no reimplementa en paralelo la misma tarea. Mientras el
trabajador actúa:

- conserva el WIP en uno;
- registra intentos;
- comprueba que no cambie archivos ajenos;
- aplica las reglas de escalado;
- interrumpe si se supera el presupuesto de cambio.

### Paso 6 — Validar

1. Ejecutar prueba focalizada.
2. Ejecutar la lane exigida.
3. Comparar archivos reales con archivos permitidos.
4. Comprobar cobertura, mutation y static cuando correspondan.
5. No pedir revisión hasta tener un diff estable o un fallo reproducible.

### Paso 7 — Revisar independientemente

1. Crear un contexto nuevo con el modelo de revisión.
2. Entregar contrato, diff y resultados; no entregar primero la defensa del
   implementador.
3. Pedir hallazgos por severidad y evidencia.
4. Si hay `S0`–`S2`, reabrir implementación.
5. La corrección vuelve a revisión; el autor no cierra su propio hallazgo.

### Paso 8 — Cerrar y auditar

Registrar:

- modelos solicitado y real;
- razonamiento;
- número de intentos;
- trigger de escalado, si existió;
- contexto de revisión distinto;
- hallazgos;
- tests y evidencias;
- decisión final.

Solo entonces la tarjeta puede pasar a `PASS`.

## 6. Escalado automático a Sol

El trabajador detiene la edición y devuelve control al coordinador cuando se
cumpla cualquiera de estas condiciones:

| Código | Trigger |
|---|---|
| `ESC-CONTRACT` | Es necesario interpretar o modificar un contrato/invariante |
| `ESC-WIRE` | Cambia wire, schema público, compatibilidad o persistencia |
| `ESC-OWNERSHIP` | Se crea, borra o reclama un recurso externo |
| `ESC-HIGHID` | Cambia la evidencia que promociona una ruta o HighID |
| `ESC-CONCURRENCY` | Toca lifetime, thread, callback, timer, cancelación o shutdown |
| `ESC-SECURITY` | Toca nonce, epoch, source validation, privacidad o secretos |
| `ESC-SCOPE` | Harían falta archivos o comportamiento fuera de la tarjeta |
| `ESC-REGRESSION` | Falla un test ajeno que antes estaba verde |
| `ESC-AMBIGUITY` | Especificación, test y código permiten interpretaciones incompatibles |
| `ESC-MUTATION` | Sobrevive un mutante crítico |
| `ESC-ATTEMPTS` | Tres intentos de implementación no consiguen verde focalizado |
| `ESC-DIFF` | Se supera el presupuesto máximo de archivos o líneas |
| `ESC-ENVIRONMENT` | El fallo depende de red/router/host y no puede aislarse |
| `ESC-RELEASE` | Se propone RC, Stable, tag, paquete o publicación |

El escalado no significa que Sol deba reescribir todo. Primero debe:

1. diagnosticar;
2. decidir si falta contrato, test, división o implementación;
3. producir la decisión mínima;
4. devolver la microtarea al nivel inferior cuando vuelva a ser mecánica.

## 7. Clasificador para microtarjetas nuevas

Si una tarjeta se divide, cada nueva microtarjeta se clasifica antes de
activarse.

### Luna

Usar Luna si todas son ciertas:

- resultado completamente especificado;
- máximo tres archivos productivos;
- no cambia contrato, wire, seguridad ni ownership;
- existe prueba focalizada determinista;
- el cambio se puede rechazar automáticamente;
- un fallo no puede promocionar una ruta falsa ni borrar recursos ajenos.

Ejemplos:

- generar vectores o corpus;
- añadir casos repetitivos a un runner existente;
- escribir documentación derivada de hechos ya aprobados;
- adaptar boilerplate;
- corregir errores locales de compilación sin cambiar diseño;
- ejecutar matrices y resumir resultados estructurados.

### Terra

Usar Terra si se cumple alguna:

- integración entre dos componentes;
- cambio local con varias ramas de estado;
- test model-based o property;
- diagnóstico de un fallo reproducible;
- refactor acotado con contrato congelado;
- implementación de protocolo siguiendo un diseño ya aprobado.

### Sol

Usar Sol si se cumple alguna:

- arquitectura o contrato;
- concurrencia, lifetime o callback tardío;
- ownership, cleanup o persistencia;
- seguridad, validación hostil o privacidad;
- HighID o promoción de endpoint;
- API/wire/schema público;
- conflicto entre requisitos;
- promoción de release;
- fallo no local después de tres intentos.

En caso de duda entre dos niveles, elegir el superior y registrar la duda.

La asignación Luna de una microtarjeta perteneciente a un WBS Terra o Sol solo
cubre su operación mecánica. El contrato del WBS, los triggers `ESC-*` y la

corpus o ejecutar una matriz, pero no decidir qué evidencia demuestra HighID.

Las tarjetas físicas mantienen a una persona como operador. El modelo guía,
comprueba precondiciones y analiza evidencia, pero no sustituye la autorización
para cambios reales de router, red o publicación.

## 13. Registro y métricas

Por tarjeta se conservan:

- modelo solicitado y real;
- esfuerzo solicitado y real;
- fallback;
- número de intentos;
- escalados y motivo;
- modelo/contexto revisor;
- resultado de revisión;
- tiempo activo aproximado;
- tokens/coste si la superficie los expone;
- gates ejecutados;
- PASS/FAIL/BLOCKED.

Métricas de programa:

| Métrica | Umbral/uso |
|---|---|
| `% microtarjetas ejecutadas por Luna` | Objetivo orientativo 55–70 % |
| `% microtarjetas ejecutadas por Terra` | Objetivo orientativo 20–30 % |
| `% microtarjetas ejecutadas por Sol` | Objetivo orientativo 10–20 % |
| `fallbacks por indisponibilidad` | Informativa; nunca ocultos |
| `escalados Luna/Terra -> Sol` | Revisar si superan 20 % |
| `rework después de review` | Señal para subir modelo o mejorar tarjeta |
| `intentos hasta verde` | Máximo tres antes de escalado |
| `aprobaciones sin contexto independiente` | Cero |
| `checkpoints Sol omitidos` | Cero |

Los porcentajes son una guía de volumen de microtarjetas, no una cuota. No se
rebaja el modelo de una tarea crítica para cumplirlos.

## 14. Condiciones de autonomía

Una ejecución puede continuar sin intervención humana entre tarjetas si:

- el usuario ha autorizado ejecutar el plan;
- la siguiente tarjeta está `READY`;
- el entorno y los modelos necesarios están disponibles;
- no hay acción destructiva, publicación o cambio externo que exija permiso;
- todos los gates de la tarjeta anterior están verdes;
- la política contiene una ruta inequívoca;
- no existe un `S0` o `S1`;
- el diff está limpio al cambiar de tarjeta.

Debe pedir intervención humana si:

- falta autoridad para una acción externa;
- hay dos interpretaciones de producto con resultados distintos;
- se consumiría reserva no autorizada;
- debe cambiarse el alcance o calendario;
- un requisito Sol obligatorio no puede ejecutarse;
- se plantea tocar router real, credenciales, publicación o release fuera de una
  autorización ya concedida;
- el mismo bloqueo se mantiene tras agotar las alternativas seguras.
