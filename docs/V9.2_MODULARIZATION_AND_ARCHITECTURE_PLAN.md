# eMule eSE 9.2 — Plan de modularización de los monolitos

Estado: plan complementario normativo integrado en el programa 9.2  
Versión del documento: 1.1  
Fecha de referencia: 25 de julio de 2026  
Ámbito: arquitectura interna posterior a 9.1.0-beta.2  
Plan funcional superior: `docs/V9.2_DEVELOPMENT_AND_TEST_PLAN.md`  
Ledger de ejecución: `docs/V9.2_EXECUTION_STATE.md`  
Política de modelos: `docs/V9.2_MODEL_ORCHESTRATION.md`

---

## 1. Propósito

Este programa reduce el riesgo concentrado en:

| Coordinador | Baseline aproximado |
|---|---:|
| `LiveTunnel.cpp` | 11.600 líneas |
| `WebServer.cpp` | 8.000 líneas |
| `LiveStreamManager.cpp` | 4.900 líneas |

La medida útil no es sólo el número de líneas. El problema es que cada archivo
mezcla varias razones de cambio: wire, estado, timers, locks, I/O, política,
serialización, UI y diagnóstico.

El resultado debe permitir:

- probar lógica crítica sin levantar MFC, sockets ni procesos externos;
- revisar cambios dentro de un dominio pequeño;
- expresar ownership y orden de locks en una sola ubicación;
- impedir dependencias circulares;
- mantener exactamente el comportamiento observable durante cada extracción;
- hacer que el tamaño y acoplamiento no vuelvan a crecer sin un gate explícito.

Este plan no autoriza una reescritura. Cada migración es incremental y
reversible.

---

## 2. Relación con beta.2 y con el plan funcional 9.2

`9.1.0-beta.2` es la baseline de conducta y pruebas. No se inicia una extracción
si esa baseline no compila y sus suites Core/Integration no están verdes.

Las extracciones 9.2 se intercalan con el plan funcional mediante esta regla:

1. caracterizar comportamiento existente;
2. mover una responsabilidad sin cambiarla;
3. demostrar equivalencia;
4. integrar;
5. sólo en un cambio posterior modificar la conducta.

Una tarea funcional puede usar un módulo ya extraído. No puede ampliar el
alcance de una extracción en curso.

## 3. Objetivos cuantitativos

### 3.1 Tamaño de coordinadores

| Archivo | Objetivo | Límite duro al cerrar 9.2 |
|---|---:|---:|
| `LiveTunnel.cpp` | 2.500–3.500 | 4.000 |
| `LiveTunnel.h` | 500–750 | 900 |
| `WebServer.cpp` | 2.000–3.000 | 3.500 |
| `LiveStreamManager.cpp` | 2.000–2.500 | 3.000 |
| `LiveStreamManager.h` | 400–600 | 700 |

El límite no se consigue moviendo código a un único monolito nuevo. Los módulos
extraídos deben estar normalmente entre 300 y 1.200 líneas por implementación.
Una excepción superior a 1.500 líneas requiere ADR y desglose posterior.

### 3.2 Acoplamiento

- cero ciclos entre módulos nuevos;
- un módulo de dominio no incluye `EmuleDlg.h`, `WebServer.h` o el coordinador
  del que fue extraído;
- acceso a tiempo, red, filesystem y procesos mediante interfaces estrechas;
- estado mutable con un único owner;
- ningún lock se expone públicamente;
- máximo recomendado de ocho dependencias directas por módulo de dominio.

### 3.3 Calidad

- ≥90 % de líneas y ≥85 % de branches en lógica pura extraída;
- 100 % de vectores wire normativos contra código de producción;
- cero warning en módulos nuevos con `/W4 /WX`;
- sanitizers en módulos portables;
- cero cambio del wire o persistencia durante una extracción mecánica;
- Core, Integration y self-tests verdes después de cada slice.

## 4. Principios de diseño

1. **Coordinador fino.** Recibe eventos y delega; no implementa codecs,
   almacenamiento ni algoritmos.
2. **Estado junto a invariantes.** La estructura y las operaciones que la
   mantienen válida pertenecen al mismo módulo.
3. **I/O en los bordes.** Parsing, políticas y transiciones se prueban sin I/O.
4. **Dependencias hacia dentro.** MFC y Windows pueden depender del dominio; el
   dominio no depende de MFC cuando sea evitable.
5. **Contratos explícitos.** Cada módulo declara entradas, salidas, errores,
   ownership, thread y locks.
6. **Compatibilidad primero.** Mover no implica reinterpretar el protocolo.
7. **Una dimensión por PR.** Extracción, cambio funcional y optimización no se
   mezclan.
8. **No crear `Utils2`.** El código compartido necesita un dominio y un owner.

## 5. Arquitectura objetivo

### 5.1 Túneles Live

`LiveTunnel` queda como fachada y coordinador. Las responsabilidades candidatas
se extraen en este orden:

| Módulo | Responsabilidad |
|---|---|
| `LiveTunnelFraming` | headers, fragmentación y reensamblado; iniciado en beta.2 |
| `LiveTunnelPending` | requests pendientes, deadlines, retry y completion única |
| `LiveCircuitRegistry` | identidad, estados y lookup de circuitos |
| `LiveCircuitHandshake` | CREATE/CREATED/EXTEND/EXTENDED |
| `LiveRelayDispatcher` | validación y dispatch de sub-opcodes |
| `LiveExitServices` | registro y lifecycle de handlers de salida |
| `LiveTunnelScheduler` | ticks, timers, shaping y trabajo diferido |
| `LiveTunnelPeerState` | desconexión, cooldown, penalización y selección |
| `LiveTunnelKadBridge` | límites explícitos entre Kad2/Kad6 y túneles |
| `LiveTunnelMetrics` | snapshots inmutables y contadores |

Orden de locks objetivo:

`registry/estado → pending → cola → timer/leaf`

Los callbacks externos se invocan sin mantener locks internos.

### 5.2 WebServer nativo

`CWebServer` conserva lifecycle, socket entrypoint y compatibilidad pública.

| Módulo | Responsabilidad |
|---|---|
| `WebRequestParser` | request line, headers, límites y normalización |
| `WebAuthPolicy` | sesión, CSRF, permisos y rate limit |
| `WebRouteTable` | método/ruta → handler sin cadena monolítica |
| `WebApiSerializer` | JSON/XML/HTML escapado y modelos de respuesta |
| `WebTransferController` | acciones de descarga/subida |
| `WebSearchController` | búsqueda y resultados |
| `WebSharedController` | catálogo compartido |
| `WebStaticAssets` | recursos estáticos, MIME, cache y rangos |
| `WebSocketResponse` | backpressure, streaming y cierre |
| `WebDiagnostics` | estado saneado sin secretos ni rutas privadas |

Los controladores no acceden directamente a sockets. Devuelven un modelo de
respuesta o un stream con ownership documentado.

### 5.3 Streaming Live

`LiveStreamManager` mantiene la orquestación de alto nivel.

| Módulo | Responsabilidad |
|---|---|
| `LiveBroadcastSession` | inicio, parada y estado del emisor |
| `LiveViewerSession` | join, leave y lifecycle del receptor |
| `LivePeerSet` | selección, reemplazo, límites y diversidad |
| `LiveChunkWindow` | ingest, orden, expiración y disponibilidad |
| `LiveStreamSecurity` | firma, pinning, replay y confianza |
| `LiveStreamFanout` | colas, backpressure y entrega a hijos |
| `LiveStreamRecovery` | NACK, FEC, replenishment y emergencia |
| `LiveStreamAnnouncer` | announces y compatibilidad wire |
| `LiveStreamSnapshot` | observabilidad inmutable |

`LiveStreamManager` no debe contener codecs, parsing de paquetes ni cálculos de
política una vez exista su módulo.

### 5.4 Dashboard Node

El dashboard ya usa rutas separadas. 9.2 completa el límite:

- `server.js` sólo compone dependencias y enruta;
- ningún handler usa procesos síncronos;
- filesystem potencialmente lento usa `fs.promises`;
- todos los procesos pasan por el runner limitado;
- contextos tipados mediante JSDoc y validados al inicializar;
- rutas por dominio con tests HTTP reales.

Objetivo: `server.js` ≤300 líneas y rutas individuales ≤500.

## 7. Microciclo obligatorio por slice

Cada slice sigue exactamente:

1. registrar funciones y estado que se moverán;
2. añadir o congelar tests de caracterización;
3. crear interfaz mínima y módulo vacío;
4. mover código sin renombrado masivo;
5. compilar con `/W4 /WX` cuando sea aislable;
6. comparar outputs, vectores y trazas;
7. ejecutar Core e Integration afectados;
8. comprobar que no aparece ciclo ni lock nuevo;
9. reducir el coordinador;
10. registrar LOC, dependencias y evidencia.

Si durante el paso 4 se descubre una corrección funcional, se documenta y se
realiza en un cambio separado después de cerrar la extracción.

## 8. Gates

### Gate M0 — Entrada

- beta.2 Release x64 y self-test verdes;
- Core e Integration verdes;
- baseline de warnings y LOC registrada;
- worktree y cambios ajenos identificados.

### Gate M1 — Dominio extraído

- API estrecha y ownership documentado;
- characterization tests equivalentes;
- cero wire/persistencia modificado;
- código nuevo sin warnings;
- no aumenta el número total de locks;
- coordinador pierde más líneas de las que gana la fachada.

### Gate M2 — Monolito reducido

- objetivo o límite duro de LOC cumplido;
- cero SCC/ciclo en el grafo de includes;
- ninguna función del coordinador supera 150 líneas salvo dispatch tabular;
- ninguna clase coordinadora posee más de 20 campos mutables;
- métricas y diagnóstico leen snapshots, no estado sin lock.

### Gate M3 — Cierre 9.2

- dos builds limpios del mismo commit;
- Core, Integration, CodeQL y sanitizers verdes;
- soak mínimo de 12 horas sin crecimiento sostenido ni deadlock;
- regresión con peer 0.70b y beta.2;
- documentación de arquitectura actualizada;
- rollback por módulo probado.

## 9. Stop conditions

Se detiene una extracción si:

- cambia un byte wire sin requisito aprobado;
- requiere migración de persistencia;
- aparecen dos owners para el mismo estado;
- un callback necesita ejecutarse bajo un lock interno;
- el nuevo módulo incluye al coordinador;
- la suite no puede distinguir conducta anterior y nueva;
- el diff supera 1.500 líneas netas sin slices independientes;
- la extracción necesita simultáneamente una corrección funcional S1/S2.

La respuesta no es ampliar el PR: se reduce el slice o se crea primero el seam
necesario.

## 12. Definition of Done

El programa sólo termina cuando:

- los tres coordinadores cumplen sus límites;
- la conducta pública conserva compatibilidad;
- el framing y parsers usan código de producción en sus tests;
- locks, ownership y threads están documentados por módulo;
- CI bloquea nuevos ciclos, crecimiento y warnings;
- las suites y el soak están verdes;
- `ARCHITECTURE.md` refleja la implementación, no una intención futura;
- no queda un “nuevo monolito” que simplemente concentre lo extraído.
