# `V92-O01` — Soak simple de leases (definición ejecutable)

Es `V92-O01` tal como lo escribe `V9.2_DEVELOPMENT_AND_TEST_PLAN.md` §20 y
`92-8.3`: ocho horas, muestreo cada cinco minutos, una pérdida provocada, un
reset de epoch y recuperación. Sustituye como gate de release al controlador
formal de `V92_RC1_EXECUTION.md` §4 (decisión D1 en `V9.2_STATE.md`), que
queda como nightly opcional.

## 1. Montaje

- Candidato de `V9.2_STATE.md` §1 en `C:\tmp\emule-rc2`, perfil nuevo, mappings
  activados, web API en `http://127.0.0.1:4711` con token.
- Router real funcionando (runbook §2). Si el router no está disponible, el
  soak puede correr contra el T8 de Hyper-V, pero entonces solo cuenta como
  ensayo: el plan exige el router para la evidencia de 9.2.0.
- El producto pide leases UPnP de 7200 s (`UPnPImplMiniLib.cpp`,
  `kPreferredLeaseSeconds`); no hay preferencia de usuario para acortarlos.
  Sobre un router real, ocho horas observan al menos tres renovaciones. El T8
  limita las concesiones a 120 s y observa muchas más; por eso el T8 sigue
  siendo útil como nightly.

## 2. Ejecución

```powershell
powershell -ExecutionPolicy Bypass -File tools\lab\v92_simple_soak.ps1 `
  -RunDirectory C:\tmp\v92-o01-<sha> -Token <token> -DurationHours 8 -IntervalSeconds 300
```

Intervenciones del operador, anotadas en `C:\tmp\v92-o01-<sha>\operator.txt`
con hora UTC:

1. Hacia las 4 h: borrar el mapping TCP del candidato desde la web del router
   (pérdida). Esperado: `WITHDRAWN`, después `CANDIDATE` y `VERIFIED` de nuevo
   con generación nueva.
2. Hacia las 6 h: reiniciar el router (reset de epoch). Esperado: generación
   nueva, mapping recreado y verificado.
3. Al terminar: cerrar eMule de forma natural y ejecutar el censo UPnP
   (`diagnose_v91_r01_upnp_capacity.ps1`). Comprobar con el Administrador de
   tareas que no queda ningún `emule.exe` ni `ese-server.exe`.

## 3. Veredicto

El script emite `summary.json` con veredicto automático sobre lo que puede
medir y una lista `operator_checks` con lo que no:

| Criterio del plan | Cómo se decide |
|---|---|
| sin crecimiento monótono | working set final ≤ inicial × (1 + `MaxWorkingSetGrowthPercent`/100) y handles final − inicial ≤ `MaxHandleGrowth` |
| generación acotada a cambios reales | número de cambios de `topology_generation` ≤ `ExpectedGenerationChanges` (2 = las dos intervenciones; usar 3 si hubo un cambio de red real más) |
| proceso vivo todo el soak | el mismo PID en todas las muestras; API disponible en ≥ 95 % de ellas |
| sin mapping huérfano | censo del operador tras el cierre: cero entradas propias |
| cero thread/proceso huérfano | comprobación del operador tras el cierre |

`PASS` = veredicto automático PASS y las dos comprobaciones del operador
anotadas como limpias. Cualquier otra cosa es FAIL y se atribuye al commit
del candidato, nunca se reetiqueta.

## 4. Lo que no hace

No arranca ni cierra eMule, no toca el router, no restaura perfiles, no crea
worktrees ni sella nada. Si falla, o es un bug del producto y se arregla en
el candidato, o es un defecto del muestreador y se simplifica el muestreador.
