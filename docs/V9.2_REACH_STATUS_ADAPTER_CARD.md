# Tarjeta 9.2 — Adapter de lectura `/api/reach/status`

Estado: **LISTA PARA EJECUTAR** · redactada 2026-08-03
Programa: eSE 9.2 · prerrequisito duro de `G92-93-DEV`
Rama destino: la rama activa de 9.2. **No `main`** (ver §11)

## 1. Por qué existe esta tarjeta

`HG06` del gate `G92-93-DEV` exige observar tres ciclos
`CANDIDATE → VERIFIED → WITHDRAWN` en un router real, y `HG03` exige que
`candidate`, `verified`, `expired` y `stale` sean distinguibles **sin leer
logs**. Hoy eso es imposible: el estado existe y está tipado en
`natmap::ReachabilitySnapshot`, `CDirectReachabilityManager::GetSnapshot()` lo
devuelve, y **nadie lo serializa**. Lo único observable por HTTP es
`upnp_ports_forwarded` (`true|false|unknown`), que colapsa UPnP, PCP y NAT-PMP
en un booleano.

Sin esta tarjeta, una sesión de laboratorio con router real no produce
evidencia admisible. Con ella se desbloquean `HG03`, `HG06`, `HG07` (mitad de
generación), `H93-03`, `H93-07`, `H93-09` y `H93-11`.

Alcance: **un lector**. Cero lógica nueva de alcanzabilidad, cero cambio de
comportamiento, cero wire.

## 3. Invariantes no negociables

1. **El endpoint no muta nada.** Es de solo lectura. No dispara verificación,
   no renueva lease, no cambia generación.
2. **No se llama a `GetSnapshot()` desde el hilo del WebServer.** El manager
   valida `AssertMainThread()` (`DirectReachabilityManager.h:40`, `.cpp:80`) y
   devuelve **referencia** a un miembro mutable. Llamarlo desde el worker es
   assert en debug y data race en release.
3. **Cero secretos y cero IP completa en la respuesta.** En particular
   `PortLease::ownership_nonce` (12 bytes) es una credencial PCP y **nunca**
   se serializa. Las direcciones se emiten como familia + clase + puerto. Ver
   §5.3.
4. **No se redefine la frontera 9.2→9.3.** Este endpoint es una proyección
   diagnóstica, **no** es `DirectCandidateSnapshotV1`. No puede reinterpretar
   ownership, endpoint, verificación ni generación. Ver §10.
5. **`ReasonCode` es append-only y persistido** (`natmap_types.h:59`, con
   `static_assert` en `:230`). Se emite el nombre **y** el número. Nunca se
   renumera.

## 4. Contrato de estados (resuelve la ambigüedad de vocabulario)

Las tarjetas del gate hablan de `CANDIDATE`/`VERIFIED`/`WITHDRAWN`. El código
tiene otra máquina (`ReachabilityState`, `natmap_types.h:40`). **No es una
biyección.** Esta tabla es normativa y debe implementarse literalmente:

| `gate_state` | `ReachabilityState` | Razón |
|---|---|---|
| `DISABLED` | `Disabled` | no participa |
| `DISCOVERING` | `Discovering`, `Mapping` | trabajo previo al candidato |
| `CANDIDATE` | `CandidateMapped`, `Verifying` | existe mapping, **no** hay prueba |
| `VERIFIED` | `Reachable`, `Renewing` | probado; `Renewing` sigue siendo alcanzable |
| `WITHDRAWN` | `Degraded` | lo tuvo y lo perdió |
| `BLOCKED` | `BlockedByCgnat`, `BlockedByRouter` | estructuralmente imposible |

La decisión de diseño que importa: **`Verifying` es `CANDIDATE`, no
`VERIFIED`.** Un mapping en curso de verificación todavía no tiene prueba, y
`VERIFIED` sin prueba es exactamente el éxito ficticio que el gate persigue.

`expired` y `stale` **no son estados**, son cualificadores ortogonales, y son
lo que `HG03` pide distinguir:

- `expired` = `reason == LeaseExpired`, o la vida del lease ya consumida.
- `stale` = la evidencia pertenece a otra generación, es decir
  `primary_evidence.generation != topology_generation`
  (equivale a `Evidence::IsCurrent()` en `natmap_types.h:197`).

Se emiten como booleanos explícitos para que `HG03` sea decidible sin
interpretar nada.

## 5. Contrato de salida

### 5.1 Forma

### 5.3 Privacidad — normativo

`H93-14` exige cero token, nonce o IP completa exportada. Por tanto:

- **Nunca** se emite `ownership_nonce`. Ni truncado, ni hasheado, ni bajo flag.
- **Nunca** se emite una dirección IP completa. Se emite `family` +
  `address_class` + `port`. El puerto sí es necesario: es lo que `HG06`
  observa cambiar.
- **No existe parámetro para revelar direcciones.** Si el laboratorio necesita
  la dirección real la obtiene del sistema operativo con
  `tools/lab/*` bajo `-IncludeSensitive`, no de este endpoint. Un flag de
  revelado en una API HTTP es un footgun permanente a cambio de comodidad
  puntual.
- `Evidence::observed_monotonic_ms` **no** se emite: es reloj interno y no
  aporta al gate. (`ESC-SECURITY` si alguien propone emitirlo.)

`address_class` se deriva de los helpers que ya existen en `IpAddress`
(`IsPrivateOrSharedV4`, `IsRfc1918V4`, `IsSharedCgnatV4`, `IsUnspecified`,
`natmap_types.h:109-142`). No escribir clasificación nueva.

## 6. Receta de implementación

### 6.1 `DirectReachabilityManager.h`

Copiar literalmente la forma de `RelayClient.h:30/41/48/49`:

```cpp
// público
void GetStatusJson(CStringA& json) const;
// privado
void UpdateStatusCache() noexcept;
mutable std::mutex m_cacheMutex;
std::string m_statusJson;
```

Requiere `#include <mutex>` y `#include <string>`.

`std::string` y **no** `CString`: el refcount de MFC no es thread-safe entre
hilos, y ese es exactamente el bug que este patrón evita.

### 6.2 `DirectReachabilityManager.cpp`

El patrón exacto de `RelayClient.cpp:299-344`, cuya parte no obvia es el orden:

```cpp
void CDirectReachabilityManager::UpdateStatusCache() noexcept
{
    AssertMainThread();
    CStringA json;
    // ... formatear AQUÍ, FUERA del lock ...
    std::lock_guard<std::mutex> lock(m_cacheMutex);
    m_statusJson.assign(json.GetString(), (std::size_t)json.GetLength());
}

void CDirectReachabilityManager::GetStatusJson(CStringA& json) const
{
    std::lock_guard<std::mutex> lock(m_cacheMutex);
    json = m_statusJson.c_str();
}
```

El lock cubre **la publicación, no la lectura del estado**. Leer `m_snapshot`
es seguro porque `UpdateStatusCache()` corre siempre en el hilo propietario.

Llamar a `UpdateStatusCache()` al final de cada mutador que ya asserta hilo
principal: `Initialize`, `ObserveMappedPorts`, `ObserveServerIdChange`,
`ObserveInboundTcpAccept`, `BeginEd2kVerification`. Si un mutador nuevo no la
llama, el endpoint sirve estado viejo — que es peor que no servir nada, porque
`HG06` lo leería como una transición que no ocurrió.

### 6.3 `WebServer.cpp` — inserción 1, la allowlist (**seguridad**)

En `bIsLiveOrHolepunch` (líneas 4592-4604), entre la línea de `/api/krp/` y la
de `/api/network/`:

```cpp
        || (sURL.Left(11) == "/api/reach/")
```

**Esto no es opcional.** La lista es *opt-in*: un `/api/` que no aparezca en
ella **no** pasa por la puerta loopback/token y queda accesible desde cualquier
IP que `AllowedRemoteAccessIPs` admita, cuyo valor por defecto es permitir
todas. Añadir el handler sin esta línea publica el estado de red del usuario a
la LAN. `"/api/reach/"` son exactamente 11 caracteres.

**No** añadir nada a la puerta admin de 4632-4636: es un endpoint de solo
lectura y el precedente directo, `/api/krp/status`, tampoco está.

### 6.4 `WebServer.cpp` — inserción 2, el handler

Insertar inmediatamente después del bloque de `/api/krp/status` (que termina en
5579) y antes del comentario de `/api/relay/`:

```cpp
if (sURL == "/api/reach/status") {
    CStringA json;
    if (theApp.directreachability != NULL)
        theApp.directreachability->GetStatusJson(json);
    else
        json = "{\"schema\":\"ESE_REACH_STATUS_V1\",\"available\":false,"
               "\"topology_generation\":0,\"planes\":{}}";
    CStringA hdr;
    hdr.Format(
        "HTTP/1.1 200 OK\r\nContent-Type: application/json\r\n"
        "Cache-Control: no-store\r\nX-Content-Type-Options: nosniff\r\n"
        "Content-Length: %d\r\n\r\n", json.GetLength());
    Data.pSocket->SendData(hdr, hdr.GetLength());
    Data.pSocket->SendData(json, json.GetLength());
    return;
}
```

Tres trampas verificadas en el árbol:

- `sURL == "..."` es **igualdad exacta**: `/api/reach/status?x=1` daría 404. Es
  lo correcto aquí (el endpoint no toma parámetros) y replica `krp`.
- **No** usar el macro `HTTPInit` que usa `/api/status`: ya incluye
  `Content-Type: text/html` y produce dos cabeceras `Content-Type`. Usar la
  variante de `krp`, que es la de arriba.
- Todo campo string que no sea un enum debe pasar por `EseJsonEscapeA`
  (`WebServer.cpp:4427`). En este contrato todos los strings son nombres de
  enum controlados por nosotros, así que en la práctica no hay entrada
  externa — pero si se añade un campo libre, escaparlo.

## 10. Obligación de reconciliación con `DirectCandidateSnapshotV1`

`TH92-1` congeló `DirectCandidateSnapshotV1` (PASS, `0ce0d88f`) y ese artefacto
**no está en `main`** — vive en la rama de 9.2. Antes de escribir código:

1. localizar el schema congelado y sus cinco goldens;
2. comprobar campo a campo que este endpoint **no contradice** su semántica de
   ownership, endpoint, verificación ni generación;
3. si hay colisión de nombres o de significado, **manda el schema congelado** y
   este contrato se adapta, nunca al revés.

Motivo: cambiar la frontera después de `WP93-0` dispara el riesgo 13 del plan
9.3 y obliga a rebasar y repetir `H93-01`–`H93-16`. Un endpoint diagnóstico no
puede tener ese poder.

## 11. Por qué en la rama de 9.2 y no en `main`

`WebServer.cpp` es precisamente el fichero que el programa `M2A-W10`
(`codex/v9.2-w10-live-api-settings-diagnostics`) está modularizando, con
presupuestos de LOC y ratchet activos. Implementar esto en `main` garantiza
conflicto de merge sobre un fichero de máximo churn, y probablemente rompe el
ratchet de LOC de la tarjeta activa.

Consecuencia práctica: coordinar con la tarjeta `M2A` en curso. Si el handler
debe nacer ya dentro de la fachada modularizada en vez de en el `if` gigante de
`_ProcessLiveAPI`, **eso manda** — la receta de §6.4 describe la forma actual
del árbol, no una obligación de conservarla.
