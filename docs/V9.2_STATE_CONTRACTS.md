# eSE 9.2 — Contratos de estado, evidencia y tiempo

Estado: contrato inicial de `92-0.3`; no cambia código productivo.

## 1. Vocabulario

| Término | Significado contractual | No significa |
|---|---|---|
| `candidate` | endpoint posible, con procedencia y generación | alcanzable o publicable como verificado |
| `verified` | endpoint que satisface el predicado de evidencia de su plano | que funcionará para todo peer o toda red |
| `topology_generation` | identidad local monotónica de una topología y sus endpoints | epoch del router o reloj civil |
| `mapper_epoch` | señal del mapper sobre su propio reinicio/continuidad | generación local |
| `lease` | concesión del mapper con ownership y expiración | prueba de entrada desde Internet |
| `primary evidence` | observación externa exigida por el plano | inbound por sí sola |
| `inbound evidence` | entrada válida ligada al endpoint y generación | HighID por sí sola |
| `ownership` | capacidad demostrada de renovar o retirar una regla propia | permiso para borrar una regla parecida |
| `network kind` | `NATIVE`, `OVERLAY` o `UNKNOWN` | clase de dirección IP |
| `verification attempt` | contexto inmutable que liga endpoint, generación, inicio y deadline | el estado actual leído al llegar un callback |
| `publishable` | candidato que puede anunciarse para obtener proof sin declararse verificado | `verified` o HighID |
| `fresh evidence` | evidencia recibida antes del deadline monotónico del intento | timestamp civil o evento reetiquetado |

## 2. Estados

| Estado | Entrada válida | Invariantes | Salida normal |
|---|---|---|---|
| `Disabled` | preferencia mappings OFF o inicialización anterior a activación | puertos anunciados clásicos; sin mapping activo | activación explícita |
| `Discovering` | `BeginGeneration` creciente | evidencia anterior vacía | mapper elegido o terminal explicable |
| `Mapping` | discovery/degraded con request vigente | request y generación actuales | mapping candidato o fallo |
| `CandidateMapped` | MAP/readback estructuralmente válido | lease y endpoint coherentes; aún no verificado | iniciar verificación, retirar o degradar |
| `Verifying` | candidato vigente | no promocionar sin predicado completo | verified o degraded |
| `Reachable` | predicado de evidencia completo y específico del plano | endpoint, intento, lease y evidencias pertenecen a la misma generación | renovar, retirar o nueva generación |
| `Renewing` | lease alcanzó deadline | identidad anterior no cambia silenciosamente | misma identidad renovada o nueva generación |
| `Degraded` | pérdida de lease/proof o fallo acotado | endpoint anterior no es publicable | retry acotado, mapping o terminal |
| `BlockedByCgnat` | ruta nativa RFC6598 sin capa superior válida | overlay no puede producir este veredicto por sí solo | nueva topología o PCP upstream autorizado |
| `BlockedByRouter` | todos los mecanismos autorizados rechazados | razón estable; sin falso HighID | nueva topología/configuración |

## 3. Predicados de verificación

### eD2K TCP IPv4

Requiere simultáneamente:

1. mapping/endpoint coherente;
2. evidencia `ServerHighId`;
3. evidencia `InboundTcpAccept`;
4. endpoint y generación idénticos en ambas evidencias.

Servidor solo o inbound solo conservan estado no verificado.

La igualdad obligatoria es:

```text
lease.public_endpoint
  == advertised
  == verification_attempt.endpoint
  == ServerHighId.endpoint
  == InboundTcpAccept.endpoint
```

Ambas evidencias deben contener el mismo `verification_attempt_id`, la misma
generación y un timestamp monotónico comprendido entre `started_ms` y
`deadline_ms`. El deadline por defecto es 30 segundos; una configuración de
laboratorio puede reducirlo, nunca ampliarlo silenciosamente.

`VerificationSucceeded` no acepta evidencias nuevas ni incompletas. Es una
transición derivada que solo puede ejecutarse cuando el snapshot ya satisface
el predicado completo del plano. Para eD2K, `IsSnapshotConsistent`,
`HasClassicHighIdEvidence` y la transición usan exactamente el predicado
anterior.

### Contexto de verificación

Al comenzar una verificación se captura un valor inmutable:

```text
VerificationAttempt
  attempt_id
  topology_generation
  endpoint
  transport
  started_monotonic_ms
  deadline_monotonic_ms
```

El servidor y el accept entregan el contexto capturado por la operación que los
originó. El manager no puede fabricar endpoint, generación o attempt a partir
del snapshot vigente cuando llega el callback. Un evento sin correlación,
posterior al deadline o perteneciente a otro endpoint es `STALE/INVALID` y no
modifica el snapshot.

### IPv6 directa

Una dirección global solo crea candidato. La promoción requiere entrada externa
válida o pinhole/firewall autorizado, vigente y ligado a interfaz y generación.
La evidencia IPv6 usa un attempt propio y debe coincidir con dirección,
interfaz, puerto, generación y deadline. Una dirección suministrada por overlay
no satisface el predicado nativo.

### LAN

RFC1918, ULA o link-local solo pueden crear `LAN/SAME_LAN` tras prueba positiva
del mismo dominio. Nunca se publican como ruta global.

## 4. Generación y epoch

La generación:

- empieza en un valor no nulo;
- aumenta al cambiar interfaz, dirección, gateway, endpoint, identidad del
  mapping, mapper o epoch incompatible;
- no aumenta por una renovación idéntica;
- invalida callbacks, proofs, leases y snapshots anteriores;
- nunca disminuye ni se reutiliza durante el proceso.

El epoch:

- pertenece al mapper;
- puede revelar un reinicio;
- se normaliza por protocolo como `CONTINUOUS`, `RESET` o `INVALID`;
- provoca una nueva generación cuando rompe continuidad;
- nunca reemplaza al identificador local de generación.

Solo `CONTINUOUS`, con endpoint, mapper, gateway, transporte y ownership
idénticos, permite conservar generación. `RESET` obliga a:

1. invalidar proof y attempts;
2. retirar el candidato publicado;
3. avanzar una única generación común TCP/UDP;
4. reconstruir mapping;
5. verificar otra vez.

`INVALID` falla cerrado. PCP y NAT-PMP mantienen vectores independientes de
continuidad, reset, wrap permitido y retroceso inválido. Ninguna capa puede
sustituir el epoch recibido y retornar éxito sin consultar esa clasificación.

## 5. Eventos

| Evento | Precondición | Efecto | Rechazo obligatorio |
|---|---|---|---|
| `BeginGeneration` | generación mayor | limpia evidencia y comienza discovery | igual o menor → stale |
| `MappingStarted` | discovering/degraded | mapping | estado distinto → invalid |
| `MappingSucceeded` | mapping + lease válida actual | candidate | endpoint/lease/generación incoherente |
| `VerificationStarted` | candidate vigente | verifying | sin lease o endpoint |
| `ServerEvidenceObserved` | endpoint/generación actuales | conserva o completa proof | endpoint/generación distintos |
| `InboundEvidenceObserved` | endpoint/generación actuales | conserva o completa proof | tipo, endpoint o generación distintos |
| `VerificationSucceeded` | predicado completo ya presente en el snapshot | reachable | tipo, endpoint, attempt, deadline o generación distintos |
| `RenewalDue` | reachable | renewing | otro estado |
| `RenewalSucceeded` | misma identidad y generación | reachable | endpoint/epoch incompatible |
| `LeaseLost` | estado activo | degraded y retirada | evento stale |
| `Disable` | generación no antigua | baseline clásico | evento antiguo |

## 6. Atomicidad TCP/UDP

Un intento de mapping que solicita TCP y UDP es una transacción:

1. ambos resultados se preparan fuera del snapshot visible;
2. ambos deben compartir generación, mapper, gateway y ownership de instancia;
3. si uno falla, se revierte únicamente lo creado por el intento;
4. el commit publica el par completo una sola vez;
5. ninguna lectura puede observar TCP nuevo con UDP anterior.

TCP sin UDP solo es válido cuando la tarea declaró explícitamente un perfil
TCP-only antes del intento. Una renovación parcial nunca conserva `Reachable`.

## 7. Clasificación de red y routability

`NetworkKind` es obligatorio en interfaz, candidato, evento y snapshot:

- `NATIVE`: ruta suministrada por el acceso normal del host;
- `OVERLAY`: Tailscale, WARP, WireGuard, ZeroTier o equivalente identificado;
- `UNKNOWN`: no existe evidencia suficiente para afirmar ninguna de las dos.

Se clasifica de forma separada la dirección:

- IPv4: unspecified, loopback, link-local, RFC1918, RFC6598, multicast,
  documentación, reservada y pública;
- IPv6: unspecified, loopback, link-local, ULA, multicast, documentación y
  global.

Solo `NATIVE + RFC6598` puede producir `BlockedByCgnat`. `OVERLAY + RFC6598`
conserva la clase de dirección y el origen overlay, pero no afirma CGNAT nativo.
`UNKNOWN` nunca se promociona como conectividad nativa. Ninguna dirección
unspecified, loopback, link-local, multicast, documentación o reservada es
publicable globalmente.

`preference_enabled`, `candidate_publishable` y `verified_reachable` son tres
valores distintos. Un bloqueo de router/CGNAT no cambia la preferencia a OFF.

## 8. Ownership

El booleano `owned_by_us` no es una entrada confiable. La lease conserva una
prueba discriminada:

```text
OwnershipProof
  kind                  NONE | UPNP_JOURNAL | PCP_NONCE | NATPMP_LEASE_SCOPE
  instance_id_digest
  gateway_identity
  mapper
  transport
  internal_endpoint
  external_endpoint
  topology_generation
  protocol_proof_digest
```

UPnP exige journal/description reconciliados; PCP exige nonce; NAT-PMP solo
permite acciones limitadas a la lease exacta creada por la instancia. Renovar o
borrar requiere coincidencia de todos los campos aplicables y readback cuando
el protocolo lo soporte. Una respuesta MAP satisfactoria por sí sola nunca
demuestra ownership.

## 9. Prioridad, publicidad y efectos externos

Orden de selección, únicamente entre rutas verificadas:

1. IPv6 global nativa con proof/pinhole vigente;
2. IPv4 pública directa verificada;
3. IPv4 mapeada verificada;
4. baseline clásico.

Un candidato no desplaza una ruta verificada. Al caducar proof, pinhole, lease
o interfaz, la ruta se retira antes de seleccionar fallback.

Un endpoint coherente puede marcarse `publishable` para solicitar al servidor
la verificación, pero UI/API no lo presentan como `verified`. El re-login se
deduplica por `(topology_generation, advertised_endpoint)` y se emite como
máximo una vez por cambio real.

La firma de red incluye interfaces y familias elegibles, direcciones,
gateways, `NetworkKind` y mappings relevantes. Un cambio:

- cancela requests y attempts con su ID original;
- incrementa una sola generación;
- invalida callbacks anteriores;
- reconstruye candidatos antes de anunciar.

## 10. Snapshot público mínimo

La frontera que posteriormente congela `TH92-1` debe representar al menos:

```text
DirectCandidateSnapshotV1
  schema_version
  topology_generation
  created_at_monotonic
  candidates[]
  terminal_reason

DirectCandidateV1
  candidate_id
  kind
  transport
  local_endpoint
  published_endpoint
  network_kind
  interface_identity_digest
  source
  scope
  mapping_identity
  lease_expires_at
  ownership_state
  verification_state
  verification_attempt_id
  evidence_digest
  reason_code
  topology_generation
```

Los campos futuros se ignoran de forma segura y un enum desconocido nunca
activa promoción. Tokens, nonce, GUID de interfaz e IP completa no se exportan
en evidencia sanitizada.

## 11. Casos RED obligatorios posteriores a A03

Antes de modificar producción deben existir pruebas rojas para:

1. `VerificationSucceeded` con primary sola;
2. evidencias de endpoints distintos;
3. evidencias con attempt/generación stale;
4. callback antiguo reetiquetado con el snapshot vigente;
5. deadline de verificación superado;
6. reset de epoch que intenta conservar generación/proof;
7. TCP nuevo con UDP anterior o fallo parcial visible;
8. `100.64/10` nativo frente a overlay;
9. loopback, link-local, multicast y reservadas como endpoint externo;
10. MAP exitoso con ownership fabricado;
11. dos instancias intentando renovar/borrar la misma regla;
12. dos re-login para el mismo endpoint/generación;
13. IPv6 candidata desplazando una IPv4 verificada;
14. `BlockedByCgnat` convertido en preferencia OFF;
15. campo/enum futuro intentando activar promoción.

Estos casos son entradas para las tarjetas de implementación correspondientes,
no autorización para corregir producción dentro de `92-0.3`. A04 archiva el
baseline actual aunque revele estas brechas; no las convierte en PASS.
