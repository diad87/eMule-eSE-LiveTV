# eSE 9.2 — Arquitectura del gateway NAT simulado T8

Estado: diseño de `92-1.1` / `B01`. Este documento no autoriza sockets,
codecs ni lógica productiva. La implementación comienza en las tarjetas
posteriores y debe conservar estas fronteras.

## 1. Objetivo y límites

T8 será un gateway NAT de laboratorio reproducible para probar UPnP IGD,
PCP y NAT-PMP sin depender del router doméstico. Un único proceso comparte
una tabla de mappings y una identidad de gateway entre los tres protocolos.
El mismo ejecutable debe funcionar en el host de laboratorio o dentro de la
VM T8.

Esta tarjeta entrega únicamente:

- la decisión de ubicación y lenguaje;
- las fronteras entre dominio puro, protocolos y efectos de red;
- el contrato de comandos, tiempo, estado, log e informes;
- un JSON Schema validable para el modelo mínimo de `92-1.2`.

Quedan fuera de `B01`:

- abrir puertos, descubrir adaptadores o cambiar rutas/firewall;
- implementar codecs UPnP, PCP o NAT-PMP;
- implementar el reducer, el allocator o la inyección de fallos;
- reutilizar lógica productiva de `libnatmap` como oráculo del fixture;
- empaquetar o aprovisionar Hyper-V.

## 2. Decisiones

### 2.1 Ubicación

El fixture vive en `tools/lab/nat_gateway/`. Es una herramienta de laboratorio
separada de `srchybrid` y de `libnatmap`; no se enlaza con MFC ni se carga
dentro de `emule.exe`.

### 2.2 Lenguaje: Node.js 22, JavaScript estricto

Se elige Node.js 22 con módulos CommonJS y solo biblioteca estándar para el
primer corte.

Razones:

- Node.js 22 ya forma parte de los prerrequisitos y del empaquetado del
  repositorio; `tools/lab` ya contiene fixtures de red en JavaScript.
- UDP, TCP/HTTP, timers monotónicos, streams JSONL y control por `stdin/stdout`
  están disponibles sin MFC ni privilegios especiales.
- JSON es un valor nativo, lo que reduce la superficie del parser de escenarios
  y del plano de control.
- un proceso/event loop simplifica el orden total reproducible de eventos y
  evita sincronización compartida entre tres servicios.
- el mismo código se ejecuta en el host Windows y en una VM sin recompilar.

La ausencia de tipos estáticos se compensa con schema estricto, validación
antes del arranque, objetos inmutables en la frontera del dominio y tests de
reducer/codecs. Si una dependencia externa llegara a ser necesaria, requiere
una decisión posterior con versión y licencia fijadas; no se presupone aquí.

El fixture no importará los codecs productivos de `libnatmap`. Sus vectores de
test sí serán una fuente de interoperabilidad, pero un encoder de respuesta
independiente evita que el cliente y el simulador compartan el mismo defecto.

### 2.3 Un proceso, tres módulos y un estado compartido

El proceso contiene módulos independientes UPnP, PCP y NAT-PMP. Los adapters
de red demultiplexan y normalizan una petición a un comando de dominio. Los
módulos de protocolo convierten valores semánticos en bytes o XML, pero nunca
son dueños de la tabla de mappings.

El gateway tiene una sola identidad, WAN, LAN, epoch, generation, allocator,
contador de peticiones y cola de respuestas. Una operación observada por un
protocolo es visible a los otros cuando el protocolo permite enumerarla o
entrar en conflicto con ella.

## 3. Arquitectura

```text
CLI / JSON stdin
        |
        v
Command adapter ---- Scenario validator
        |                    |
        +----------+---------+
                   v
          Gateway reducer puro
          - mapping table
          - allocation policy
          - ownership checks
          - counters / queue
          - faults / epoch
                   |
          effects + next state
                   |
        +----------+-----------+
        |          |           |
      UPnP        PCP       NAT-PMP       protocol modules
        |          |           |
     SSDP/HTTP   UDP adapter  UDP adapter  network adapters
        |
        +---------------> JSONL event sink / report projector

     Clock port <----- real monotonic | virtual deterministic
```

### 3.1 Fronteras de módulos previstas

| Frontera | Responsabilidad | Prohibido |
|---|---|---|
| `domain/gateway_state` | valores de estado, invariantes y snapshot | sockets, filesystem, timers |
| `domain/reducer` | `(state, command, now) -> {state, effects, events}` | leer reloj o generar azar global |
| `domain/allocation` | selección determinista de puerto a partir de reglas y seed | consultar puertos del host |
| `domain/ownership` | comparar owner/nonce/scope aplicable | asumir ownership por éxito MAP |
| `domain/faults` | seleccionar una acción declarada por contador/selector | dormir o enviar paquetes |
| `protocols/upnp` | valores SSDP, descriptor y SOAP | mutar mappings directamente |
| `protocols/pcp` | parseo/encoding PCP y validación estructural | decidir generación local |
| `protocols/natpmp` | parseo/encoding NAT-PMP y validación estructural | decidir generación local |
| `adapters/*` | bind, receive, send y datos de origen | política, ownership o allocation |
| `control/*` | traducir CLI/JSON a comandos | acceso lateral al estado |
| `reporting/*` | JSONL y proyección sanitizada | payloads, nonce o IP completas |

Cada adapter recibe explícitamente sus puertos y selector de interfaz. Ningún
módulo de dominio conoce nombres de NIC, handles, sockets o privilegios.

### 3.2 Modelo de efectos

El reducer no ejecuta I/O. Devuelve efectos declarativos como
`SEND_RESPONSE`, `SCHEDULE_RESPONSE`, `CANCEL_RESPONSE`, `BIND_ADAPTER`,
`CLOSE_ADAPTER` o `WRITE_EVENT`. Un runtime interpreta esos efectos.

Antes de publicar el estado siguiente se comprueban sus invariantes. Un fallo
de invariant es terminal para el escenario y produce un evento sanitizado; no
se intenta reparar silenciosamente.

## 4. Estado y semántica temporal

### 4.1 Estado mínimo

El escenario de `scenario.schema.json` describe:

- `gateway_id`, epoch, generation, WAN y una o más LAN;
- configuración lógica de adapters y puertos;
- protocolos habilitados;
- regla de asignación de puertos;
- mappings TCP/UDP iniciales;
- owner/nonce cuando el protocolo lo permite;
- lease inicial, creación y expiración;
- contadores de peticiones;
- cola semántica de respuestas;
- fallos declarativos;
- política de privacidad del informe.

Los datagramas, HTTP bodies y payloads crudos no forman parte del estado
persistente ni del informe.

### 4.2 Reloj inyectable

La única interfaz temporal del dominio es:

```text
now_ms() -> uint53 monotónico
advance_ms(delta_ms) -> now_ms
```

`RealMonotonicClock` usa el reloj monotónico del runtime. No deriva expiración,
orden ni freshness de UTC. `VirtualClock` comienza en
`clock.start_monotonic_ms` y solo avanza mediante `advance-time`.

En modo virtual, un avance:

1. mueve el reloj hasta el siguiente deadline menor o igual al destino;
2. procesa todos los eventos de ese instante por `(deadline, insertion_seq)`;
3. repite hasta agotar deadlines;
4. deja el reloj exactamente en el destino.

No se usa `Sleep` en tests. El reloj UTC puede aparecer como dato informativo
del proceso, nunca como causa de una transición.

### 4.3 Epoch y generation

`epoch` pertenece al gateway y se expresa en segundos de protocolo. PCP y
NAT-PMP leen la misma fuente de epoch; UPnP no lo publica, pero comparte los
efectos del reinicio. `restart-epoch`:

1. invalida respuestas pendientes;
2. elimina mappings del gateway;
3. instala el `restart_seconds` del escenario;
4. incrementa una sola generation;
5. registra el cambio antes de aceptar otra petición.

`generation` es local, empieza en un valor no nulo, nunca disminuye ni se
reutiliza durante la vida del proceso. Aumenta una vez cuando cambia WAN,
gateway, identidad de mapping, allocator incompatible o epoch reiniciado. Una
renovación idéntica conserva generation.

`reset` reconstruye el baseline de forma determinista, pero conserva el
allocator monotónico de generation del proceso. Por tanto, dos secuencias de
comandos iguales producen snapshots iguales; el único valor no reciclable es
la nueva generation asignada al reset. Esto evita que respuestas anteriores
se vuelvan actuales accidentalmente.

## 5. Mappings, leases y ownership

La clave de colisión es `(external_address, external_port, transport)`. TCP y
UDP son espacios distintos. Cada mapping conserva protocolo creador, cliente,
endpoint interno, puerto solicitado/concedido, epoch y generation.

Una lease finita usa:

```text
created_monotonic_ms + lifetime_seconds * 1000 == expires_monotonic_ms
```

Una lease permanente usa `lifetime_seconds = 0` y
`expires_monotonic_ms = null`. El valor cero solo significa permanente donde
el protocolo lo permita; una petición de borrado se representa como operación,
no como mapping persistente.

Ownership es discriminado:

- UPnP: journal/description reconciliados y digest de instancia/gateway;
- PCP: nonce de 96 bits y digest de instancia;
- NAT-PMP: scope exacto de la lease y digest de instancia;
- `none`: el protocolo no demuestra ownership.

El nonce puede existir en el escenario privado para producir tráfico PCP, pero
solo su digest aparece en logs o informes. `delete-mapping` falla cerrado si
no coinciden todos los campos aplicables; una respuesta MAP satisfactoria no
crea por sí sola prueba de ownership.

## 6. Atomicidad TCP/UDP

Los protocolos de gateway reciben peticiones TCP y UDP separadas: T8 no
inventará una transacción de red inexistente. La prueba de atomicidad del
producto se obtiene programando respuestas complementarias, por ejemplo:
aceptar TCP y rechazar o perder UDP, y después observar el cleanup de TCP.

T8 garantiza que cada comando individual muta su tabla atómicamente en el
event loop. `atomic_group_id` permite correlacionar un par en escenarios,
logs e informes, pero no retrasa ni fusiona peticiones. Para un par válido:

- hay exactamente un mapping TCP y uno UDP;
- comparten generation, gateway y owner de instancia;
- una renovación parcial o un epoch reset hace visible el fallo, no fabrica
  un par exitoso.

El consumidor bajo prueba es quien debe preparar ambos resultados fuera de su
snapshot, revertir únicamente lo creado por el intento fallido y publicar el
par una sola vez.

## 7. Inyección de fallos

Los fallos tienen ID estable, selector, trigger contable y una acción. La
selección usa el contador de peticiones ya incrementado y orden de declaración.
Con el mismo escenario, seed y secuencia de comandos, el resultado es idéntico.

El contrato admite, sin definir todavía su implementación:

- demora fija o jitter determinista;
- pérdida, duplicación y reordenamiento;
- respuesta desde adapter/origen incorrecto;
- truncado y replay semántico;
- código de rechazo y lease reducido;
- mapping desaparecido;
- reinicio del gateway/epoch;
- cambio de WAN o de puerto;
- conflicto inducido entre clientes.

Cada aplicación o descarte de fallo produce JSONL con `fault_id`, selector,
contador y resultado. No se registran payloads.

## 8. Plano de control

El runtime posee una única ruta de comandos. La CLI y los objetos JSON son
fachadas del mismo dispatcher; ninguna escribe el estado directamente.

Interfaces mínimas:

| Comando | Resultado |
|---|---|
| `start` | valida escenario, crea estado y solicita bind de adapters |
| `stop` | deja de aceptar tráfico, cancela cola y cierra adapters |
| `reset` | vuelve al baseline determinista con generation nueva |
| `load-scenario` | valida y prepara un escenario solo estando parado |
| `advance-time` | avanza tiempo virtual; error estable en modo real |
| `list-mappings` | snapshot ordenado y sanitizado |
| `delete-mapping` | intenta borrar por ID y prueba de ownership |
| `restart-epoch` | simula reinicio compartido del gateway |
| `export-report` | escribe el informe canónico sanitizado |

También se expone `get-status` para readiness sin capturar paquetes.

### 8.1 Envelope JSON

Cada línea de control es un objeto JSON independiente:

```json
{"schema":"ese.v92.t8.command/v1","request_id":"req-0001","command":"advance-time","arguments":{"delta_ms":1000}}
```

La respuesta conserva `request_id`, incluye `ok`, `reason_code`,
`monotonic_ms`, `epoch` y `generation`. Los objetos desconocidos, comandos
desconocidos y argumentos extra se rechazan.

El transporte normativo del control es JSON Lines por `stdin/stdout` del
proceso en foreground. Así no existe un puerto administrativo ni credenciales.
Un runner host o VM conserva los pipes del hijo. La CLI traduce argv al mismo
envelope; un adapter de named pipe futuro sería opcional y local-only.

## 9. Adapters y puertos

Los valores se suministran en el escenario; el dominio no contiene puertos
fijos. El diseño contempla:

| Superficie | Transporte | Puerto convencional | Configuración |
|---|---|---:|---|
| UPnP SSDP | UDP | `1900` | selector de interfaz, bind y puerto |
| UPnP descriptor/control | TCP/HTTP | sin default implícito | selector, bind y puerto |
| PCP | UDP | `5351` | selector, bind y puerto |
| NAT-PMP | UDP | `5351` | selector, bind y puerto |

PCP y NAT-PMP pueden compartir bind/puerto cuando el adapter de datagramas
demultiplexe por versión/opcode, o usar puertos distintos para tests aislados.
La validación de colisiones de binds ocurre antes de abrir el primer socket.

En host se usan interfaces de laboratorio explícitas. En VM se usan nombres
lógicos resueltos por configuración de la VM. No se codifican GUID, nombres de
máquina, Tailscale ni direcciones del entorno del autor.

## 10. JSON Lines e informe

Cada evento tiene como mínimo:

```json
{"schema":"ese.v92.t8.event/v1","sequence":17,"run_id":"run-digest","scenario_id":"pcp-renewal","event":"map_created","monotonic_ms":1200,"gateway_id":"t8-a","epoch":4,"generation":7,"protocol":"pcp","transport":"tcp","mapping_id":"map-1","outcome":"applied","reason_code":"none"}
```

`sequence` es creciente y resuelve empates del mismo instante. Los nombres de
evento y `reason_code` son estables y append-only. `export-report` incluye
identidad/hash del escenario, seed, configuración efectiva sin datos privados,
estado inicial/final normalizado, contadores, fallos aplicados, mappings
sanitizados y verdict técnico. Es compatible con el collector común de WP0.

Por defecto y en todo informe público:

- direcciones se reducen a clase o digest/prefijo;
- nonce, tokens, GUID e identidad de instancia se reducen a SHA-256;
- payloads, headers de autorización y credenciales se omiten;
- nombres de host y adaptadores físicos se sustituyen por IDs lógicos;
- un campo futuro desconocido nunca se copia automáticamente.

No existe opción de credenciales en el schema. Un diagnóstico sensible futuro
requeriría un artefacto privado separado y opt-in explícito; no modifica el
informe canónico.

## 11. Reset, host y VM

`start` es foreground y no requiere elevación para tests de dominio. Los tests
unitarios usan adapters falsos y reloj virtual. Solo un test de integración que
haga bind puede necesitar una reserva o regla de firewall; esa necesidad no se
filtra al núcleo.

El empaquetado de VM, switch, forwarding y teardown pertenece a `92-1.8`.
T8 nunca configura el router doméstico. Los scripts futuros deben ser
idempotentes, resolver adapters lógicos al entrar en la VM y restaurar cambios
de red al salir.

## 12. Validación y criterios de aceptación de B01

El schema debe validarse como Draft 2020-12 con format assertions activadas.
Antes de cualquier bind:

1. se valida JSON y schema;
2. se aplican invariantes cruzadas documentadas que JSON Schema no expresa:
   rangos de allocation ordenados, lease aritméticamente coherente, IDs únicos,
   colisiones de mappings, pares atómicos completos y protocolos/listeners
   concordantes;
3. se rechaza todo el escenario con ruta de campo y reason code estable.

`B01` es aceptable si:

- existen este documento, README y schema;
- el schema es JSON válido y el propio schema pasa un validator 2020-12;
- `additionalProperties: false` cierra todos los objetos de dominio;
- están definidas todas las interfaces mínimas;
- estado/reloj/reducer son independientes de adapters y sockets;
- puertos e interfaces son configurables;
- reset, epoch, generation, lease y ownership no son ambiguos;
- se puede modelar fallo parcial TCP/UDP y los fallos requeridos;
- logs e informes tienen reglas explícitas de privacidad;
- el diff solo contiene los tres artefactos de `B01`.

## 13. STOP

Se detiene la implementación y se devuelve la tarjeta a diseño si ocurre
cualquiera de estas condiciones:

- un test unitario necesita privilegios, NIC real, socket o `Sleep`;
- estado, protocolo o policy importa un adapter de red;
- un adapter muta mappings sin pasar por el reducer;
- no existe `reset` o una misma traza deja estados diferentes;
- generation disminuye/se reutiliza o epoch reemplaza generation;
- TCP/UDP parcial se presenta como par exitoso;
- ownership se deduce solo de puerto, descripción o éxito MAP;
- un escenario inválido llega a abrir un socket;
- un puerto, GUID, adaptador físico, credencial o IP del entorno queda
  codificado;
- logs o reportes contienen payload, nonce/token completo o IP completa;
- el fixture comparte con `libnatmap` la lógica usada como resultado esperado.
