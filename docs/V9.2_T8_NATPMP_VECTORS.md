# V9.2 T8 NAT-PMP vectors (C01)

Source tree commit: `374075c` (the native codec files are unchanged from the
v9.2 base while this table is created).

This C01 table freezes only byte strings already present in the native
NAT-PMP codec tests or directly determined by the existing productive codec.
It is data for future fixture cards, not a Node encoder or decoder. The JS
test uses literal goldens and never imports, executes, or reimplements the C++
codec.

Source baseline: `374075c747a6e1e11ec82ebd4a721817a0340d07`.

`DERIVED_FROM_PRODUCTIVE_CONSTANT` is deliberately narrow: the UDP request
changes only the opcode from the complete TCP test vector, using the existing
`NatPmpTransport::Udp = 1` enum and the existing assignment of that enum to
byte 1. No complete UDP request or response was present in the native tests.

## Byte layout

All multi-byte numeric fields below are network byte order (big-endian):
`Put16`/`Put32` write most-significant byte first in
`libnatmap/src/natpmp_codec.cpp:8-18`, and `Get16`/`Get32` read the same layout
at lines 20-30. The external IPv4 field is intentionally preserved as four
network-order octets by `memcpy` at line 55; it is not host-endian decoded.

## Explicit gap

There is no complete UDP MAP response golden in the existing native test or
productive codec. C01 therefore does not create one. A later card may add a
separate traceable vector after its own evidence is available; it must not
promote the TCP response by changing its opcode in this table.
