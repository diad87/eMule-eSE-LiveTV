## 1. Objetivo

Este stack intenta falsar, no confirmar, cinco afirmaciones:

1. existe una ruta directa A↔B;
2. DCO nomina exactamente una sesión autenticada;
3. R y los witnesses solo transportan control;
4. ninguna técnica excede su autoridad o presupuesto;
5. Birthday y DVL no alteran el significado del Core.

Un ACK, SYN, `UTP_STATE_CONNECT` o handshake DVL no satisface por sí solo el
criterio de éxito de producto.

## 3. Independencia y severidad

- El autor no aprueba su propio cambio crítico.
- Wire, identidad, DCO, Punch2/Punch3, Birthday, DVL y claims estadísticos
  requieren revisión Sol independiente.
- Un hallazgo S0/S1 bloquea todos los tracks afectados.
- Un hallazgo S2 bloquea el track y consume reserva solo tras reproducción.
- Una prueba flaky se trata como fallo hasta aislar causa y seed.
- Tres reintentos manuales sin explicación activan `ESC-ATTEMPTS`.

## 4. Gauntlet

### L0 — Autoridad, alcance y provenance

Bloquea si falta:

- ADR tesis/especificación;
- commit 9.1 RC1, freeze 9.2 o base 9.3;
- worktree limpio y separado;
- matriz requisito→código→test→evidencia;
- modelo ejecutor/revisor y presupuesto de archivos;
- baseline de 206 `libreach`, 14 cookie y 182.789 `libnatmap`.

### L1 — Compilación estricta

Ejecutar configuraciones Debug/Release y x64 soportadas, además de:

```powershell
cmd /d /c .\libreach\make.bat
cmd /d /c .\libnatmap\make.bat
cmd /d /c .\srchybrid\tests\make.bat
powershell -ExecutionPolicy Bypass -File .\tools\verify_eSE.ps1
python .\tools\check_protocol_registry.py
```

No se aceptan nuevos warnings en archivos modificados ni supresiones sin
justificación localizada.

### L2 — Análisis estático y linters semánticos

Checks obligatorios:

- ownership/lifetime y callbacks al hilo propietario;
- conversiones KadID/user hash/node key/session handle;
- arithmetic de longitudes, TTL, clocks y contadores;
- dependencia prohibida hacia relay;
- claves/tokens/cookies/IP completas en logs;
- `CUpDownClient*` dentro de `libreach`;
- TUN/TAP, rutas, sockets arbitrarios o servicios del host en DVL.

Linters de arquitectura:

```text
DirectOnly factory contains no relay adapter
No DCO bypass in Download/Upload/SourceExchange/LiveTV
No uTP expectation from Birthday before verified hit
No remote value raises a local budget
No private/ULA candidate is globally published
```

### L3 — Unit tests y goldens

Cada contrato público tiene:

- caso válido mínimo;
- límite inferior/superior;
- truncation/overflow;
- versión anterior, actual y futura;
- unknown TLV;
- expiración y generación stale;
- identidad, firma, nonce, token y endpoint incorrectos;
- cancelación antes, durante y después de callback.

Goldens separados para `CandidateV1`, la proyección
`ReachabilityDescriptor`↔`ReachVector` v2/v3, `ObservedEndpointReceiptV1`,
`RdvReservationV1`, Punch2, Punch3, `BHP_*` y DVL.

### L4 — Property/model-based

Propiedades bloqueantes:

1. a lo sumo una sesión `CONNECTED`;
2. un evento stale no cambia estado;
3. cancelación es idempotente;
4. auth fallida nunca entrega bytes y solo reabre dentro del deadline;
5. todos los caminos terminan en `CONNECTED`, `DIRECT_UNREACHABLE` o
   `CANCELLED`;
6. predicción produce 0–17 destinos;
7. Birthday produce una sola expectation exacta;
8. R nunca aparece como endpoint de datos;
9. DVL no existe antes de un path autenticado;
10. cada recurso reservado se libera exactamente una vez.

Explorar interleavings de timeout, ACK tardío, cambio de generación,
desactivación, doble callback, auth fallida, caída de R y cierre del cliente.

### L5 — Coverage y mutation

Sobre código nuevo/modificado:

- líneas ≥90 %;
- branches ≥85 %;
- 100 % de reason codes y terminales ejecutados;
- mutation score ≥80 % en módulos objetivo;
- cero mutante superviviente que permita relay, datos antes de auth, más de un
  ganador, stale generation, `>17`, token inválido o migración DVL sin challenge.

Un umbral no sustituye la revisión de ramas críticas.

### L6 — Fuzzing y sanitizers

Targets:

- codecs y TLV;
- bridge nativo;
- candidates/receipts/reservations;
- mensajes Punch2/Punch3;
- todos los mensajes `BHP_*`;
- `DVL_INIT/ACCEPT`, varints, frames, tags y longitudes;
- API local y bundle diagnóstico.

Presupuesto mínimo:

| Lane | Tiempo por target |
|---|---:|
| PR focal | 10 min |
| nightly | 2 h |
| pre-RC | 12 h acumuladas |

ASan/UBSan o equivalentes se ejecutan donde la toolchain lo permita; Dr. Memory
o Application Verifier cubren el binario Windows nativo. Todo crash, timeout,
OOM o crecimiento no acotado bloquea.

### L7 — Requisitos ejecutables

Cada invariante del plan se expresa en Gherkin o test equivalente. Ejemplos:

```gherkin
Given a Punch2 ACK for the current attempt
When SecureIdent has not completed
Then the transport remains provisional
And no file byte, credit or slot is committed
```

```gherkin
Given R coordinated a valid Punch3
When A and B transfer a unique payload pattern
Then R contains control bytes
And rdv_file_payload_bytes equals 0
And rdv_livetv_payload_bytes equals 0
```

```gherkin
Given one peer is EIM and the other is EDM
When Birthday is disabled or maxK equals 0
Then no BHP socket or probe is created
```

### L8 — Red virtual determinista

Topología: A, B, dos W y hasta tres R sobre gateways programables.

Dimensiones:

- IPv4/IPv6/dual/CGNAT;
- EIM/ADM/APDM/EDM/secuencial/aleatorio;
- firewall IPv6 y UDP bloqueado;
- pérdida 0/1/5 %, reorder y RTT 20/100/400 ms;
- timeout, renovación, rebind y cambio de generación;
- nuevo↔nuevo y nuevo↔antiguo;
- control, descarga, subida, Source Exchange y LiveTV.

Cada fallo conserva seed, configuración NAT, logs y PCAP correlacionada.

### L9 — Integración nativa y éxito

PASS exige:

- socket final A↔B;
- identidad esperada;
- generación vigente;
- un ganador;
- primer bloque eD2K válido;
- hash final correcto;
- créditos, slot y contadores exactamente una vez.

Ejercicios:

- transferencia bidireccional;
- 4 GiB, hash y resume desde bloques confirmados;
- 100 ciclos connect/disconnect;
- LiveTV 12 Mbps durante 2 h con pérdida y cambio de path;
- callback clásico aplicable e inaplicable;
- auth fallida tras uTP provisional;
- desactivar todo durante cada estado.

### L10 — Witnesses y Punch3 adversarial

Witness:

- selección local pseudoaleatoria de 2–4;
- diversidad `/24` o `/48`, ASN cuando exista;
- exclusión de self, target y R;
- máximo cuatro consultas, cooldown y TTL;
- receipts contradictorios, stale, firmados por otro witness o sujeto;
- remoto incapaz de elegir witnesses.

R:

- reserva ligada a B, endpoint, servicio, generación, cuota y expiración;
- return-routability antes de estado caro/forward;
- duplicación, reorder, mutación, retención y redirect a tercera IP;
- caída de R tras `CONNECTED` sin cortar datos;
- búsqueda del hash/patrón de archivo y LiveTV en PCAP de R.

Los oráculos correctos permiten control en R y exigen cero payload de archivo y
LiveTV.

### L11 — Abuso, límites y privacidad

Presupuestos medibles:

- intentos activos globales, por peer y por prefijo;
- candidate checks por intento;
- witnesses y reservations por peer;
- forwards por token/R;
- expectations uTP;
- probes/segundo y sockets Birthday;
- streams DVL y bytes de reassembly.

Ningún valor remoto eleva límites. Probar replay, Sybil, spoof, reflection,
amplificación, clock wrap, token theft, churn, resource starvation y cleanup.

El bundle diagnóstico:

- se crea solo por acción explícita;
- muestra vista previa e inventario;
- no contiene claves, tokens, cookies, hashes/nombres de archivo, IP completas
  ni historial de puertos;
- pasa un escaneo automático con canarios sintéticos;
- documenta retención y deja claro que DVL no aporta anonimato.

### L12 — Birthday

Gate independiente:

- exactamente EIM↔EDM; doble EDM aborta;
- `CAP_BIRTHDAY_V1`, consentimiento bilateral y token efímero;
- token ligado a intento, peers, roles, IP, generación y expiración;
- `K≤256`, `B≤1024`, `≤100 probes/s`, deadline acotado;
- secuencia CSPRNG sin reemplazo;
- memoria O(K)+O(1), nunca O(B);
- cero objeto cliente/expectation por sonda;
- primer hit bloquea la ronda y crea una única expectation;
- cancelación en cada estado y cero sockets tras 100 ciclos;
- comparación B0/B1/B2/B3 con Punch2 en la misma topología;
- IDS/ICMP/throttling provoca abort, nunca escalado.

La distribución observada se compara con `1-exp(-KB/M)`, sin promover por
probabilidad teórica.

### L13 — DVL

Antes de código se congela suite, transcript y lifecycle mediante revisión
criptográfica independiente.

Gates:

- KAT de X25519/HKDF/AEAD y firmas;
- transcript ligado a roles, identidades, intento, generación, endpoints,
  capabilities y suite;
- downgrade/mutación de capabilities aborta;
- claves efímeras no persistidas ni registradas;
- nonces únicos, packet numbers monotónicos, replay window y wrap;
- rekey por tiempo/volumen;
- fuzz de handshake/framing;
- límites de streams/reassembly y fairness;
- ningún TUN/TAP, route, DNS, ARP, DHCP, LAN, loopback, WebServer o SMB;
- `PATH_CHALLENGE/PATH_RESPONSE` antes de migrar datos;
- spoof antes/después de challenge;
- fallback limpio a uTP crudo.

Un frame inválido cierra el link afectado, no el proceso ni otros links.

### L14 — Falsificación

Lane obligatoria antes de Beta:

| Hipótesis | Contraprueba |
|---|---|
| PCP crea path | denegar PCP o insertar CGN no controlado |
| witness descubre candidato | usar EDM que cambia endpoint hacia A |
| predicción es estable | consumir puertos en paralelo |
| Punch3 no relaya | buscar payload/hash en R |
| DVL migra legítimamente | spoof sin `PATH_RESPONSE` |
| no existe path | activar IPv6/mapping y repetir |

### L15 — Campo, estadística, soak y release

Laboratorio físico:

- dos routers de fabricantes distintos;
- CGNAT y móvil;
- IPv6;
- red corporativa/restrictiva;
- doble NAT;
- capturas A/B/R.

Cuatro rondas pueden servir como smoke. Todo porcentaje necesita al menos 30
intentos por sentido y celda en momentos distintos, cohorte, denominador,
intervalo de confianza y conservación de fallos.

Soak de 24 h:

- renovación de mappings y reservas;
- rotación R;
- cambio de dirección/generación;
- transferencia bidireccional y LiveTV;
- presión de memoria Core/A en peers, candidatos, mappings, reservas y sockets.

La presión sobre streams/reassembly pertenece a QA93-10 y se ejecuta solo con
`G-DVL`; no forma parte de L15 para `RELEASE-CORE`.
