# eMule eSE 9.4 — Runbook de ejecución DirectOnlyV1

Versión: 2.0

Plan rector: `V9.4_DEVELOPMENT_AND_TEST_PLAN.md`

Estado vivo: `V9.4_EXECUTION_STATE.md`

Gauntlet: `V9.4_ASSURANCE_STACK.md`

## 1. Objetivo

Convertir la WBS v9.4 en sesiones pequeñas, repetibles y resistentes a
interrupciones. Ninguna tarjeta puede introducir una segunda autoridad de ruta,
confundir señalización con transporte o habilitar relay de payload.

## 2. Orden de autoridad

1. decisión de producto que reconcilie tesis y especificación;
2. tesis técnica consolidada;
3. este plan y su assurance stack;
4. ADR/wire freeze aprobados;
5. tarjeta activa;
6. implementación.

Si dos niveles discrepan, se detiene la tarjeta y se registra el conflicto. No
se “resuelve” por inferencia local.

## 3. Estado inicial

La primera sesión comienza con:

```text
program_status = BLOCKED_BY_SPEC_RECONCILIATION
active_card    = NONE
budget_total   = 130 JP
dvl_budget     = 30 JP (NOT_APPROVED)
```

Solo `94-0.1`, `94-0.2`, lectura, auditoría y baseline son ejecutables mientras
`G-ENTRY` esté bloqueado.

## 4. Inicio mecánico de cada sesión

1. Abrir `V9.4_EXECUTION_STATE.md`.
2. Leer `program_status`, `active_card`, gates y defectos abiertos.
3. Ejecutar `git status --short`.
4. No tocar cambios ajenos.
5. Confirmar SHA y toolchain del manifest.
6. Elegir una única tarjeta `READY`.
7. Cambiarla a `IN_PROGRESS` antes de editar.
8. Escribir precondiciones y prueba roja.
9. Implementar el cambio mínimo.
10. Ejecutar lane focal y regresión exigida.
11. Pedir revisión independiente cuando corresponda.
12. Guardar artefactos y actualizar ledger.

No hay trabajo “rápido” fuera del ledger.

## 5. Tarjeta universal

Cada tarjeta contiene:

### A. Contrato

- requisito `DR94-F/I`;
- propietario de estado;
- inputs/outputs;
- `AttemptId` y `TopologyGeneration`;
- thread/lock/lifetime;
- límites y terminales;
- superficies de privacidad.

### B. Precondiciones

- dependencias `DONE`;
- gates verdes;
- flags y perfil;
- fixture y seed;
- files in-scope;
- cambios ajenos detectados.

### C. Rojo

- test que falla antes del cambio;
- resultado exacto esperado;
- artefacto conservado;
- razón por la que el test prueba el requisito.

### D. Implementación

- diff mínimo;
- sin API o dependencia no aprobada;
- sin segunda política de rutas;
- sin bypass temporal de seguridad;
- sin relay.

### E. Verde focal

- test rojo ahora verde;
- properties/mutants/fuzz aplicables;
- warning delta cero;
- sanitizers cuando haya parsing, lifetime o concurrencia.

### F. Regresión

- Core directo;
- generación/cancelación;
- single-winner/exactly-once;
- peer antiguo;
- kill switch;
- gate estructural no-relay;
- consumidor nativo afectado.

### G. Revisión

- revisor distinto en superficies críticas;
- findings S0–S3;
- evidencia de cierre;
- waiver explícito si procede.

### H. Cierre

- SHA/diff;
- comandos y exit codes;
- artefactos/hash;
- JP real;
- riesgos residuales;
- siguiente tarjeta desbloqueada.

## 6. Preflight

### `N0.1` — Observar el árbol

```powershell
git status --short
git rev-parse HEAD
rg --files libreach libnatmap libkad6 srchybrid tools
rg -n "ReachVector|TopologyGeneration|Punch2|Punch3|DirectReachabilityManager|REACH_RELAY|KRP_|RelayTransportAdapter" libreach libnatmap srchybrid
```

Salida: manifest de procedencia y mapa inicial de superficies. Una coincidencia
relay no implica por sí sola fallo; debe clasificarse como legado inerte,
decodificación compatible o ruta ejecutable. La última bloquea `DirectOnlyV1`.

### `N0.2` — Baseline de bibliotecas

```powershell
cmd /c libreach\make.bat
cmd /c libnatmap\make.bat
cmd /c libkad6\make.bat
```

Conservar stdout, exit code, toolchain y conteo. No copiar cifras históricas de
la tesis como si fueran del SHA actual.

### `N0.3` — Baseline host

```powershell
cmd /c srchybrid\tests\make.bat
python tools\check_direct_port_usage.py
```

Si el build nativo completo requiere entorno Visual Studio, registrar el
comando reproducible exacto y no declarar PASS con solo tests de biblioteca.

### `N0.4` — Baseline direct-only

Verificar:

- ninguna decisión hace hard-fail solo por LowID;
- orden Core observable;
- ACK no equivale a conexión;
- generación vieja no muta;
- un solo ganador;
- configuración hostil no activa relay;
- contadores R de payload en cero.

### `N0.5` — Inventario físico

Registrar disponibilidad real de:

- dos routers de fabricantes distintos;
- móvil/CGNAT;
- IPv6;
- red restrictiva;
- doble NAT;
- captura A/B/W/R;
- reloj y zona horaria;
- capacidad de repetir ≥30 intentos/sentido.

Una celda ausente queda `NOT_TESTED_PHYSICAL`.

## 7. Etapas de implementación

### Etapa A — Rebase y contrato

| Tarjeta | WBS | Acción | PASS |
|---|---|---|---|
| `A01` | `94-0.1` | congelar commit/toolchain | manifest completo |
| `A02` | `94-0.2` | reconciliar tesis/especificación | ADR aprobado |
| `A03` | `94-0.3` | gap audit | mapa reutilizar/corregir/crear/eliminar |
| `A04` | `94-0.4` | repetir baseline | logs hashados |
| `A05` | `94-0.5` | freeze trazabilidad/lab | 12 F + 12 I cubiertos |

No abrir Etapa B mientras `A02` siga roja.

### Etapa B — ReachVector y candidatos

Secuencia:

1. `B01`: decidir v2 completo o v3;
2. `B02`: codec y límites;
3. `B03`: bridge nativo completo;
4. `B04`: `CandidateGatherer`;
5. `B05`: publicación/ingestión;
6. `B06`: capabilities runtime;
7. `B07`: privacidad/LAN/TTL;
8. `B08`: métricas de evidencia.

Prueba roja clave: un vector que pierde generación, candidato o reserva al
atravesar host↔wire. PASS: round-trip semántico, unknown compatible y malformed
fail-closed.

### Etapa C — DCO y Direct Core

Secuencia:

1. `C01`: ADR autoridad única;
2. `C02`: estados y terminales;
3. `C03`: política Core;
4. `C04`: budgets, `AttemptId` y generación;
5. `C05`: efectos/reloj inyectables;
6. `C06`: nominación y single-winner;
7. `C07`: cancelación/shutdown;
8. `C08`: `TransportHandle`;
9. `C09`: reason chain;
10. `C10`: gate estructural no-relay;
11. `C11`: cache/cambio de topología.

Tabla mínima de rutas:

| Ruta | Aplicable | Vigente | Consentida | Resultado |
|---|---:|---:|---:|---|
| IPv6 | sí | sí | sí | gana sin probar posteriores |
| mapped v4 expirada | sí | no | sí | se descarta con reason |
| callback no aplicable | no | — | — | no consume budget |
| Punch2 | sí | sí | sí | solo gana tras auth |
| ninguna física | — | — | — | `DIRECT_UNREACHABLE_CORE` |

Prueba roja clave: completar dos transportes en el mismo tick. PASS: una sola
adopción, loser cerrado, una sesión y contabilidad única.

### Etapa D — Punch2, transporte e identidad

Secuencia:

1. `D01`: mapa wire actual;
2. `D02`: cookie ligada a identidad/intento/generación;
3. `D03`: expectation exacta y mismo socket UDP/uTP;
4. `D04`: separar ACK/transporte/éxito;
5. `D05`: autenticación mutua/transcript;
6. `D06`: primer bloque/chunk;
7. `D07`: replay/rate/cooldown;
8. `D08`: corpus hostil.

PASS end-to-end:

- PCAP muestra el mismo socket;
- ACK solo mueve estado de control;
- la identidad correcta precede a `CONNECTED`;
- el primer bloque válido precede a éxito de transferencia;
- replay cruzado no crea estado pesado.

### Etapa E — Advanced A

Secuencia:

1. `E01`: witness receipt tipado;
2. `E02`: diversidad W;
3. `E03`: reservas R rotatorias;
4. `E04`: wire/authority Punch3;
5. `E05`: máquinas A/R/B;
6. `E06`: half-RTT/PROCEED;
7. `E07`: cero payload/kill R;
8. `E08`: predicción ≤17;
9. `E09`: anti-scan/backoff;
10. `E10`: properties/fuzz/R malicioso;
11. `E11`: consentimiento/kill/caps.

La primera prueba E07 bloquea el resto de integración:

- capturas simultáneas A/B/R;
- socket remota A↔B;
- primer bloque válido;
- `rdv_file_payload_bytes == 0`;
- `rdv_livetv_payload_bytes == 0`;
- matar R no corta la transferencia.

### Etapa F — Advanced B

Secuencia:

1. `F01`: feasibility/threat;
2. `F02`: motor separado;
3. `F03`: clasificador EIM↔EDM;
4. `F04`: niveles B1/B2/B3;
5. `F05`: scheduler y tasa;
6. `F06`: memoria;
7. `F07`: cancelación;
8. `F08`: negativos;
9. `F09`: A/B, IDS y firewall;
10. `F10`: revisión independiente de entrada a campaña.

Stop inmediato:

- se inicia EDM↔EDM;
- se toca una expectation uTP normal;
- se sondea un IP que no pertenece al peer;
- B3 supera 100 sondas/s;
- queda un socket tras cancelación;
- el resultado se presenta como promesa de 70 % global.

F10 termina en `READY_FOR_PHYSICAL` o `NETLAB_STOP`. El segundo fija
`NETLAB_ONLY`; la promoción solo puede decidirse después de la celda física
Advanced B de Etapa I.

### Etapa G — Integración nativa

Orden:

1. descargas;
2. single-winner/exactly-once;
3. subidas;
4. Source Exchange;
5. LiveTV;
6. cambio de topología;
7. UI/API;
8. métricas/privacidad.

Para cada consumidor:

- eliminar su cascada paralela;
- solicitar un `TransportHandle`;
- adoptar una sola vez;
- cancelar losers;
- no mezclar identidad, endpoint o estado servidor;
- comprobar kill y rollback.

LiveTV no pasa si conserva `Direct → Punch2 → Punch3 → Relay`.

### Etapa H — Harness y assurance

1. NAT programable;
2. pérdida/reorder/RTT;
3. correlación PCAP;
4. runner F01–F10;
5. manifest/hash;
6. CI lanes;
7. intervalos;
8. gate estático;
9. orquestación física;
10. ejecución first-pass de L0–L10.

El first-pass técnico L0–L10 se completa antes de abrir la campaña física. No
se presenta como aceptación completa del stack.

L11 no puede cerrarse hasta terminar Etapa I. L12 no puede cerrarse hasta
Etapa J. `94-8.10` es la revisión independiente final, posterior a ambas.

### Etapa I — Campaña física

Orden:

1. controles IPv6, IPv4 directa, mapped y callback;
2. EIM/EIM Punch2;
3. EIM/EDM Advanced A;
4. EDM/EDM terminal negativo;
5. doble NAT;
6. móvil/CGNAT;
7. red restrictiva/UDP bloqueado;
8. cambio de topología;
9. Advanced B NetLab y decisión `PROMOTE/NETLAB_ONLY`;

11. LiveTV 2 h;

14. cierre L11.

No borrar fallos ni sustituir una celda física por simulación.

### Etapa J — Release

4. upgrade/downgrade/rollback;

## 8. Orden obligatorio por cambio

```text
CARD rojo
  -> build focal
  -> unit
  -> property/model
  -> static/no-relay
  -> fuzz/sanitizer si aplica
  -> integración nativa si aplica
  -> revisión
  -> lane CORE
  -> evidencia
```

Nightly, física y release se añaden según el gate. Saltarse una flecha deja la
tarjeta en `VERIFYING`, no en `DONE`.

## 9. Cierre de sesión

Antes de interrumpir:

- no dejar tarjeta en un estado ambiguo;
- cancelar procesos propios;
- no borrar artefactos fallidos;
- registrar el último comando y resultado;
- anotar cambios ajenos preservados;
- actualizar JP real y reserva;
- definir el siguiente paso mecánico;
- si hay riesgo S0/S1, poner `program_status = BLOCKED`.

## 10. Diagnóstico guiado

### Si no compila

1. identificar el primer error;
2. confirmar toolchain y SHA;
3. distinguir regresión propia de baseline rojo;
4. no editar archivos no relacionados;
5. conservar log completo.

### Si ACK aparece como éxito

1. inspeccionar transición DCO;
2. verificar expectation exacta;
3. buscar identidad y transcript;
4. exigir primer bloque;
5. añadir property con ACK duplicado/perdido.

### Si aparecen dos sesiones

1. correlacionar `AttemptId` y generación;
2. inspeccionar nominación provisional;
3. confirmar compare-and-adopt atómico;
4. buscar slot/crédito/bytes del loser;
5. ejecutar la carrera 100.000 veces.

### Si Punch3 “funciona” pero R tiene bytes

1. parar promoción;
2. preservar PCAP A/B/R;
3. clasificar S0;
4. localizar la ruta de forwarding;
5. reejecutar gate estructural y runtime.

### Si cambia la red

1. observar incremento de generación;
2. cancelar candidatos/reservas/expectations anteriores;
3. inyectar callbacks tardíos;
4. comprobar `no-op`;
5. volver a reunir candidatos.

### Si una celda no conecta

1. separar física, clasificación, implementación, autenticación y aplicación;
2. revisar reason chain;
3. verificar que la ruta era físicamente compatible;
4. aceptar `DIRECT_UNREACHABLE` como PASS si el agotamiento fue correcto;
5. no ampliar predicción ad hoc.

### Si aparece HighID inesperado

1. inspeccionar `server_id_state`;
2. verificar que route state no lo escribió;
3. buscar conversiones endpoint↔identidad;
4. ejecutar negativos de Punch2/Punch3/DVL;
5. clasificar como S1.

### Si queda un socket/timer

1. reproducir con seed;
2. identificar propietario;
3. ejecutar kill en cada transición;
4. comprobar idempotencia de callback tardío;
5. repetir 100 ciclos.

## 12. Cuándo pedir intervención humana

- reconciliar tesis y especificación;
- decidir v2 vs v3 si wire parcial ya se publicó;
- aprobar threat/crypto;
- habilitar puertos o topologías físicas;
- aceptar privacidad/telemetría;
- promover Advanced B fuera de NetLab;
- aprobar consumo de reserva;
- decidir una excepción S0/S1;
- activar la pista DVL;
- firmar Beta, RC y Stable.

## 13. Éxito de ejecución

La ejecución termina cuando:

- 130 JP o desviación aprobada están conciliadas;
- `G-ENTRY`, G0–G6 y `G-RELEASE` están verdes;
- `DirectOnlyV1` no puede construir relay;
- DCO es autoridad única;
- la cascada produce conexión directa o terminal honesto;
- identidad, single-winner y exactly-once están probados;
- R transporta cero payload;
- matriz física, 4 GiB, LiveTV 2 h, 100 ciclos y soak 24 h pasan;
- métricas publican cohorte, denominador e intervalo;
- Advanced B queda `PROMOTE` o `NETLAB_ONLY`;
- G7-DVL sigue separado salvo aprobación expresa;
- Stable y rollback tienen evidencia reproducible.
