# eMule eSE 9.4 — Política de orquestación de modelos

> **Archivo lógico histórico — 30 de septiembre de 2026.** Política histórica retirada: la v9.3 única no exige modelos concretos ni el routing descrito aquí.
> El plan vigente es [V9.3_PLUS_RELEASE_TRAIN.md](V9.3_PLUS_RELEASE_TRAIN.md)
> y el único ledger activo es [V9.3_EXECUTION_STATE.md](V9.3_EXECUTION_STATE.md).
> Se conserva íntegro el contenido anterior para trazabilidad; las menciones
> normativas, bloqueos y decisiones del cuerpo pertenecen a aquel plan.

Versión: 2.0

Ámbito: programa `DirectOnlyV1` de 130 JP

Objetivo: asignar implementación, revisión y verificación sin reducir gates ni
convertir la reserva en capacidad de razonamiento implícita

## 1. Principios

1. El modelo se elige por riesgo, no por longitud del diff.
2. Un cambio crítico recibe revisión independiente.
3. El implementador no firma su propio wire, crypto, authority model o gate.
4. Un modelo no inventa autoridad normativa.
5. Las pruebas y evidencia tienen precedencia sobre la confianza declarada.
6. El escalado no cambia JP ni criterios de aceptación.
7. KRP/relay permanece fuera del producto en todos los perfiles de modelo.
8. DVL necesita autorización propia y no se mezcla con la ruta crítica.

## 2. Perfiles

### Luna

Uso:

- búsquedas y clasificación mecánica;
- cambios locales de bajo riesgo;
- tablas, manifests y documentación;
- unit tests simples ya especificados;
- actualización del ledger;
- triage inicial de logs.

No decide:

- wire;
- ABI;
- propiedad de estado;
- crypto;
- thread/lifetime;
- gates;
- promoción.

### Terra

Uso:

- implementación acotada con contrato aprobado;
- codecs y fixtures no criptográficos;
- CandidateGatherer;
- harness/CI/evidencia;
- UI/API/métricas;
- integración localizada;
- property y fuzz harnesses;
- documentación técnica.

Escala si encuentra ambigüedad de autoridad, identidad, generación, socket
ownership, compatibilidad wire o seguridad.

### Sol

Uso obligatorio:

- reconciliación tesis/especificación;
- ReachVector v2/v3 y ABI;
- ADR de DCO;
- state machine, cancelación y single-winner;
- Punch2 same-socket y expectativas;
- identidad, transcript y forward secrecy;
- authority model Punch3;
- prueba estructural no-relay;
- birthday engine y promoción;
- exactly-once nativo;
- threat model y crypto DVL;
- revisión RC/Stable.

## 3. Algoritmo automático

Para cada tarjeta:

1. clasificar impacto `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`;
2. identificar superficie;
3. comprobar si existe contrato aprobado;
4. asignar implementador;
5. asignar revisor distinto;
6. definir lane y artefactos;
7. registrar la decisión antes del cambio.

```text
si cambia autoridad/wire/crypto/single-winner/no-relay:
    IMPL = Sol
    REVIEW = Sol independiente
si ejecuta contrato crítico ya congelado:
    IMPL = Terra
    REVIEW = Sol
si es mecánico y local:
    IMPL = Luna o Terra
    REVIEW = Terra
si el contrato es ambiguo:
    STOP -> Sol/humano
```

## 4. Escalado obligatorio

Escalar a Sol cuando:

- se decide v2 o v3;
- un callback carece de `AttemptId` o `TopologyGeneration`;
- una ruta puede ganar antes de autenticación;
- dos consumidores tienen políticas distintas;
- se toca socket pool/expectation uTP;
- se mezcla endpoint, identidad o estado servidor;
- R puede elegir target o tocar payload;
- predicción supera 17 o sale del IP propio;
- birthday toca el motor normal;
- aparece EDM↔EDM;
- kill/shutdown no converge;
- el gate no-relay depende solo de configuración;
- una métrica podría inflar éxito directo;
- se propone incluir DVL en Stable;
- un waiver afecta S0/S1.

Escalar a humano cuando:

- hay conflicto normativo;
- falta consentimiento o base legal/privacidad;
- se necesita infraestructura física;
- se consume reserva;
- se promueve Advanced B;
- se acepta Beta/RC/Stable;
- se autoriza DVL.

```text
CARD:
WBS:
REQUIREMENTS:
RISK:
PROFILE:

FILES OUT OF SCOPE:
PRECONDITIONS:
RED TEST:
IMPLEMENTATION CONTRACT:
INVARIANTS:
COMMANDS:

```

Ejemplo:

```text
CARD: C06-single-winner
WBS: 94-2.6
REQUIREMENTS: DR94-F09, DR94-I01, I04, I06, I07
RISK: CRITICAL
PROFILE: Sol
FILES IN SCOPE: DCO state/arbiter tests
FILES OUT OF SCOPE: UI, DVL, relay
RED TEST: dos transportes autenticados completan en el mismo tick
PASS: una adopción; loser cerrado; slot/crédito/bytes exactly-once
REVIEWER: Sol independiente
STOP: callback sin AttemptId/generación o segunda autoridad host
```

## 9. Registro por tarjeta

```yaml
card: C06-single-winner
impl_profile: Sol
impl_run: UNSET
review_profile: Sol
review_run: UNSET
independent: true
sha_before: UNSET
sha_after: UNSET
red_evidence: UNSET
green_evidence: UNSET
findings: []
decision: UNSET
```

No registrar nombres vagos como “AI review”; se necesita run, perfil, entrada,
salida y decisión.

## 10. Autonomía permitida

Luna/Terra pueden:

- ejecutar lecturas y pruebas;
- implementar una tarjeta con contrato cerrado;
- añadir tests y artefactos previstos;
- actualizar el ledger;
- detenerse ante un stop condition.

No pueden sin autorización:

- cambiar alcance o presupuesto;
- reinterpretar wire;
- debilitar auth, límites o no-relay;
- promover Advanced B;
- consumir reserva;
- iniciar DVL;
- aceptar Beta/RC/Stable;
- modificar la autoridad normativa.

## 11. Reserva y desvíos

El modelo propone; el humano aprueba:

- JP solicitadas;
- causa;
- alternativa;
- riesgo de no hacerlo;
- gate afectado.

Una tarea que añade KRP, relay, TUN/TAP o DVL no es estabilización y no puede
imputarse a `94-R`.

## 12. Definition of Done

La orquestación está terminada cuando:

- toda tarjeta tiene implementador y revisor;
- los cambios críticos tienen independencia real;
- checkpoints conservan entradas, findings y decisión;
- no hay autoridad normativa inventada;
- el escalado fue trazable;
- la reserva fue aprobada explícitamente;
- Advanced B y DVL tienen decisiones separadas;
- los modelos nunca redujeron el perfil `DirectOnlyV1`.
