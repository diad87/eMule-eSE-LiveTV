# eMule eSE 9.8 — Envolvente de interoperabilidad y seguridad de servidores

Estado: **PROPOSED / NOT AUTHORIZED**  
Tren: `V98-SERVER-INTEROP`  
Fecha de propuesta: 15 de agosto de 2026  
Estimación inicial: **95–135 JP / 24–34 semanas** a tiempo completo  
Reestimación obligatoria: freeze de 9.7

Este documento no es un plan normativo de desarrollo. Conserva una propuesta
trazable para después de 9.7; no modifica `V9_RELEASE_SPECIFICATION.md`, no
autoriza implementación y no puede seleccionar una tarjeta activa.

## 1. Objetivo

Convertir la compatibilidad receptora preparada en 9.7 en interoperabilidad
activa y segura con eMuleQt, eNode y servidores clásicos, sin sustituir Kad6,
Punch2/Punch3, el perfil `DirectOnlyV1` ni el
`DirectConnectionOrchestrator` (DCO).

9.8 añade señalización y transporte del enlace cliente-servidor. El servidor:

- nunca transporta archivos o LiveTV;
- no se convierte en autoridad de rutas peer-to-peer;
- no promete conectividad universal detrás de CGNAT;
- ve las búsquedas, publicaciones y endpoints necesarios para operar; TLS no
  oculta esos datos al propio servidor.

## 2. Dependencias obligatorias

| Release | Contrato requerido |
|---|---|
| 9.5 | endpoint dual-stack canónico, procedencia, verificación, TTL, dedupe, source cache y persistencia versionada |
| 9.6 | preferencias por servidor, diagnóstico, privacidad de logs, reset y rollback visibles |
| 9.7 | checklist receptor completo: `0xAA/0xAD/0xAE`, flags servidor `0x4000`, sentinel `0xFFFFFFFF`, ExtSX v1, `0xA0/0xAC/0x9A`, server-list IPv6, hints Kad `ip6`/`bi6`, callback `0x26`, filtros IPv6, DCO estable y `REG-DEBT-001` resuelto antes de emitir |
| upstream | especificación pública, namespace y reserva verificable para todo identificador nuevo |

Si falla una dependencia, 9.8 no crea una ruta paralela para esquivarla. La
interoperabilidad eSE-private/JEmuleServer se conserva como dialecto separado;
no se reinterpreta silenciosamente como eMuleQt/eNode.

## 4. Work packages propuestos

### `WP98-0 — REGISTRY-CONFORMANCE`

Promover el catálogo y laboratorio ya preparados. Añadir golden packets,
PCAPs, corpus hostil, pruebas diferenciales y detección automática de
colisiones. Ningún identificador nace de documentación narrativa.

### `WP98-1 — SERVER-INTEROP`

Conservar perfiles descriptivos `CLASSIC`, `EMULEQT_ENODE_IPV6_V1` y
`ESE_PRIVATE_V1`, pero decidir runtime solo por capacidades. Recepción primero:
no dial IPv6 ni anuncio `0xAE` antes de demostrar que el sentinel no puede
desalinear el paquete.

### `WP98-2 — CROSS-SERVER-CALLBACK`

Una fuente contiene la identidad verificable del servidor del destino y un
voucher opaco, corto y de un solo uso. El solicitante habla directamente con
ese servidor; no se exige federación servidor-A↔servidor-B. El servidor prueba
return-routability antes de notificar al LowID.

La notificación entra al DCO solo como candidato correlacionado por
`transaction_id`, `attempt_id` y `topology_generation`. El callback clásico
continúa disponible cuando sea aplicable.

### `WP98-3 — RENDEZVOUS-V2`

`PR_NAT v1` se reconoce únicamente para diagnóstico. Un user hash de login no
autentica por sí solo un datagrama UDP. `RendezvousV2` utiliza una capacidad
distinta y exige:

- identidad cliente obligatoria mediante prueba de posesión SecureIdent, mTLS
  u otra clave pública verificada; el `user_hash` solo correlaciona y nunca
  autentica;
- además, channel binding: TLS exporter cuando exista TLS, o challenge firmado
  ligado a `server_id/session_generation` sobre transporte clásico; el binding
  de canal nunca sustituye la autenticación de identidad;
- token/MAC emitido por el servidor después de esa prueba y ligado a
  `(server_id, session_generation, verified_public_key, channel_binding,
  expiry, purpose)`; no funciona como bearer token reutilizable;
- cada datagrama UDP firma o autentica con MAC `server_id`, generación,
  transacción, familia, propósito y nonce; el servidor nunca acepta un
  `srcHash` arbitrario ni un token copiado desde otra sesión/canal/endpoint;
- endpoint obtenido del paquete observado;
- challenge/cookie de return-routability;
- consentimiento del destino antes de revelar endpoints;
- nonce/transacción de 128 bits, TTL corto y uso único;
- cache anti-replay acotada y limpieza determinista;
- límites por IP, `/64`, hash, sesión, destino y servidor;
- límite global de memoria;
- amplificación máxima 3× antes de validar retorno;
- logs sin hashes, tokens o endpoints completos por defecto.

Si falta la autenticación de identidad o el binding verificable del canal, todo
`RendezvousV2` permanece fuera de alcance y deshabilitado: no se degrada a
confianza por user hash.

### `WP98-4 — TLS-TCP`

El servidor anuncia un endpoint TLS explícito; no se adivina `STARTTLS`.
Validación PKIX cuando exista nombre estable y pin/TOFU para servidores
identificados por IP. Una conexión previamente validada no cae a plaintext sin
política explícita del usuario y diagnóstico visible. Cero datos eD2K en 0-RTT.

### `WP98-5 — SERVER-QUIC`

Un selector único del enlace de servidor, separado del DCO de peers, elige
QUIC/TLS-TCP/TCP clásico. QUIC transporta exactamente la semántica ya validada:
no añade opcodes. UDP bloqueado, pérdida, timeout o fallo producen fallback
acotado, cancelación del intento perdedor y nunca duplican login, publicación,
búsqueda o callback.

### `WP98-6 — PHYSICAL-LAB-RELEASE`

Matriz fijada por versión/commit con eMule clásico, eSE, eMuleQt, eNode-go y los
servidores disponibles. JEmuleServer y ed2kNET solo entran cuando fuente,
build, licencia y snapshot son reproducibles.

## 5. Gates de promoción

| Gate | Bloquea | PASS requerido |
|---|---|---|
| `G98-SPEC` | todo emisor nuevo | registro, threat model, reserva upstream y downgrade escritos |
| `G98-RX` | dial IPv6 y anuncio `0xAE` | golden packets, truncación, fuzz y cero desalineaciones/crashes |
| `G98-SERVER` | interop activa | IPv4-only, IPv6-only y dual-stack con controles vanilla |
| `G98-XCALLBACK` | `V98-F03` | dos clientes, dos servidores y redes distintas; 30/30 casos aplicables y cero callbacks no autorizados |
| `G98-RDV2` | `V98-F04` | cero secuestros, replays o disclosures; negativos de hash ajeno, mismo hash en conexión distinta, nuevo canal TLS con ese hash pero sin su clave privada, token robado, token desde otro canal/endpoint, replay entre sesión/servidor/familia, rotación y cierre; cuotas, memoria y amplificación acotadas |
| `G98-TLS` | `V98-F05` | certificado correcto/caducado/hostname erróneo, pin cambiado, rotación y MITM |
| `G98-QUIC` | `V98-F06` | UDP bloqueado, pérdida, reordenación y migración; fallback sin duplicar estado |
| `G98-RELEASE` | Stable | regresión 0.70b, rollback, clean checkout, matriz física y soak de 72 h |

Pruebas trazables propuestas: `V98-A01` build/registro, `V98-W01` wire/fuzz,
`V98-I01` interop, `V98-C01` callback, `V98-N01` NAT, `V98-T01` TLS,
`V98-Q01` QUIC, `V98-S01` abuso y `V98-R01` rollback.

Los gates son independientes. Un PASS TLS no valida NAT; un PASS de callback no
valida QUIC. Una función con gate rojo no se anuncia y permanece cerrada por
defecto.

## 6. Fuera de alcance

- reemplazar eD2K/Kad o retirar compatibilidad clásica;
- copiar `PR_NAT v1` sin cambios;
- hacer obligatorio TLS o QUIC;
- relay de archivos/LiveTV a través de servidores;
- ocultar al servidor los datos que necesita para operar;
- garantizar conexión entre dos NAT simétricos/EDM;
- asignar opcodes sin acuerdo verificable;
- confiar en nombre, versión o banner autodeclarado;
- introducir cualquiera de estos cambios en 9.2–9.4;
- reintroducir KRP, TURN o relay de payload en `DirectOnlyV1`.

## 7. Riesgos que debe cerrar el plan normativo

| Riesgo | Mitigación obligatoria |
|---|---|
| Desalineación por sentinel | `G98-RX` antes de dial/anuncio |
| Colisiones de opcode/tag | registro namespaced, catálogo externo y linter |
| Secuestro de user hash | identidad cliente con prueba de posesión **y** binding de canal; token/MAC ligado a sesión y propósito; rechazo de todo hash aportado sin ambos |
| Reflexión y endpoint disclosure | return-routability, consentimiento y antiamplificación |
| Downgrade TLS | estado seguro persistente y fallo visible |
| Bloqueo selectivo de QUIC | fallback acotado y kill switch |
| Doble autoridad de rutas | toda señal produce candidatos; solo DCO decide |
| Fragmentación entre mods | emisión tras capacidad y vectores públicos |
| Deriva upstream | commits congelados y repetición del laboratorio |
| Pérdida de privacidad | redacción, retención mínima y métricas agregadas |

La creación del plan normativo exige `9.7 Stable`, un informe del laboratorio,
presupuesto reestimado y una decisión explícita del propietario. Hasta
entonces, el estado permanece `PROPOSED / NOT AUTHORIZED`.
